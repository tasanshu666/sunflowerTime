## 1. M2：经济与商店核销

### 1.1 M2 的产品定位

M1 打通了「专注 → 阳光」的产出链路；M2 补上**消耗侧**：孩子把阳光花出去、家长在现实里兑现、并把「孩子自己说了算」改成「家长点了才算」。

一句话：**孩子发起，家长核销，钱（阳光）只有家长点过确认那一刻才真正扣除。**

### 1.2 阳光账本（append-only）

| 项 | 规则 | 出处 |
|---|---|---|
| 记账方式 | **只追加、不修改、不删除**。每一笔阳光变动写一行，余额由流水推导 | `SunlightRepository.append`；`SunlightType` 枚举注释「§3.2 append-only」 |
| 一笔记录含 | 时间 / 类型 / 原始额 `gross` / 实得额 `net` / 当时余额 `balanceAfter` / 来源标识 `refType` / 关联 id / 日键 `dayKey` | `sunlight_entry.dart` |
| 账本类型 | `earn`（产出）、`redeem`（兑换扣减）、`queueRelease`（排队放行扣减）、`plant`（植物消耗，M3 起） | `enums.dart` `SunlightType` |
| 可追溯性 | 家长能在孩子端「我的 → 来源」逐笔回看，任何一笔都能追到来源 | `child_sunlight_history_page.dart` |

**阳光来源标识（`refType`）与用户可见文案对照表**（单点收口，UI 不散落字面量）：

| `refType` | 来源页显示 | 计入方向 |
|---|---|---|
| `focus` | 专注产出 | 收入 |
| `task_checkin` | 成长项奖励 | 收入 |
| `plant_plant` | 种植植物 | 支出 |
| `plant_water` | 浇水 | 支出 |
| `plant_fertilize` | 施肥 | 支出 |
| `plant_revive` | 救回植物 —— ⚠️ **已废止**（付费救回已取消，见宪法 C12；该类型仅用于读懂历史账本） | 支出（历史） |
| `plant_expand` | 花园扩容 | 支出 |
| `plant_death_refund` | 植物死亡返还 | 收入 |
| `redeem` | 兑换奖励 | 支出 |
| `queueRelease` | 阳光池释放 | 支出 |
| `parent_gift` | 家长赠予 | 收入 |
| `debug_grant` | 调试发放 | 收入（**提审前须删除，见 §7-3**） |

> `refType='task_checkin'` 是**数据标识不是文案**。M3 把用户可见的「任务」统一改成「成长」时刻意**不改**它，否则与历史账本对不上（见 §2.6）。

### 1.3 每日额度（2026-09-23 起两条独立额度线）

> **旧口径已废**：原「分段软顶」（0–60 全额 / 60–90 计 50% / 90–110 计 20% / 硬顶 79）已由玄参拍板**取消**。
> 原因：分段的第一段本身就是「60 分钟以内全额」，与「封顶跟随年段」在数学上不能共存；旧口径下高年段孩子专注满 120 分钟只能拿 79 阳光。裁定见 `口径裁定表_v1.md` C11。
> 下文历史记录（§3.6 / §5 的漏洞台账）里出现的「软顶」二字，均指**当时的旧口径**。

**① 专注额度（跟随年段）** —— 专注产出恒为 1 分钟 = 1 阳光，不折损，但当日专注总量封顶：

| 年段 | 年级 | 每日额度 | 常量 |
|---|---|---|---|
| 低 | 1–2 年级 | 60 分钟 / 60 阳光 | `kDailyFocusCapLow = 60` |
| 中 | 3–4 年级 | 90 分钟 / 90 阳光 | `kDailyFocusCapMid = 90` |
| 高 | 5–6 年级 | 120 分钟 / 120 阳光 | `kDailyFocusCapHigh = 120` |

**② 成长奖励额度（独立）** —— 打卡发放的阳光单独封顶 **79**（`kTaskCheckinDailyCap`）。

- 两条线**各读各的账目类型**（专注看 `focus_session`、成长看 `task_checkin`），因此**互不挤占**：当天专注拿满、或家长赠予到账，都**不会**让成长奖励发不出来（这是本次一并修掉的旧 bug，见 §6-1）。
- 额度只压**收入**，不碰已有余额；离席、拒绝、驳回都不会倒扣。
- **三道拦**：选时长页把超剩余额度的档位置灰并提示「今天还可以专注 N 分钟」→ 开始前按剩余额度截断 → **结算时再硬截断一次**（`effectiveFocusSunlight`）。结算这道是唯一可靠的兜底，防计时器因「离席恢复」多算。
- **「其他年级无限制」不落地**：档位只有低 / 中 / 高三档，App 没有第 4 档入口，产品只服务 1–6 年级。

### 1.4 阳光池：月池 → 周池

| 项 | 规则 | 出处 |
|---|---|---|
| 周期 | **自然周**（周一 0 点重置） | `weekKey`；`WeeklyPoolService.ensureAndReset` |
| 默认预算 | 高年段 **400**、低年段 **160** | `kPoolBudgetDefaultHigh / Low` |
| 家长可调区间 | **50 – 500**（2026-09-22 玄参拍板：原上限 1200 太大，收到 500；输入越界提示且不保存） | 常量 `kWeeklyPoolBudgetMin/Max`（`prd_params.dart`），`pool_indicator.dart` 引用；卡面提示「建议值 400」 |
| 池的口径 | 「本周已花出去多少阳光」，与账本余额是两套独立对账 | `WeeklyPool{used, autoReleased, budget}` |
| 历史包袱 | 原设计是**月池**（物理表仍叫 `monthly_pools`、列仍叫 `monthly_pool_budget`）。2026-09-21 拍板改周池时**刻意不迁表**（避免破坏已装调试库），只在 Dart 域标识层改名 | `weekly_pool_local_repository` / `settings_local_repository` 内部映射 |

### 1.5 奖励模板与每周限领（冷却）

| 项 | 规则 | 出处 |
|---|---|---|
| 模板来源 | 家长在「奖励」tab 增删改；首次启动播种 5 条占位模板 | `reward_seed.dart` |
| 种子模板 | 小零食 20 / 选今晚动画片 40 / 多玩 10 分钟 60 / 周末出去玩 120（以上家长经手类）；多看一集动画片 50（**自服务类**） | `kSeedRewardTemplates` |
| 限领 | 每模板 `frequencyLimitPerWeek`（默认 **1 次/周**）；`≤ 0` 视为**不限次数** | `kCooldownWeeklyDefault = 1`；`RedemptionService` / `_onCooldown` |
| 计数时机 | **落单即计数**（`createRequest` 后 bump 本周冷却计数），核销不重复计数 | `reward_local_repository.createRequest` |
| 卡片文案 | 剩余 = 限领 − 本周已领；`≤0`→「不限次数」；剩 ≥2→「可兑换次数为 N」；剩 1→「仅可兑换 1 次」；剩 0 → 隐藏 | `reward_template.dart` `weeklyRedeemLabel` |
| 定价 | **家长设定价 = 孩子显示价 = 实际扣费价**（2026-09-21 起不再叠加分龄系数 K） | 口径裁定表 **C10**；`_priceFor` 直接返回 `baseCost` |

### 1.6 兑换申请状态机

| 状态 | 含义 | 何时扣阳光 | 用户看到什么 |
|---|---|---|---|
| `pending` 待核销 | 已发起、等家长处理 | **不扣** | 孩子端卡片显示「待家长核销」；家长端「今日」出现核销卡 |
| `queued` 排队中 | 超本周池，顺延到下周 | **不扣** | 孩子端卡片显示排队位次 + 「撤销排队」；家长端可「立即发放」 |
| `verified` 已核销 | 家长点确认（或超池次周自动释放 / 家长强制立即发放） | **此刻才扣** | 孩子端弹窗「🎉 家长已确认你的兑换」，列出逐笔与合计 |
| `rejected` 已拒绝 | 家长点拒绝（可写理由） | **从不扣** | 孩子端弹窗「🚫 兑换未被通过」，显示家长理由，提示「本次阳光未被扣除，可重新兑换」 |

**判流走向（孩子端发起一次兑换）**：

| 情形 | 结果 |
|---|---|
| 冷却未过（本周已领满） | **不生成申请**，按钮灰掉（不埋兑换事件） |
| 阳光余额不足 | **不生成申请**，提示余额不足（不埋兑换事件） |
| 以上都通过 | 生成申请；**孩子端一律强制进入 `pending`**（即使满足免确认双条件也不自动放行） |
| 本周池放不下 | 进 `queued`，下周按申请先后自动释放；也可由家长「立即发放」 |

> **C5 免确认双条件仍保留在判定逻辑里**（① 单笔 ≤ 高 130 / 低 50；② 本周累计自动放行 ≤ `min(固定天花板 高100/低40, 周池×25%)`；③ 自服务类一律不自动放行），但**对孩子端发起路径已不生效** —— 孩子端传 `forcePending = true`，所有兑换都要家长点一下。

### 1.7 家长端核销与驳回

| 项 | 规则 |
|---|---|
| 入口 | 家长端「**今日**」tab（待处理流，有时效性）；空则整卡不渲染，显示「暂无待确认奖励 🎉」 |
| 核销步数 | **≤ 2 步**：看到卡 → 点「确认兑换」→ 弹窗二次确认「确认核销？」→ 完成。避免误触直接扣阳光 |
| 驳回 | 点「拒绝」→ 弹窗「确认拒绝？」→ 可填理由（选填）→ 完成。**阳光原路返回**（本来就从未扣除） |
| 排队处理 | queued 只能由「立即发放」或跨周 `releaseQueue` 放行，不能当 pending 核销（按钮禁用） |
| 48h 兜底 | 申请距提交 > **48 小时**未处理，家长端卡片与孩子端卡片显示「这次的阳光奖励还在等你确认哦～」 |
| 孤儿申请 | 成长项被家长删除后，其历史 pending 仍可在「今日」核销，名字显示「（已删除的成长项）」—— 属预期行为，方便清历史 |

### 1.9 M2 用户可感知路径（实测路径）

```
孩子端「商店」tab
   ↓ 挑一张奖励卡（显示价格 X 阳光 + 本周剩余次数）
点「兑换」
   ├─ 本周已领满 → 按钮灰掉，点不动
   ├─ 阳光不够   → 提示余额不足
   └─ 成功       → 卡片变「待家长核销」
家长端 PIN → 「今日」tab
   ↓ 看到核销卡（提交时间 / 价格 / 48h 兜底提示）
   ├─「确认兑换」→ 二次确认 → 阳光此刻才扣 → 孩子端弹「🎉 家长已确认你的兑换」
   └─「拒绝」    → 二次确认（可填理由）→ 阳光未扣 → 孩子端弹「🚫 兑换未被通过」
```

### 2.7 植物养成

**阶段与状态**：

| 维度 | 取值 | 说明 |
|---|---|---|
| 阶段（3 个） | 种子 → 幼苗 → 成株 | 一段长满进下一段；成株长满 = 开花 |
| 状态（4 个） | 成长中 / 已开花 / 枯萎中 / 已死亡 | 开花后**保持 3 天即花谢**，回到成株/成长中，养满可再盛开（循环，见下） |
| 心情（3 个） | 开心（今日有有效专注）/ 平静 / 口渴 | 枯萎→口渴；死亡→平静 |

**养护动作**：

| 动作 | 价 | 次数/间隔 | 效果 | 限制 |
|---|---|---|---|---|
| 浇水 | 5 阳光 | 每天最多 **3** 次，两次间隔 ≥ **30 分钟** | 本阶段进度 **+1%** | **成长中 / 枯萎中**可做（开花期不可） |
| 施肥 | 10 阳光 | 每天 **1** 次 | 本阶段进度 **+3%** | **成长中 / 枯萎中**可做（开花期不可） |
| 恢复 | **免费**（靠养护，见下） | 见「枯萎与死亡」 | 枯萎中 → 成长中 | 仅枯萎中 |
| 清理（铲除回收） | 免费 | — | 死亡植物移出花盆，可重种 | 仅已死亡 |
| 扩容 | 低年段 **160** / 高年段 **400** 阳光 | 每次 +1 盆 | 花园容量 4 → 最多 12 | 见下方确认卡 |

**枯萎与死亡**（只与养护挂钩，**绝不因专注表现杀死**）：

| 事件 | 触发 | 后果 |
|---|---|---|
| 枯萎 | **3 天**未浇水（浇水/施肥都会刷新计时） | 状态 → 枯萎中 |
| **恢复** | 枯萎**未满 3 天**：浇水 **1 次**即恢复；枯萎**已满 3 天**：需浇水 **3 次 + 施肥 1 次** | 状态 → 成长中（`wiltedAt` 清空） |
| 死亡 | 枯萎后**再 7 天**仍未恢复 | 状态 → 已死亡，返还 **30% 种植成本**到阳光账本，花盆释放 |

> ⚠️ **付费救回已取消**（玄参 2026-09-23 拍板，宪法 **C12**）：原「花 20/8 阳光救回」整段删除（`revive()` + `kPlantReviveCostLow/High` 不存在），枯萎**只能靠养护恢复**。恢复次数**以账本为唯一事实源**派生，不给 `Plants` 表加计数列。

**花谢循环**（玄参 2026-09-23 拍板，宪法 C12）：成株盛开保持 **3 天**（`kBloomDurationDays`）→ 花谢（状态 → 成长中、进度回落至 **0.5** `kBloomWiltProgressFloor`，**体型保持成株不缩回幼苗**）→ 由时间/养护重新养满后**自动再盛开**。

**成长速度**：当日有有效专注（WFD）→ 当天速率 **×1.3**；没有专注也照样长（**×1.0**，软绑定底线）。

| 物种 | 稀有度 | 高价 / 低价 | 每阶段时长 |
|---|---|---|---|
| 向日葵 | 普通（初始物种） | 0 / 0 | 普通档 |

## 3. M4：成长项联动 + 家长核销（防作弊）

### 3.1 起因：玄参报的经济漏洞

> 「比如数学专注 10 分钟，是不是需要和专注联动？……如果不联动，孩子点我做到了，阳光直接核销，没有家长监管，是不是孩子容易不做这个事情，也会刷分？」

核实属实，共 4 处：① 一次专注可解锁当天**所有**需专注项（一鱼三吃）；② 家长端对成长项打卡**零引用**；③ 非联动项随手可点、点了就发钱；④ 原设计里「任务数 × 完美日系数」那条公式自 M2 起**从未被调用**（唯一调用点从未传值）。

### 3.2 两类成长项（核心规则）

| | **联动项**（专注联动） | **非联动项** |
|---|---|---|
| 判定 | 家长勾了「专注联动（自动结算）」 | 未勾 |
| 孩子端按钮 | **「开始专注 · 需 N 分钟」**（**没有**可点的打卡按钮 → 无从刷分） | **「我做到了」** |
| 流程 | 从该项进入专注 → 专注达标 → **自动结算**（直接入账） | 点「我做到了」→ 落 **待家长确认** → 家长核销后才入账 |
| 归属 | 从成长项进入专注，专注会话与该项**一一绑定** | — |
| 阳光奖励 | **固定 = 最少专注分钟 × 40%**，家长不再可调 | 家长定价（默认 **8**，区间 **5 – 15**） |
| 家长可驳回 | 否（专注达标即生效） | 是，可写理由 |

### 3.3 奖励上限 = 最少专注分钟 × 40%

| 项 | 规则 | 出处 |
|---|---|---|
| 比例 | `kTaskRewardRatio = 0.4` | `prd_params.dart` |
| 公式 | 奖励上限 = 最少专注分钟 × 40%（四舍五入，至少 1） | `Task.rewardCapFor` |
| 适用范围 | **只作用于联动项**；非联动项归家长定价 | `Task.effectiveSunlightReward` |
| 单点收口 | 编辑器与结算共用同一公式，禁止各处复写 | `task.dart` |
| 滑杆 | 最少专注 **5–60 分钟** → 奖励上限随之 **2–24**；分钟下调或联动开关切换时自动夹回 | `task_editor_dialog.dart` |
| 历史超标数据 | 编辑器打开即显示夹回后的合法值，但**数据库原值不动**（家长把分钟调大后奖励自动恢复） | 2026-09-22 拍板 |
| 连带影响 | 种子项「完成学校作业」「练习数学口算」（15 分钟 / 家长设 12）生效值 **12 → 6**；「阅读 20 分钟」是非联动，仍按家长设定值 | 工作日志 |

### 3.4 完美日

| 项 | 规则 |
|---|---|
| **×1.5 系数** | **已移除**。奖励变成确定值，不再叠加任何系数（常量 `kPerfectDayCoefficient = 1.5` 仍在 `app_constants.dart` 但奖励公式已不引用） |
| 剩下什么 | 只留**徽章语义**：当日「每日成长项」全部提交 → 弹「🌻 今日成长项全部完成！…获得「完美日」标记！」 |
| 判定口径 | 按「**已提交**」判定：联动项自动结算算提交、非联动项打卡算提交 —— **不等家长核销**，保持即时情绪反馈 |
| 统计范围 | **只统计每日项**（`repeatRule` 为 null / 'daily'）。每周项（`weekly`）仍列出、仍可打卡，但**不计入完美日** |
| 被驳回 | 不算「已做到」，不凑完美日；但**可以重做**（新增一行，保留审计痕迹） |
| 降级说明 | PRD 原文要求「同日**同科**专注 + 打卡」，但专注会话**没有科目字段**，无法判定学科 → 降级为「当日存在 ≥15 分钟专注」 |

### 3.5 家长核销入口与成长奖励额度

| 项 | 规则 |
|---|---|
| 入口 | 家长端「**今日**」tab 的「待确认的成长项」卡（核销有时效性）；空则整卡不渲染 |
| 核销 | 点「确认发放」→ 入账；只对**待确认**记录生效，重复点会被拦（这是钱） |
| 驳回 | 点「驳回」→ 弹「驳回这项成长？」→ 可填理由（选填）→ 不入账 |
| 成长奖励额度 | 按**打卡原始日**核算：`实发 = max(0, min(本次奖励, 79 − 当日已发的打卡阳光))`，**只读 `task_checkin` 自身账目** —— 不读当日全部收入，所以专注拿满、家长赠予到账都不会挤占它 |
| `pending` 不占额度 | 只有真正入账才计入当日打卡收入合计，家长迟迟不核销不会把当日额度白占掉 |
| 孤儿记录 | 成长项被删除后其历史待确认仍可核销，名称显示「（已删除的成长项）」 |

### 3.7 数据变更记录

| 版本 | 内容 |
|---|---|
| v4 → v5 | `tasks` 补 `custom_subject` 列（自定义科目） |
| v5 → v6 | `check_ins` 补 5 列：`status` / `sunlightGross` / `sunlightGranted` / `resolvedAt` / `parentNote`。**枚举顺序刻意把「已核销」放 index 0**：老库补列默认值 0 会把历史打卡视为「已核销」（历史行为确实是打卡即入账）；若把「待确认」放 0，升级后会突然冒出一堆历史遗留待办 |
| v6 → v7 | 成长中的植物**重置清零**，已开花 / 枯萎 / 死亡**保留** |

当前 `schemaVersion = 7`。

### 3.8 M4 其他已拍板口径

| 项 | 口径 |
|---|---|
| 归属机制 | 从成长项进入专注建立绑定，**不给专注会话加科目列**（省一次迁移 + 一套选科 UI） |
| 每日项 / 每周项 | `repeatRule` 取值域只有 `null / 'daily' / 'weekly'`，**无星期信息** → 每周项仍每天列出、仍可打卡，但不计入完美日（不改数据模型） |
| 今日必做进度 | `今日成长 x/y` 只统计**每日项**，不是列表可见行数 |
| 专注未达标 | 不抛异常、不写记录、不写账本，返回「未达标」让界面提示「再专注一会儿」 |
| 累计制 | 「我的」页全部用累计指标（累计专注时长/次数/有效天数、累计成长打卡、累计开花植物），**不做「连续 N 天」** |

## 4. 「不做」的边界（明确写死，避免后来者越界）

| # | 不做 | 原因 / 出处 |
|---|---|---|
| 1 | **无账号、无联网、无云同步** | Plan B 单孩子单机版（口径裁定表 C1）；`account_service` 留桩；家长端是本地 PIN 锁，不接云账号；埋点只落本地表，不接任何云 SDK |
| 2 | **不做「连续 N 天」断档清零式设计** | PRD 明确反对——「连续断了就归零的设计本身就是挫败源」。一律**累计制**：累计专注、累计打卡、累计开花 |
| 3 | **没有植物产阳光** | 能力接口骨架已就位（§2.9），但**未接入任何具体玩法**，界面上不会出现 |
| 4 | **没有草地花园式布局** | 玄参有此设想，但**尚未拍板**。此处只记「**未实现**」，不展开任何方案 |
| 5 | 孩子端「自主核销」默认关 | 设置页有「自主模式（孩子自助核销）」开关，默认不开启；孩子端发起兑换一律走家长核销 |
| 6 | 不做「导出成册」文件 | 删除入口按「先导后清」只在删除页提示导出，导出 UI 未做 |
