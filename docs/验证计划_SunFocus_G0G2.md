## 1. G0 合规重定性（Plan B 版）

### 1.1 判断题结论（明确）

**结论：Plan B 下，主张适用《儿童个人信息网络保护规定》第 28 条豁免的「精神」，并将合规义务从「网络运营者全量儿童保护义务」降级为「本地最小必要 + 透明告知 + 删除权」简化集；但不得主张「我完全不是处理者、零义务」。**

理由（逐条）：

1. **豁免成立的形式前提已满足。** 《儿童规定》第 28 条：「通过计算机信息系统自动留存处理信息且**无法识别**所留存处理的信息属于儿童个人信息的，依照其他有关规定执行。」Plan B 无账号/无家庭组/无云同步 → 运营者（开发者）在**任何网络侧都无法获取、无法将本机数据与特定儿童关联**——满足「无法识别属于儿童个人信息」的适用前提，故《儿童规定》的专门儿童保护条款（专条、专员、可验证监护人身份、加密传输、泄露通知等）不再按原强度适用。
2. **但《个保法》第 28/31 条字面不以「联网」为限。** 第 28 条将不满 14 周岁未成年人个人信息列为敏感个人信息；第 31 条要求处理此类信息须监护人同意 + 专门处理规则。本地仍存「昵称 + 年龄档 + 专注记录」，从设备层面可识别为儿童个人信息。因此**「完全免除儿童个人信息处理者身份」在《个保法》字面下站不住**。
3. **最稳姿态（建议玄参采纳）**：把网络侧重义务降为零，把本地基础义务做足，对外如实表述（不写绝对话）。这比 PRD §10.1 原「建了孩子档案就是处理者、豁免不再适用」的口径**更适配 Plan B**——因为 Plan B 已砍掉「账号/家庭组」这个网络侧触发器，原口径是为「联网账号形态」写的，直接套用于 Plan B 会过度合规、徒增成本。

> ⚠️ **诚实提示**：这是单人开发者的「务实降级」，不是法务背书。若玄参对风险敞口零容忍，应预留 PRD §8.1 所述 ¥2,000–5,000 法务咨询预算（见 §6 待拍板 1）。

### 1.2 法条依据（已核对原文）

| 法条 | 原文要点 | 对 Plan B 的含义 |
|---|---|---|
| 《儿童规定》第 28 条 | 自动留存处理且**无法识别属于儿童个人信息**的，依其他规定执行 | 豁免网络侧专门儿童义务的前提满足 |
| 《个保法》第 28 条 | 不满 14 周岁未成年人个人信息属敏感个人信息；须特定目的+充分必要+严格保护 | 本地处理仍属敏感信息，基础保护义务在 |
| 《个保法》第 31 条 | 处理不满 14 周岁信息须**监护人同意** + **专门处理规则** | 本地同意流 + 本地处理规则必须做 |
| 《个保法》第 19 条 | 保存期限为最短必要 | 本地最短必要 + 到期自清 |
| 《个保法》第 47 条 | 撤回同意/目的已实现须删除 | 本地删除权入口必须做 |
| 《儿童规定》第 8 条 | 指定专人负责 | 本人即专人，披露本人+渠道 |

## 2. G1 形态验证方案（设备可得性 + 横屏放置意愿）

> 依据 PRD §8.1 G1：T+2–4 周；核心假设＝家庭有可专用化闲置设备、孩子愿意横屏放置。

### 2.1 招募口径

| 维度 | 口径 |
|---|---|
| 目标人群 | 一线/新一线城市、6–12 岁孩子家庭、有**可闲置专用化的 Android 设备**（旧手机/旧平板） |
| 招募规模 | 10 户主样本 + 2 户候补（应对中途退出） |
| 渠道 | 玄参私域（家长群/朋友圈/本地妈妈群/小红书）；**零成本**，可附小礼品（见 §6 待拍板 2） |
| 筛选问卷（3 题） | ① 家中有无可闲置 Android 设备（型号/屏幕大小）；② 孩子年龄段（低 6–8 / 高 9–12）；③ 家长是否愿意给孩子专用化 7 天 |
| 设备约束 | 优先 Android（MVP 先 Android）；若测平板体验，单列记录（PRD §9.2 开放问题 1） |

### 2.2 测什么（判据复述，来自 §8.1 G1）

| 判据 | 阈值 |
|---|---|
| 设备可得性 | ≥ 60%（10 户中 ≥ 6 户有可用闲置设备并愿意专用化） |
| 横屏放置达成 | ≥ 7 户在 7 天内完成 **≥ 5 次横屏放置**（每次 = 横屏放置 ≥ 5 分钟有效专注，见 §6.2 最短结算时长） |

### 2.3 怎么测（7 天观察表模板）

**观察表字段（每户一张，D1–D7 每日填）：**

| 字段 | 取值 | 说明 |
|---|---|---|
| 户号 / 孩子年龄档 | 低/高 | — |
| 设备来源 | 闲置/主力 | G1 主路径＝闲置 |
| 设备可得性 | Y/N | 是否真给孩子专用化 |
| D1–D7 每日：横屏放置次数 | 整数 | 每次 ≥ 5 分钟计 1 次 |
| D1–D7 每日：单次最长分钟 | 分钟 | 常亮/耗电观察 |
| D1–D7 每日：是否主动拿起 | Y/N | 孩子主动性信号 |
| D1–D7 每日：家长干预次数 | 整数 | 维护成本信号 |
| 设备争抢事件数 | 整数 | 闲置设备被占用/争抢 |
| 常亮耗电反馈 | 轻/中/重 | P6 技术验证项 |
| 家长维护耗时（分钟/日） | 整数 | 零维护默认档前提 |
| 是否达成 ≥5 次 | Y/N | 判据 2 |

### 2.4 7 天关键信号（无埋点，靠观察表 + 简短回访）

| 信号 | 关注点 | 判读 |
|---|---|---|
| 横屏放置频率 | 孩子是否自然横放 | 核心假设验证 |
| 设备争抢 | 闲置设备是否被占用 | 决定 B 计划必要性 |
| 家长维护耗时 | 一次配置长期受益是否成立 | 零维护默认档承重墙 |
| 常亮耗电 | P6 待评估代价 | 决定降级（低亮定时/系统专注模式） |
| 主动 vs 被动 | 孩子主动 vs 家长催促 | 习惯养成前置信号 |

### 2.5 量化「愿意横屏放置」

- **一次有效横屏放置**＝横屏放置且产生 ≥ 5 分钟有效专注（对齐 §6.2：「自然结束同样要求实际专注 ≥ 5 分钟才计产出」）。
- 用「7 天内有效横屏放置次数」作为唯一量化指标，避免主观打分。
- 数据来源：观察表（主）+ 设备屏幕使用时间截图（辅，验证常亮耗电）。

### 2.6 判据与 B 计划

| 情形 | 动作 |
|---|---|
| 设备可得性 ≥60% 且 ≥7 户达成 ≥5 次 | **G1 过**，进入 M1/M2 开发主线 |
| 判据 1 或 2 不过（首次） | 触发 **B 计划**：转「主力机 + 引导式单应用锁定」重测 |
| B 计划落地 | Android **屏幕固定（Screen Pinning）/ 引导式访问**把应用锁为唯一前台，消解设备争抢；同口径重测 7 天 |
| B 计划二次不过 | **停**（PRD §8.1：「二次不过则停」），回主理人重估形态假设 |

| 观察指标（不设门槛） | 玩具档首次核销时点、默认定价保持率、小零食消耗占比、低年级超限放行率 | — |
| 额度调整后复测窗口 | **4 周**（高频事件，10 周浪费） | — |

**WFD 定义（§8.3 写死）：** 一周内「当日完成 ≥1 次有效专注（**≥15 分钟且完成率 ≥90%**）」的天数，健康值 **≥4 天/周**。

**留存口径（§8.3 + G3）：** D1 45% → D7 30% → D30 18%（衰减 0.67/0.6）；D90 ≥10%；平坦度 D30:D7 ≥0.6。

**免确认双条件（§4.8 E6）：** 须同时满足 ① 单笔 ≤ 高 130 / 低 50；② 当月累计自动放行 ≤ 当月池 25%（高 400×25%=100 / 低 160×25%=40）。**自服务类一律 0**（不自动放行）。

**周池（§4.8 E9，M2 落地为周度）：** 默认 400（高）/ 160（低、中）阳光/周，可调 **50–500**；超池改「排队中」，下月 1 日按申请先后自动放行。标死：池只吸收 17–26% 阳光产出。

### 3.4 数据看板最小字段

| 维度 | 最小字段 |
|---|---|
| 周维度（核心） | WFD 均值、达标家庭占比、家长周活跃率、队列事件/户/周（分龄） |
| 留存 | D1/D7/D30/D90 曲线、平坦度 |
| 经济 | 月度池吸收率、撞顶家庭占比（§8.3 护栏 ≤20%）、默认定价保持率、小零食消耗占比、低年级超限放行率 |
| 质量 | 低活跃户标记、队列充足性预警 |

## 5. 里程碑时间窗与验证窗口衔接建议

### 5.1 时间窗表（单人 20h/周 · 诚实估算）

| 里程碑 | 乐观工期 | 诚实工期（含缓冲） | 累计（诚实） | 重叠验证 |

| M3 花园/任务/家长端 | 3 周 | 4 周 | W16 | **G2 起跑（W12）** |
| M4 打磨与上架 | 2 周 | 3 周 | W19 | G2 跑数中 |
| **G0 合规** | T+0–2 | T+0–2 | — | 与 M0 并行 |
| **G1 形态** | T+1–4 | T+1–4 | — | 与 M1 并行（影子测试） |

> 诚实结论：单人 20h/周 + 集成/调试/迭代，主线开发约 **19 周**；G2 主门判读在 **T+22 周**；若 G2 二次不过改一次再跑 4 周，则 **T+26 起**。比双肩扛慢，属正常。

### 5.2 开发期与验证期并行不打架的逻辑

| 并行关系 | 为什么不打架 |
|---|---|
| G0（T+0–2）‖ M0 | G0 是文档/合规模板/文案，零代码依赖，与工程骨架并行 |
| G1（T+1–4）‖ M1 | G1 是**形态假设**验证，用可降级原型/手动观察/影子测试即可，**不等 M1 全完成**；M1 开发照常推进 |
| G2（M2 后起跑）‖ M3/M4 | G2 必须等 M2（商店核销上线）才有队列数据，故 G2 起跑点 = M2 完成（W12）；其 10 周验证期**覆盖 M3/M4 开发**，互不阻塞——M3/M4 按 DoD 推进，G2 同期回收数据 |
| 纪念册埋点（T+11）‖ G2 | §8.4 要求 T+11 周起埋原料，正好落在 G2 窗口内，一次埋点同时满足 G2 与 V2 纪念册 |

**关键原则**：轻量验证（G0/G1）前置并行、重验证（G2）等数据就绪再起跑，避免「为验证而阻塞开发」或「没数据硬判门」。
