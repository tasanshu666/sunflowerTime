## 一、玄参原话（需求记录）

> 我想到花园的后续玩法。我想给花园增加一些**天气系统**，比如说今天**阳光明媚**，然后花园花盆的进度**额外增加 1%**；今天遇到**大风大雨、气温骤降**，花盆的进度**减少 1%、2%** 之类的。那你可以按照这个想法去扩展一下，总结一下，可以先把这个想法记录下来，以待后续版本的开发。

## 二、主理人扩展构想（按原意发散，全部未拍板）

### 2.1 天气类型与效果草案（数值全为示例，立项时拍板）

| 天气 | 视觉基调 | 进度效果 | 附加效果（候选） |
|---|---|---|---|
| ☀️ 阳光明媚 | 亮色、光斑 | 全花园进度 **+1%** | 晨露 +1？（阳光产出，需经济核算） |
| ⛅ 多云 | 中性 | 无增减 | — |
| 🌧️ 大雨 | 冷色、雨丝 | 全花园进度 **−1%** | **自动浇水**（养护度浇水槽直接补满？见 §五.4） |
| ⛈️ 暴雨大风 | 深色、摇曳 | 全花园进度 **−2%** | 有概率生成**害虫**（虫子被风吹来/雨天滋生）；枯萎倒计时不加速（不直接威胁植株存活，见 §四.3） |
| ❄️ 骤冷（远期候选） | 雪粒 | −2% | 需「保暖」应对动作，复杂度高，建议首版不做 |
| 🌈 彩虹（稀有惊喜） | 彩带 | +2% | 低概率出现，配合开花惊喜系统发一次性小奖励 |

### 2.2 配套玩法候选（未拍板）

1. **每日天气角标**：花园页角落常驻今日天气图标；点击看一句童趣播报（「今天阳光很好，植物们都在加油长个！」）。
2. **次日预告**：播报卡带一句「明天可能有雨」——给孩子「今晚把养护做完」的轻决策动机（用未来的坏天气推动今天的养护，而不是直接惩罚）。
3. **保护动作（阳光 Sink，推荐）**：坏天气当天可花少量阳光「搭小棚 / 穿雨衣」，抵消当日进度损失——把负面天气变成**主动应对**而非被动挨罚，同时给阳光增加新消耗出口（符合经济系统需要更多 Sink 的大方向）。
4. **与空盆长草长虫咬合**（玄参 2026-10-26 提出的空盆构想）：雨天空盆更容易长草、虫子更活跃——两个系统共用一套「花园环境状态」，立项时合并设计。

## 三、与现有体系的咬合点（可行性预判）

| 玄参诉求 | 现有挂点 | 增量评估 |
|---|---|---|
| 进度 ±1%~2% | 植物生长按「经过小时数 ÷ 每阶段小时数」推进（`kPlantGrowthHoursPerStageDefault`） | **不能直接改时间流速**（会污染专注结算与枯萎倒计时），需给每株加「天气加成累积器」字段（如 `growth_bonus_ms`，可正可负）——🔴 涉及 schemaVersion 迁移 + 迁移测试铁律 |
| 全花园范围 | 花园页已有盆位列表与统一渲染 | 天气是**花园级**状态，建议单字段存当天天气 + 是否已用保护动作，不逐盆存 |
| 每天一变 | 晨露每日 08:00 结算已有「按日结算」先例 | 天气用**日期种子确定性生成**（见 §四.1），结算点与晨露对齐（每日 0 点或 8 点，待拍板） |
| 视觉 | 花园背景 / fx 序列帧管线现成 | 天气图标 + 背景色调微调即可起步；雨丝/雪粒动效可后置 |
| 惊喜联动 | 开花瞬间惊喜系统（保底 6☀ + 概率池） | 🌈 彩虹建议独立 roll，同变异花朵原则：不挤占现有惊喜概率池 |
| 杂草害虫 | 除草 +1☀ / 除虫 +2☀ 已有 | 天气调制生成概率即可（雨天 ×2 之类），机制零改动 |

## 四、关键设计取舍（主理人建议，供拍板）

1. **天气来源：本地伪随机，不接真实天气 API**。本项目是**纯本地单机**：真实 API 要联网 + 定位权限（儿童 App 隐私敏感，隐私政策要改），且断网时体验割裂。建议**按日期做确定性种子**——同一天全世界用户天气相同，孩子之间有话题（「今天下雨了你也下雨了吗」），零网络零权限。
2. **负面天气只减速、不杀伤**：坏天气绝不直接推进枯萎/不扣养护度存量——进度损失封顶 −2%，且**不得把植物推入枯萎**（只减「距下一阶段的剩余进度」，保底到 0 为止）。6-9 岁挫败感控制参照变异花朵保底讨论。
3. **保护动作优先于概率修正**：与其调「坏天气出现频率」，不如让孩子有应对手段（§2.2.3）——把惩罚转化为决策，教育价值更高。
4. **经济红线不动**：天气只影响**生长节奏**（时间维度），不直接发/扣阳光；凡涉及阳光产出的附加效果（雨天自动浇水、晴天晨露 +1）立项时必须过一遍 40 级升级曲线核算，防止变成「刷阳光后门」。
5. **专注主循环零渗透**：天气不影响专注时长结算 / 护眼奖励（同变异花朵 §三.4 红线）。

## 五、实现前必须先定的问题（开放问题）

1. **数据模型**：`plants` 加 `growth_bonus_ms`（迁移 + 迁移测试）？还是花园级单行表存「今日天气 + 各盆累积器」？倾向逐盆累积器进 `plants`（生长语义内聚），花园级天气另存 SP/单行。
2. **结算时刻**：天气在每日 0 点换（与自然日对齐）还是 8 点（与晨露对齐）？跨午夜在线的孩子怎么补结算（复用「上次结算基准 + 无条件推进」幂等模式）？
3. **数值模型**：±1% 是「当前阶段总时长」的 1% 还是「当日自然生长量」的 1%？建议后者（当日生长的小百分比，好解释好展示）；叠加规则（连续坏天气累加？封顶？）。
4. **雨天自动浇水与养护度咬合**：直接补满浇水槽会让「浇水」日常失去意义——建议改为「雨天浇水槽不衰减」或「雨天浇水动作阳光折扣」，保留主动性。
5. **预告与频率**：坏天气连击上限（如连续坏天气 ≤2 天后必出好天气）？预告是否必准（孩子会学会信任预告，建议必准）？
6. **美术与 i18n 清单**：天气图标 5-6 枚 + 背景色调 + 保护动作小动画（豆包批量）；文案 zh+en 并入创作类批。
7. **与变异花朵 / 空盆长草的批次合并**：三者同属花园生命力方向，共享「环境状态」概念，建议一次立项避免三次 DB 迁移。
