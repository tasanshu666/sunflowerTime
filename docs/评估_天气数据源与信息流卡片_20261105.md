## 1. 乙：给花园接真实天气 —— 可行，但现在不该做

### 1.1 它说对的部分（我已核实）

| 文档主张 | 核实结果 | 来源 |
|---|---|---|
| WeatherKit 随 Apple Developer Program 提供，每月 50 万次免费，可商用 | ✅ 准确 | Apple 官方 WeatherKit 页：「up to 500,000 API calls a month per Apple Developer Program membership」，超额后 100 万次/月 US$49.99 起 |
| Open-Meteo 免费层 1 万次/天、30 万次/月，**仅非商用** | ✅ 准确，且比文档说得更硬 | 官方 pricing 表：Free/Open-Access 一列 `Commercial use ❌`；商用授权最低 $29/月（1M 次） |
| 日活 1000 × 每天 3 次 ≈ 9 万次/月，离 50 万很远 | ✅ 算术正确（1000×3×30 = 90,000） | — |

### 1.2 🔴 它说错/漏掉的部分

**① 前提判错了我们的实现。** 文档开篇说「如果园子里的晴雨由代码随机决定，孩子玩上两周就会摸到规律」——**这句话不成立**。我们的天气是 `FNV-1a(日期字符串) / 2^32` 落权重桶（`weather_system.dart:356-365`），32 位哈希，人眼不可能反推；外面还套了两条软约束（同型不连三、同型极端不连二）。孩子摸不出规律。
**但它的结论仍然对**：孩子摸不出规律 ≠ 孩子觉得这雨跟自己有关。**真实感缺的是「关联」，不是「随机性」** —— 这个区分很重要，它决定了后面该修什么。

**② 漏了 WeatherKit 的强制署名。** 用 WeatherKit 必须在界面上挂 **Apple Weather 商标 + 法律链接**，且**不得**用于紧急/救生类宣传（Apple Developer Program License Agreement 附件 8）。我们的花园页右上是天气胶囊，加一个「Apple 天气」角标会挤掉现有 187pt 的宽度预算（A2 已算满）。

**③ 漏了「在中国，WeatherKit ≈ 和风」。** Apple 天气在中国大陆的数据源就是和风（QWeather）。文档把 WeatherKit 和和风当成两条并列的路，实际在国内是同一条——真正独立的只有 Open-Meteo（欧洲模型，国内地名/预警不贴）。

**④ 漏了系统版本。** 文档说「接入用 Swift 原生，一天能通」。我们的 `IPHONEOS_DEPLOYMENT_TARGET = 15.0`，而 **WeatherKit 的 Swift API 要求 iOS 16.0+**。要让 iOS 15 用户也能用，就得走 REST API，而 REST 要 **JWT 签名（Service ID + 私钥）** —— 单机 App 没有服务端，只能把私钥打进客户端，Apple 明确不建议。⇒ **要么抬最低版本到 16，要么维护两条数据通路。**

### 1.3 真正的障碍（按严重度排序，全是我实测的）

| # | 障碍 | 事实 | 严重度 |
|---|---|---|---|
| **1** | **数值系统是按「极端日 20%」设计的** | 权重 `20/14/18/14/14/7/5/5/3` ⇒ 极端日恰 20%。干旱 `growthFactor=0.20`（几乎停长）+ `waterFactor=3.00`（浇水救命）；暴雨 `waterQuota=0`（当天不能浇水）；棚 10 阳光。**真实天气是强季节性的**：唐山 7~8 月才多雨、12~2 月多晴冷、3~5 月多风、暴雨一年就几天 ⇒ 「极端日」会从均匀 20% 变成「某个月 60%、某个月 0%」 | 🔴 崩盘级 |
| **2** | **无网怎么办** | 全仓**零网络**：`pubspec.yaml` 无 `http`/`dio`；`Info.plist` 零 `UsageDescription`；零 ATS 配置。离线回退必须保留现在的哈希日历 ⇒ **两套天气并存**，网络失败那次会出现「花园显示昨天暴雨、实际今天晴」 | 🔴 |
| **3** | **上架姿态要改** | `pubspec.yaml` 明确写着「不申请任何系统敏感权限（含定位）→ 不触发 iOS 隐私串，无需新增 `UsageDescription`」，这是审核铁律。接真天气要么按城市（钉死坐标，可规避定位权限），要么开定位（儿童 App 的定位 = Kids 类目红线）。**且 2.1 正在审（构建 2105），任何 capability 变更都要重新出包重审** | 🔴 |
| **4** | **跨端断裂** | WeatherKit 只覆盖 iOS；Android 8.0+ 端要么走 WeatherKit REST（私钥问题），要么第三家 ⇒ 两个平台可能同一天不同天气，账号数据却共用 | 🟠 |
| **5** | **改造面** | `WeatherKind/WeatherDay/WeatherSystem` 被 **8 个 lib 文件**引用约 186 处（`weather_system` 82、`weather_status_bar` 49、`plant_growth_service` 31、`weather_growth_math` 10、其余零散）；**12 个天气测试文件**全建立在「按日期哈希」这个前提上 | 🟠 |
| **6** | **A6 刚补完的 36 条平板矩阵 + 6 行区间断言全部要重算** | 那些期望值都是从「9 型权重 + 哈希」推出来的 | 🟠 |

### 1.4 成本对比（同一个人干）

| 方案 | 工作量 | 风险 |
|---|---|---|
| 接真实天气（iOS WeatherKit + Android 第三家 + 缓存 + 回退 + 9 型映射 + 平衡重跑 + 测试） | **5~8 人日** | 一轮上架重审；玩法数值崩；跨端不一致 |

## 2. ✅ 我的建议：不接真天气，改「季节权重」

文档想解决的真问题是「花园的雨跟我家的雨没关系」。但**接真实网络数据不是唯一的解法，而且是最贵的那种**。

**做法**：把 `_weights`（`weather_system.dart:174`）从固定 9 个常量，改成**按月份查一张 12×9 的表**。唐山气候大致：7~8 月多雨（提高 lightRain/rainstorm）、3~5 月多风（提高 wind）、12~2 月干冷（提高 cold、降 rainstorm）、春秋少雨（提高 drought）。

**为什么这个方案值**：
- 孩子能感知到「夏天老下雨、冬天老刮风」——**这就是真实感**，而且比「今天唐山真的下雨了」更容易被感知（后者需要孩子真的看窗外）；
- 零网络、零权限、零 schema、零审核风险，**和现有全部测试同构**（改一张表，`_pickKind` 不动）；
- 不同月份玩法节奏自然变化，反而解决了「每天都一样」的问题——这其实是**养成游戏更想要的**：季节感。

**必须付的代价（不能藏）**：极端日占比会随月份波动，`20%` 这个数不再成立。项目里已有 6 行区间断言 + 36 条平板矩阵钉着各种期望值，**改之前必须先跑一遍统计**，确认每个月的极端日占比落在可接受区间（建议 12%~28%），否则道具经济（4 种棚、10 阳光/次）会失衡。

**这条要不要做，等你拍。它独立于 A3/A5-b，随时可插。**

## 3. 甲：信息流卡片这套做法 —— 不进产品，但值得偷 5 条

### 3.1 对 SunFocus 的产品 UI：**不建议**

- 单文件 HTML + 原生 JS，在 Flutter 里只能靠 **WebView** 承载；
- 儿童 App 用 WebView 做核心 UI：无障碍（TalkBack/VoiceOver）失配、我们现成的 ARB i18n 体系作废、字体/主题要重做一套、离线首屏与审核（远程可变内容）都要额外解释；
- 它的「三态布局」解决的是**信息流**问题（竖版卡 / 详情 / 宽屏），我们根本没有信息流。

### 3.2 值得偷的 5 条（只借思想，不引技术栈）

| # | 它的做法 | 对应我们的现状 | 值不值得 |
|---|---|---|---|
| 1 | **schema 先行 + 字段路径级报错 + 拒绝未知字段**，绝不静默截断 | 我们的「不许为变绿放宽断言」「不许静默兜底」是同一个信念 | ✅ 已在做，继续 |
| 2 | **内容与版式彻底解耦** | 我们的 `prd_params` 常量表 + ARB 文案 = 同构 | ⚠️ 已具备 |
| 3 | **`sourceNote` 主动交代「哪些是查的、哪些是推算的」** | 我们文档里没有这个习惯 | ✅ **值得学**，尤其验收报告 |
| 4 | **首屏内容烤进文件，宿主慢就是白屏** | A2 的「天气胶囊首帧即可见，不等 loading」是同一条道理 | ✅ 已在做 |
| 5 | **数字一律取整，不让浮点尾巴上屏** | 我们踩过（进度百分比） | ✅ 已收敛 |

### 3.3 唯一有实用价值的落点

这套格式适合**我给你的交付/验收报告**（现在都是 md）。做成 `.card.html` 单文件，你能在手机上看、能截图存档。**但优先级低于 A3/A5-b/F176，不建议现在做。**

## 4. 一句话结论

**接真天气：技术上可行，产品上现在不该做** —— 它会撞碎按 20% 极端日设计的数值系统，把我们「零网络零权限」的上架姿态改掉，成本 5~8 人日，而现在 2.1 还在审。
**想要真实感的便宜解法是「季节权重」**：0.5 人日、零风险，拿到八成效果。
**信息流卡片不进产品**，但「来源与口径说明」这条习惯值得搬进我们的验收报告。
