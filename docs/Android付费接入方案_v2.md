## 0. 结论先行

### 0.1 一句话

**Android 版就一个包：官网直供，买断，激活码解锁，100% 收入归你，不上任何应用商店。** 不是「先委屈做免费版」，是「商店这条路对买断制本来就不成立」。

### 0.2 为什么商店上不了 —— 不是资质问题，是模式问题

这是本次核查最重要的发现，直接推翻了「等我拿到资质就能上商店卖」的假设：

**买断制 App 在国内手机自带商店根本没有位置。** 商店的付费能力只有两种形态：

| 商店付费形态 | 适合的商业模式 | 买断制能否套用 |
|---|---|---|
| 应用内购买（IAP，非消耗型） | 免费下载 + 内购解锁 | 形式上可以，但**准入要求企业主体 + 商务白名单** |
| 应用联运 | 免费下载 + 内购分成（~50%） | 不能，联运的前提是有「内购点」 |
| 付费下载 | 下载即付费 | 形态最贴合买断，但**国内已基本不做**（见 §1.2） |

**行业实证（最硬的旁证）**：

- **《沙石镇时光》**（买断 29 元，正规商业产品）官方下载指引原文：「安卓没有上架华为、小米、OPPO、vivo 自带应用商店，**不要在手机自带应用市场盲目搜索，搜不到属于正常情况**」，实际走好游快爆 / 4399 游戏盒。
- **《风帆纪元》**（买断 29 元）：「小米、华为手机自带的应用商店没有收录」，实际走 TapTap + 官网。

两家正规发行商，同一个结论。**买断制进不去国产手机自带商店，是这个行业的常态，不是个体户特有的门槛。**

### 0.3 那还剩什么

| 路径 | 可行性 | 收入归属 | 结论 |
|---|---|---|---|
| **官网直供 + 激活码** | ✅ **100% 确定可行** | **100%** | ⭐ **唯一主线** |
| 应用宝（免费/付费选项） | ⚠️ 需实测 | 商店代收 30% | 待探，不排期 |
| 小米应用联运（个体户口头子） | ⚠️ 需商务邮件确认 | 商店代收（约 50%） | 发一封邮件问，不投入工程 |
| 荣耀（"无内购"选项下自管支付） | ⚠️ 口径矛盾，必须书面确认 | 不抽成或 30% | 发一封工单问，不投入工程 |
| 小米 IAP / OPPO / vivo / 华为 | 🔴 死路（企业主体 + 商务白名单 / 鸿蒙） | — | 放弃 |

## 1. 先把「买断制为什么进不了商店」讲透

### 1.1 商店的钱是怎么收的

国产商店的数字商品收入，几乎全部来自「联运」：App 免费下载，用户在 App 内买道具/会员，商店按 30%–50% 分成。这套体系的设计前提是**持续的复购**。

买断制是一次性交易，没有复购点。对商店来说：
- 走付费下载 → 需要单独的业务通道 + DRM，收入体量小、运维成本高，**国内各家陆续关停**；
- 走内购 → 要把「一次性买断」包装成一个非消耗型商品，技术上可以，但**准入被卡在企业资质和商务审批上**（见 §2）；
- 走联运 → 没有内购点，谈不起来。

结论：**不是商店不让个体户卖买断，是商店体系里没有「买断」这个货架。**

### 1.2 付费下载在国内的真实状态

| 商店 | 付费下载业务 | 现状 |
|---|---|---|
| 华为 | 有（"付费情况"选"付费"，强制华为支付） | 🔴 只覆盖 HarmonyOS 4.x 及以下存量机；HarmonyOS 5/6/7 移除 AOSP、不装 APK，且安卓侧买的付费 App 升级鸿蒙后不继承。**已按玄参决定排除** |
| 荣耀 | 创建应用时"付费情况"有「付费下载」选项 | ⚠️ 选项存在，但实际开通需走联运/商务，未见自助入口 |
| 小米 | 未见公开的付费下载业务 | 🔴 小米只有 IAP 与应用联运两条付费路 |
| OPPO / vivo | 联运为主 | 🔴 无独立付费下载 |
| 应用宝 | 有"付费应用下载"服务声明 | ⚠️ 入口在商务体系内，近年收缩，需实测 |
| Google Play | 有，且成熟 | ✅ 但国内用户访问受限，仅出海有意义 |

> **参考对照组**：买断制在国内活得好的，都是「垂直渠道 + 官网」，不是手机自带商店——TapTap（一次性买断、定价自主、国内零抽成）、好游快爆、4399 游戏盒。代价是这些渠道以游戏为主，工具类不好进。

## 2. 「注册通过」≠「付费能力开通」—— 小米这条必须分清

你小米注册过了，这是真的。但**能上架免费应用**和**能收钱**是两套权限，中间隔着两道门。

### 2.1 官方原文（本次核到的一手文档）

小米开发者平台《技术接入前准备(IAP)》（更新 2026-01-20）与 GetApps 国际版文档，同一句话：

> **"Developers who access the Xiaomi IAP service must be enterprise developers"**
> （接入小米 IAP 服务的开发者必须是企业开发者）

### 2.2 两道门

| 门 | 要求 | 个体户 |
|---|---|---|
| 门 1：主体资质 | 企业开发者 | 🔴 卡住 |
| 门 2：IAP 白名单 | 官方文档原文：「由于当前应用内支付(IAP SDK)接入流程处于**灰度阶段**，需要配置白名单后才可完成配置，**请联系商务配置 IAP 白名单**」 | 🔴 非自助，需商务审批 |

另外，小米的 IAP 接入入口是「管理控制台 → 应用和游戏 → **创建游戏**」（即使是非游戏应用也从这里进，合作类型选「其它」）。这套路径本质是联运体系，不是开放的自助支付。

### 2.3 唯一可能的口子：应用联运

小米《应用联运接入流程》里，资质要求写的是：

> 「联运应用必须有**软著及 ICP 证或 ICP 备案截图**，且 ICP 证或 ICP 备案截图不能授权。」

**这里没有写「必须企业主体」。** 联运需要的其他条件是：线上签合同、寄盖章纸质对账单、开发票——个体户这些都能做（有公章、有对公账户、能开普票）。

但要注意两个现实：
- 联运是「内容购买(IAP)合作模式」，分成约 50%，且**需要 App 内有内购点**——买断制套进去要把它包装成「一个非消耗型商品」，商务认不认是未知数；
- 申请要发邮件到 `wangsiqi5@xiaomi.com`，标题格式 `【应用联运合作申请】【应用类型】【应用名称】【公司主体名称】`，官方注明「不提供资质，一律不回复」。

> **建议**：发一封邮件问两个问题——① 个体工商户主体能否申请应用联运；② 纯买断制（无内购点，单一非消耗型商品）能否走联运。**只发邮件，不投入工程。** 拿到书面「可以」再谈。

### 2.4 荣耀的口径值得单独试一次

荣耀官方开发者社区 QA 里有一条关键回答：

> 「上架应用的时候，有个应用内资费的选项……**付费情况选择无内购即可；应用内资费选择其他，后续并不会影响应用内用户付费动作**，第二个内购选项实际指的**应用联运**。」

意思是：荣耀建应用时选「无内购」，**商店不介入 App 内的支付动作**，且不参与分成。这在五大门店里是唯一一条明确表态"非联运应用可自管支付"的官方口径。

但存在矛盾：另有官方文档写「开发者在荣耀平台分发付费内容（付费应用/主题、应用内付费），则必须开通荣耀商户服务」，以及行业指南称荣耀「仅企业主体」。

**处置**：提一张工单问三件事——① 个体工商户能否注册荣耀开发者并通过审核；② 选「无内购」的应用，App 内接微信支付是否合规；③ 若违规，处罚依据是哪条。拿工单编号和书面答复存档。

> 附：荣耀分成表里有明确档位——**教育类应用内购买 20%:80%（荣耀:开发者）**，工具类 30%:70%。若将来走荣耀，类目选择会直接影响 10 个点。

## 3. 推荐方案：单包直供，不做免费版

### 3.1 方案本体

| | 设计 |
|---|---|
| 分发 | 只有 `sunfocused.cn` 官网，一个 APK |
| 付费 | 微信 Native 扫码，买断价一次性 |
| 解锁 | 「输入激活码」，Ed25519 离线验签，写入既有 `Entitlement` |
| 支付代码 | 无任何商店 SDK，无网络支付依赖 |
| 商店 | **不上**（除非 §2.3 / §2.4 拿到书面肯定答复） |
| 收入 | **100% 归你**，只付微信 0.6% 通道费 |

### 3.2 与 v1 双包方案的对比

| | v1（双包：商店免费版 + 直供包） | **v2（单包直供）** |
|---|---|---|
| 包数量 | 2 个，需维护两套构建 | **1 个** |
| 工程改造 | 9 项，含通道分流、守卫测试、双份隐私政策 | **5 项**（见 §4） |
| 合规风险 | 中（要防商店查出站外痕迹） | **接近零**（不经审核） |
| 教育移动应用备案 | 上架商店时可能被要求 | **不需要**（该备案是商店上架核验的前置） |
| 收入 | 直供 100%，商店 0 | **100%** |
| 获客 | 商店自然流量 + 官网 | **只有官网**（唯一代价） |

### 3.3 这个方案的真实代价，必须说清

**没有商店自然流量。** 买断制靠官网卖，获客完全靠自己——这是本方案唯一但很重的代价。

三个可用的低成本获客方向（供参考，不展开）：
1. **小红书店 / 抖音「家长专注力」内容**：亲子向产品，内容带货比商店搜索有效；
2. **同类家长社群**（小学家长群、ADHD 家长社区）口碑；
3. **iOS 版已有用户导流**：App Store 已有 1.0.0 在售，iOS 用户里愿意推荐给安卓亲友的，是最精准的第一批。

### 3.4 免费增值结构（已拍板：不做试用，保持现状）

**玄参 2026-11-24 拍板：不加限时试用。** 理由：现有产品结构本身就是「免费可正常使用基础功能 + 买断解锁全功能」，用户先体验、自行判断是否购买。

🔴 这里要把两个概念彻底分开，此前一直混着说：

| | 判断 |
|---|---|
| ❌ 「为商店流量专门做的阉割免费版」 | 玄参反对，本方案也不做 |

## 4. 工程改造清单

现有架构改动量不大：`lib/platform/iap_service.dart` 的 `IapAdapter` 是天然适配缝，域层 `IapClient` 契约不用动，`EntitlementTier` 的 free/premium 二值正好覆盖买断语义。

**建议分两步走，不要一次做完** —— 先用最小闭环验证付费意愿，再投支付 SDK 的工。

### 4.1 第一步：激活码闭环 —— ✅ **已完成（2026-11-24，分支 `feature/android-payment`，未提交）**

实际落地与原计划的**关键偏离**，先讲清楚：

| 原计划 | 实际做法 | 为什么改 |
|---|---|---|
| 新增 `RedeemCodeAdapter implements IapAdapter` | 新增独立能力接口 `RedeemCodeActivator`，由 `MatrixEntitlementService` 额外实现 | ① `IapAdapter.startLifetimePurchase()` 语义是「发起购买并等消息流」，**无法弹出输入框**；② 给 `EntitlementService` 抽象加方法会打挂 29 个测试 Fake。故采用项目既有的**能力扩展模式**（照抄 `DebugEntitlementOverride`），调用方用 `is` 探测 |
| 付费页「主按钮立即解锁 + 次级入口已有激活码」 | Android 侧**主按钮直接变为激活入口** | Android 官网版没有 Play Billing 商品，原主按钮必然落到「暂不可购买」禁用态；两个按钮会让家长不知道点哪个 |

🔴 **发布闸门（发版前必须完成，否则包是废的）**
`redeem_public_key.dart` 的公钥仍是空串 ⇒ **当前打出的 APK 任何激活码都返回 `notConfigured`，用户付钱也解不开**。发版前必须：生成生产密钥对 → 填入公钥 → 重新构建。
⚠️ **公钥随 APK 发布即不可更换**（换公钥 = 已发出的老码全部作废）。发版 checklist 必须加一条「公钥已确认为最终生产公钥」。

🔴 **一个必须记住的坑：`-` 是 Base64URL 的数据字符（值 62），不是分隔符**
设计初稿让「分组用 `-`、粘贴时剥 `-`」，这会让**约七成半合法码**（实测 72%，理论 76.4%）解码不完整而判格式错误——**已付费用户永远激活不了，且极难排查**。现口径：分组显示用**空格**；`normalizeRedeemCode` 只剥空白、保留 `-`；另用 `redeemCodeCandidates()` 提供「再剥一次 `-`」的备选形态兜底手打连字符，**两个候选都必须过 Ed25519，安全性不变**（QA 已用逐位篡改 368 次 + `-`→`A/_/0` 全替换验证无放水）。
🟡 已知边界：码**本身含 `-`** 且用户又**手打 `-`** 当分组符 → 双候选均失效。概率低（展示已改空格），客服话术里备一句「请直接复制粘贴，不要手动加符号」。

**工作量实绩**：App 侧约 **1 人日**（工程师 37 分钟 + QA 复验），比原估 2 人日少——因为验签是纯 Dart、无服务端依赖。

### 4.2 第二步：支付宝 App 内支付（验证有量之后）

| # | 改动 | 说明 |
|---|---|---|
| 7 | 客户端接支付宝 SDK | 唤起收银台、处理支付回调；**绝不让私钥进包**，客户端只拿 `orderStr` |
| 8 | 服务端统一下单 + 异步回调验签 | 订单落库、幂等、防重复发码 |
| 9 | 发码与订单绑定 + 对账页 | 「已付款未发码」必须能一键补发（这是客服工单第一大来源） |
| 10 | 状态机测试 | 待支付 / 已支付 / 发码中 / 已解锁 / 超时关单 / 重复回调 |

**工作量**：客户端 **2 人日**，服务端 **3 人日**，测试 **1 人日**，合计约 **6 人日**。

> 🔴 关键取舍：第一步的「人工发码」看起来土，但它能让你在投入 6 人日之前先知道**到底有没有人愿意花 ¥29.90 买**。前 50 单转化率不行，第二步的工就省了。

## 5. 激活码技术方案

### 5.1 设计原则

- **离线可用**：不依赖网络，家长断网也能激活（与「离线优先」红线一致）。
- **私钥绝不进 App**：签发在服务端，App 只内置公钥。
- **可撤销**：出问题能停发；已发出的码无法远程作废（离线代价，接受）。
- **盗版接受度**：买断 + 单机离线必然可被共享/破解，行业默认接受。缓解靠已有 R8 + Dart 混淆、验签逻辑分散、公钥不明文。

### 5.2 码格式

**实际实现（2026-11-24 落地版，覆盖此前的 Base32 短码设想）**

激活码 = **69 字节二进制 → Base64URL（无 padding）→ 92 字符**：

```
偏移   长度   内容
[0]     1     version = 0x01
[1..4]  4     serial  = uint32 大端序（签发序号，对账/防重）
[5..68] 64    Ed25519 签名（对 [0..4] 这 5 字节签名）
```

**为什么不用原先设想的「Base32 Crockford 短码 + JSON 载荷」**

短码必须靠**在线校验**才可能短——离线验签的签名长度由算法固定（Ed25519 = 64 字节），压不下去。而第一步的目标是**零服务端依赖先跑通**，所以接受长码：

| | 短码（20 字符） | 本方案长码（92 字符） |
|---|---|---|
| 需要服务端 | ✅ 必须 | ❌ 不需要 |
| 手抄 | 可行 | 不现实 |
| 复制粘贴 | 可行 | 可行（同机购买场景占绝大多数） |

现实链路是「App 内点解锁 → 跳浏览器付款 → 回 App 粘贴」，**同机复制粘贴无障碍**。跨设备（电脑买、手机激活）靠微信转发文本。

**分组显示用空格，不用连字符** —— 见下方红线。

🔴 **`-` 是 Base64URL 的数据字符（值 62），绝不可当分隔符**
Base64URL 字母表是 `A-Z a-z 0-9 - _`。92 个字符里「至少含一个 `-`」的概率 **76.4%**（实测 200 枚命中 144 枚 = 72.0%）。若把 `-` 当分组符剥掉，**约七成半的合法码会解码不完整 → 判格式错误 → 已付费用户永远激活不了**，且极难排查。
现口径：
- `formatRedeemCodeForDisplay()` 用**空格**分组（空格一定不是数据字符）；
- `normalizeRedeemCode()` **只剥空白，保留 `-`**；
- `redeemCodeCandidates()` 另给一个「再剥一次 `-`」的备选形态，兜底用户手打连字符；**两个候选都必须通过 Ed25519 验签**，安全性不变。

**签名覆盖范围**：只签 `version + serial` 这 5 字节。故改动 version 或 serial 任一字节都会让签名失配——**攻击者无法把 1 号码改成 999 号码**。

**失败安全**：`RedeemCodeVerifier.verify()` **绝不抛异常**。格式错、编码错、签名错、算法内部任何意外，一律收敛为 `RedeemCodeInvalid`（附原因枚举）。一个错码绝不可能让 App 崩溃。

公钥内置 App（`lib/core/constants/redeem_public_key.dart`），私钥只在签发端（第一步是本机 CLI，第二步可迁到云服务器）。

### 5.3 设备与换机

- **第一阶段不做设备绑定**（离线无法强约束，做了只是心理安慰）。
- 文案承诺「同一激活码家庭 3 台设备可用」——靠信任，符合亲子场景（爸爸手机、妈妈手机、平板）。
- **换机**：用户需自存激活码；购买时自动邮件发一份（所以购买页必须收邮箱）。
- 第二阶段（可选）：极简服务端记录「码 → 激活次数」，支持自助解绑。

### 5.4 发货链路

```
用户 → 官网购买页（微信 Native 扫码）
     → 微信支付回调（云服务器，验签）
     → 签发激活码（Ed25519）→ 落库 + 页面展示 + 邮件发送
     → 用户在 App 输入 → 本地验签 → 写 Entitlement → 立即生效
```

- 🔴 **微信 APP 支付是死路（不是"大概率"）**。腾讯客服 FAQ 原文：「**从 2022 年 8 月 8 日起，APP 需在主流应用市场上架后，才能申请 APP 支付**」；申请材料要求「APP 上架到应用市场的截图」和「APP 下载链接：**APP 必须已经上架到应用市场**」。官网分发的 APK 永远满足不了。
- 🟢 **但支付宝 APP 支付不同，它给未上架应用留了口子**——详见 §5.5。这是个体户唯一能真正把支付做进 App 的通道。
- 手机端体验（微信侧）：购买页放二维码，微信内长按识别；非微信浏览器引导「保存图片 → 扫一扫」（§5.5 会说明为什么微信只能这样）。
- 兜底：支付成功未收到码 → 后台按订单号补发，页面提供「重新获取」。

### 5.5 收款通道：个体户能开哪些、怎么放进 App

#### A. 先破一个误区：收款码不能放进 App

「把收款码图片放进 App」是**技术上最简单、合规上最危险**的做法，三个原因：

| 问题 | 说明 |
|---|---|
| **个人收款码禁用于经营收款** | 央行《关于加强支付受理终端及相关业务管理的通知》（2022-03-01 施行）：个人静态收款码原则上禁止用于**远程非面对面**收款；有明显经营特征的须转为商户码 |
| **商家收款码是线下场景产品** | 微信「收款商业版」、支付宝「当面付」，设计场景是面对面。用于线上虚拟商品收款属挪用经营场景，**风控冻结概率极高**（虚拟商品 + 远程 + 固定金额重复，是反洗钱模型的典型特征） |
| **业务上根本跑不通** | 静态码没有回调，无法自动发激活码、无法对账、无法退款、无法开票 |

⇒ **正确做法是接「支付产品」，不是贴「收款码」。**

#### B. 个体户实际能开哪些（官方准入已核实）

**微信支付** —— 主体准入 OK（官方：「微信支付商家仅面向企业、**个体工商户**、政府及事业单位……」）。但产品按经营场景授权，差异极大：

| 微信产品 | 场景 | 个体户能否开通 | 对本品可用性 |
|---|---|---|---|
| **Native 支付** | 互联网网站（PC） | ✅ 可以 | ✅ 可用（生成二维码） |
| **JSAPI 支付** | 互联网网站 / 公众号内 | ✅ 可以（公众号需已认证服务号） | ✅ 可用，微信内体验最好 |
| **H5 支付** | 手机浏览器 | 🔴 **「个体工商户、小微商户暂不支持申请」** | ❌ 开不了 |
| **APP 支付** | App 内 | 🔴 必须已上架主流应用市场 | ❌ 死路 |

> 开户时经营场景选「互联网网站」，系统默认授权 **JSAPI + Native** 两个权限——不需要单独申请 H5。

**支付宝** —— 个体户准入全面开放，且**APP 支付接受未上架应用**：

| 支付宝产品 | 个体户 | 关键条件 |
|---|---|---|
| **APP 支付** | ✅ **可以**（官方原文：「企业或个体工商户可申请，纯个人不能申请」） | **未上架也可签约**：提供应用名称 + 官网下载链接，或 Demo/产品说明文档（含产品说明、资费说明、3–5 张购买流程截图）。需含明确经营内容与价格，且与营业执照经营范围一致 |
| 手机网站支付（WAP） | ✅ 可以 | 网站已 ICP 备案，**且备案主体须与支付宝账号主体一致——个体户不接受备案授权** |
| 电脑网站支付 | ✅ 可以 | 同上 |

> ⚠️ **支付宝两个必须注意的点**：
> ① 材料不齐会**限额**：单笔 ≤ ¥2000、单日 ≤ ¥20000。¥29.90 单价远低于单笔限额，但**单日 2 万约等于 200 单上限**，销量起来必须提额。
> ② 新签约未满 90 日或连续交易未满 30 日的，资金**次日结算**（不是实时到账），现金流要按 T+1 规划。

#### C. 推荐组合

| 端 | 通道 | 理由 |
|---|---|---|
| **App 内点「买断」** | **支付宝 APP 支付**（原生 SDK，直接唤起支付宝） | 唯一能在 App 内直接完成支付的通道，体验最好，转化最高 |
| 微信内打开官网 | 微信 JSAPI 支付 | 微信内原生体验，需已认证服务号 |
| PC 打开官网 | 微信 Native 扫码 + 支付宝电脑网站支付 | 双通道兜底 |
| 手机浏览器打开官网 | **支付宝手机网站支付为主**；微信侧给「保存二维码 → 扫一扫」 | 微信 H5 支付个体户开不了，这是硬限制 |

**一句话结论：以支付宝为主通道（它是唯一能进 App 的），微信做补充（官网/PC 场景）。** 这比 v2 初稿「以微信 Native 为主」更符合个体户的实际准入。

#### D. 三种技术形态：怎么「放进 App」

| 形态 | 做法 | 合规 | 体验 | 结论 |
|---|---|---|---|---|
| **① 贴收款码图片** | App 内显示二维码图片 | 🔴 违规（见 A） | 差（要手动发码） | ❌ 不做 |
| **② 跳浏览器到官网页** | `url_launcher` 打开 `sunfocused.cn/buy` | ✅ 完全合规（App 内无支付 SDK） | 中（跳出 App，回流靠输码） | ✅ 保底方案 |
| **③ App 内集成支付宝 SDK** | 接 APP 支付，唤起支付宝 | ✅ 合规（已签约产品） | **最好**（不跳出，付完回来即解锁） | ⭐ **推荐** |

形态 ③ 的完整链路：

```
App 内点「立即解锁 ¥29.90」
  → 客户端向自有服务端下单（订单号 + 金额 + 商品 ID）
  → 服务端调支付宝统一下单，返回 orderStr
  → 客户端调支付宝 SDK 唤起收银台
  → 用户付款 → 支付宝异步回调服务端（验签）
  → 服务端签发激活码 → 同一订单号关联
  → 客户端支付回调成功 → 向服务端拉取激活码 → 本地验签 → 写 Entitlement → 立即解锁
```

> 🔴 **红线**：私钥（支付宝应用私钥 / 激活码签发私钥）**只能在服务端**，绝不进 APK。客户端只拿 orderStr 和最终激活码。

> 🔴 **② 与 ③ 不是二选一，③ 是叠加在 ② 之上，不是取代它。**
> 做了 ③ 之后，激活码仍需保留，降级为兜底通道，三个场景离不开它：
> 1. **换机 / 重装**（无账号体系时，码是最可靠的凭证）；
> 2. **支付回调丢失**（客服按订单号人工补发）；
> 3. **PC / 他人代买**（家长在电脑上买，孩子手机输码）。
>
> 另一个易混淆点：区别的轴心不是「用哪个支付工具」——**② 的网页里支付宝和微信都能付**；③ 因为是 App 内 SDK，受微信 APP 支付「必须已上架应用市场」限制，**实际只有支付宝可走**。
>
> 两者的准入成本也不同：**② 只需支付宝手机网站支付/Native 权限**（门槛低、审核快）；**③ 必须签下支付宝 APP 支付**（未上架可签，但要留意 30 天提额要求，见 §5.5-B）。

| 平台 | 材料 | 备注 |
|---|---|---|
| 微信支付商户号 | ① 营业执照彩色扫描件/照片 ② **对公账户或法人对私账户**（含开户行省市、账号）③ 法人身份证彩色件 | 无申请费；费率 0.6%–1%；审核 1–2 工作日 |

### 6.1 软著：官网直供到底要不要（玄参问）

**结论：不要。官网直供不等软著，可以先跑。但软著仍须补办，理由不在「准入」而在「举证」和「将来」。**

先纠正一个常被混淆的前提：**软著是「确权」，不是「许可」。** 《计算机软件保护条例》规定，软件自开发完成之日起自动享有著作权，**登记是自愿的，不是强制的前置条件**。所以「没有软著就不能卖自己写的软件」这句话在法律上不成立。

逐个环节核：

| 环节 | 是否要软著 | 依据 |
|---|---|---|
| 工信部 APP 备案 | ❌ **不要** | 工信部通知解读：APP 备案「沿用了原有网站备案信息……仅需补充 APP 有关信息」。实际填报的是包名、公钥、MD5、图标、域名、主体证件 |
| 网站 ICP 备案 | ❌ 不要 | 备案材料清单无此项 |

> 🔴 **此处修正本文件早前的一处错误**：v2 初稿与 v1 均写过「国内安卓商店基本强制软著」。华为官方文档明确写的是**非必选**，该说法不准确。真实情况是：华为非必选，其余几家实操中按硬门槛执行——各家口径并不统一，不能一概而论。

**那为什么还是要办？三个真实用途：**

1. **微信支付类目卡点**——「软件销售」类目若被要求补材料，软著是最直接的一份。这是唯一可能立刻卡住收款的环节，所以它从「商店资质」变成了「收款资质」。
2. **防盗版举证**——买断制 + 单机离线，被山寨几乎是必然。真要投诉下架仿品，权属证明是第一步，没有它只能被动挨打。
3. **将来上任何商店都要**——早晚要办，现在办省二次准备。

**成本参考**：官费已免，代理约几百至一千余元，周期 1–2 个月（可加急）。**不阻塞官网直供主线**，可与买断开发并行。

**操作建议**：先把微信支付商户号申请提交上去，看类目审核要不要软著——要就立刻补办，不要就不影响收款。不要为了等软著把主线停 1–2 个月。

## 8. 定价与收益测算

### 8.1 定价：¥29.90（玄参 2026-11-24 18:20 拍板）

> 🔴 **已被 2026-11-26 新决策覆盖**：现行价 **¥49.90**（美国区 $6.99）。本节以下为 11-24 当时的完整论证，保留作决策留痕，不代表现行口径。

**当时的结论：¥29.90。** 玄参原话：「一杯奶茶钱，冲动消费还是可以的」。

此前 28 / 68 / 98 三档分析作废（结论曾被建议为 68），本条为终局口径。

**合法性先确认**——¥29.90 是中国区合法价格点，不必退到 ¥28 或 ¥30。Apple 官方档位表（developer.apple.com/cn/in-app-purchase）：

- 中国区价格步长 `CN¥1` 覆盖 **1–200**
- 支持惯例 `X9.90`，范围 **9.90–99.90**

⇒ **¥29.90 合法可用。**

**但有一个数学临界点必须盯住（这是数，不是意见）**

每个下载的期望收益 = 单价 × 转化率：

| 单价 | 转化率 | 单下载期望 |
|---|---|---|
| ¥68 | 3.0% | ¥2.04 |
| ¥29.90 | 3.0% | ¥0.90 |
| ¥29.90 | **6.8%** | ¥2.03（与 68/3% 打平） |

⇒ **¥29.90 的转化率必须比 ¥68 高出约 127%，收入才持平。** 这不是否定低价——冲动区定价确实可能带来这个量级的提升，亲子产品尤其如此（家长为孩子花钱的决策门槛低）。但这是上线后唯一要盯的核心数：**每 1000 次付费页曝光，成交多少单**。

**三个缓解动作（不动价格，只改做法）**

1. **用真实的原价做锚点。** 你的 IAP 现在卖 $14.99，中国区自动档位约 ¥108。若属实，「¥108 → ¥29.90」是**真实降价 72%**，可作为合法卖点（《明码标价和禁止价格欺诈规定》要求原价须真实成交过，此情形满足）。⚠️ 上架前先去 ASC 后台核对当前中国区实际价，别用错数字。
2. **不做虚假划线。** App 内付费页写「首发价 ¥29.90」可以；写「原价 ¥68，现价 ¥29.90」不行——¥68 从未成交过，属虚构原价。
3. **把涨价路径写成「承诺」而非「暗示」**：文案写「首发特惠，后续将调整至 ¥49」。给自己留了动作，用户也有预期。

🔴 **一句话记住**：¥29.90 不是「便宜卖」，是**用价格换样本**。第一批 100 单的目的不是赚钱，是拿到真实转化率数据；数据在手再决定涨不涨。

### 8.2 iOS 怎么改：入口不是「App 价格」，是「App 内购买项目」

🔴 **先纠正一处：改 App 价格是无效的。**

你的商品是**非消耗型内购**（`com.sunflowertime.app.premium.lifetime`，`lib/core/constants/iap_product_ids.dart` 注释明确「一次性永久买断、非消耗型」），**App 本身免费下载**。用户付的钱进的是内购，不是 App 售价。

| ❌ 走错 | ✅ 正确 |
|---|---|
| 价格与销售范围 → 改 App 价格 | **App 内购买项目 → 选 `premium.lifetime` → 价格 → 编辑价格点** |

**具体填什么**

| 项 | 填什么 | 说明 |
|---|---|---|
| 基准地区 | 美国（保持不变） | 改基准会删除已排定的价格变更，没必要冒风险 |
| 美国价格点 | **$3.99** | Apple 自动映射：$2.99→¥22、$3.99→¥28、$4.99→¥38（2026-10 实测）。$3.99 名义值最接近 ¥29.9 |

**区域差异化已排除**：玄参 11-24 18:27 确认「海外还没有支付用户」⇒ **全球统一降到 $3.99**，不做「中国特价、海外维持 $14.99」的分区方案。理由是海外零基数，分区只会制造跨区比价问题而无收益可保。

> 🔴 **11-26 更新**：美国价格点改 **$6.99**，中国区手动覆盖 **¥49.90**。上表与本节金额为 11-24 口径，保留留痕。⚠️ 若改美元基准价，苹果会重新生成中国区等效价（约 ¥48），**记得手动覆盖回 ¥49.90**，否则会自动跳到 ¥58。

**两端必须同价**：官网也定 ¥29.90。跨端比价最伤信任——你在官网明码标价，iOS 用户一搜就看到。

> ⚠️ 本节全部数字按 11-24 的 ¥29.90 计算，**仅供历史参考**；现行价 ¥49.90 需按新单价重算。

⚠️ 降价带来的副作用要说清：**客单价从 68 降到 29.9，「官网省分成」的绝对金额同步缩水约 2.5 倍**（68 元时是每单多 ¥20，现在只剩 ¥6–10）。比例优势不变，绝对数额变小。1000 单从「多 ¥2 万」变成「多 ¥6,000–10,000」。
