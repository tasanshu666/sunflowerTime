### 1.2 目标（3 个，正交）

- **G1 给「专注」一个当天的兑现口**：专注 → 能量 → 免费赶走小偷。**专注越多，越不用花钱**。这是本玩法唯一的教育闭环。
- **G2 让花园有「被惦记」的故事**：花草会被偷 → 有人守着 → 孩子愿意每天回花园看一眼。
- **G3 零新增货币**：掉落全是「折扣券」，当天过期，不进任何长期池。**不碰碎片、不碰种子、不新增货币**。

### 1.3 User Stories

- 作为**孩子**，我早上打开 App 就看到「偷菜贼来了」，点一下，阿葵 10 秒把它打跑，我拿到 2 个阳光和一张浇水券 —— 因为我昨天专注过，所以**没花钱**。
- 作为**孩子**，我今天没专注，胶囊写「要 5 ☀」。我点了「今天不赶了」也没关系 —— 阿葵顶班，我明天再努力。
- 作为**孩子**，我在花园左上角看到「💧 浇水 -1」，知道这是我今早打小偷赢的，一键浇 5 盆只花 20 而不是 25。
- 作为**家长**，我看到这个玩法**每天只要点一次、10 秒、能跳过**，而且奖励跟孩子看多久屏幕**完全无关**。
- 作为**家长**，我不担心它变相给孩子塞钱：掉落全是「今天便宜一点」，明天就作废。

## 2. 一条完整的时间线（**全部在同一天内**）

```
00:00  ① 小偷生成（确定性哈希 seed = dayKey + childId + kGuardDaySaltV2）
       └ 同时把「昨日未处理」的损失结算掉（只算 1 天，不叠加）→ 见 §3.6
  │
07:30  ② 孩子打开 App → 今日页 ListView 第 0 项出现 44pt 胶囊
       └ 「🦝 偷菜贼来了，现在赶跑它吧   [免费] ›」
  │
07:31  ③ 点胶囊 → 成本判定（先能量、后阳光）→ 状态 fighting
  │
07:31  ④ 战斗 10.0s（占位图形/emoji）— 任意时刻点空白 → 立即跳到 ⑦
  │      └ 落骰在 ③ 时**已算完并落盘**：动画只回放结果，所以跳过 = 同样的奖励
  │
07:31  ⑤ 结算卡：赶跑了 {小偷名} · ☀ +2 · 💧 浇水券（今日每盆浇水 -1）
  │
07:31  ⑥ 点「收下」→ 写账本一行 earn + 写 buff → 状态 claimed
  │
07:31  ⑦ 今日页胶囊变「🌻 赶跑了馋光鼠 · +2☀   去用掉 ›」
       └ 花园页左上角**第二行**出现 💧 buff chip（第一行仍是碎片/种子）
  │
09:00  ⑧ 一键浇水 5 盆 → 20☀（不是 25☀）→ buff 剩余额度 6-5=1
  │
23:59  ⑨ buff 卡自带「今日」角标，随时可点开看说明
  │
00:00  ⑩ 过期：buff 消失、能量清零、胶囊消失、新小偷生成
```

**纪律**：整条时间线**不跨天**。没有「昨晚战报」「巡逻槽」「24h 契约」「离线结算窗口」—— 这些是 v1 被否的结构，v2 一条不留。

## 3. 玩法规则（可直接开发）

### 3.1 触发与频次

| 项 | 规则 | 常量 |
|---|---|---|
| 位置 | 孩子端「今日」页 **ListView 第 0 项**（3 张状态卡**之上**，不是卡片、不占场景区） | — |
| 生成时刻 | **每日 0 点**（`dayKey` 变化即视为新一天，无需定时器：复用 `ChildTabAutoRefresh` 的跨天边界检查，`kChildTabBoundaryCheckSeconds`） | — |
| 只数 | **1 只/天**，恒生成（有存活植株时） | `kGuardThiefPerDay = 1` |
| 过期 | 次日 0 点。未处理的按 §3.6 结算损失 | — |
| 无植株 | 全园无存活株（含全部枯萎）→ 胶囊**不渲染**，零占位，不生成小偷 | — |
| 随机源 | **确定性哈希，禁止 `Random`**（与天气系统同款纪律）：`seed = '$dayKey|$childId|$kGuardDaySaltV2'`，一次派生「小偷种类 + 偷取值 + 掉落档 + 保底阳光」全部字段 | `kGuardDaySaltV2` |

> **为什么一律确定性哈希**：① 可单测、可重放、可调试（`强制出顺手贼` 才有意义）；② 杀进程 + 重进不会重掷（跳过动画与看完动画结果必须逐位相同）；③ 与天气 / 杂草害虫同源纪律，不引入第二套随机语言。

### 3.2 成本：优先免费，其次付费

| 顺序 | 条件 | 消耗 | 账单 | UI |
|---|---|---|---|---|
| ① | 今日能量 ≥ 1 | **0 ☀**（消耗 1 点能量） | **不写账本**（能量是派生量，不是货币） | 右侧绿色徽标 **`免费 · 1⚡`** |
| ② | 今日能量 = 0 且余额 ≥ 5 | **5 ☀** | 账本 1 行：`type=plant, refType='guard_pay', refId='garden', gross=5, net=-5` | 右侧橙色徽标 **`5 ☀`** |
| ③ | 今日能量 = 0 且余额 < 5 | **不允许支付** | — | 右侧灰色 **`还差 N ☀`**，且当天**免罚**（`kGuardFreeRideBalance=5`） |

🔴 **「有能量时必须不花阳光」是硬约束**：UI 必须让两种状态**一眼可辨**（颜色 + 徽标文字都不同），且 `resolve()` 内部**先读能量、能量为 0 才读余额**，不允许「先扣钱再退」的实现（会产生一行脏账本）。

### 3.3 能量（从专注派生，**零新表**）

| 项 | 规则 | 常量 |
|---|---|---|
| 获取 | 完成 **1 次有效专注** = 1 点 | `kGuardEnergyPerFocus = 1` |
| 「有效专注」判据 | `actualFocusMin ≥ kValidFocusMinutes(15)` **且** `actualFocusMin / plannedMin ≥ kCompletionRateThreshold(0.90)` —— **复用现有单点口径**，不新造 | 复用 |
| 日上限 | **2 点/天** | `kGuardEnergyDailyMax = 2` |
| 有效期 | 当天，**0 点清零** | — |
| 计算式 | `可用能量 = clamp(今日有效专注次数, 0, 2) − 今日已消耗点数` | — |
| 落点 | 「今日有效专注次数」**不存**；「今日已消耗点数」必须存（1 个 int，见 §7） | — |

🔴 **不许用 `sessions.length` 当「专注次数」**。今日页现有的「今日专注 N 次」用的是 `sessions.length`（含 3 分钟就放弃的 `shortAborted`），那是**展示口径**，不能拿来发能量 —— 否则孩子点开专注 3 秒退出就能刷满 2 点能量。能量必须走 `kValidFocusMinutes` + `kCompletionRateThreshold`。

### 3.4 小偷（3 种，P0 全做）

| 小偷 | 外观（P0 占位） | 偷什么 | 命中范围 | 稀有度（权重） |
|---|---|---|---|---|
| **馋光鼠** | 🐭 + 名字 | 阳光 **1~3** | 只扣余额，**不碰植物** | 常见 **0.45** |
| **啃叶虫** | 🐛 + 名字 | 成长度 **1~3%** | **随机 1 株**（存活株中随机） | 常见 **0.45** |
| **顺手贼** | 🦝 + 名字 | 阳光 **1~3** **+** 成长 **1~5%** | **全部存活株**，每株 −1~5% | 稀有 **0.10** |

| 常量 | 值 | 理由 |
|---|---|---|
| `kGuardThiefWeights` | `[0.45, 0.45, 0.10]` | 常见/常见/稀有；顺手贼 10% ≈ 每 10 天 1 次，够稀有到「遇到会截图」，又不至于一个月见不到 |
| `kGuardSunStealMin/Max` | 1 / 3 | 玄参定；均值 2 ☀ = 一顿浇水的 40%，疼但不疼死 |
| `kGuardGrowthStealMinPct/MaxPct` | 1 / 3 | 啃叶虫（常见）用轻档：1~3% = 1/10 ~ 3/10 个成长日 |
| `kGuardSlyGrowthStealMaxPct` | 5 | 顺手贼（稀有）用重档：1~5% = 最多半天成长 |
| `kGuardGrowthStealPerPlantDailyCap` | **0.05** | 🔴 **每株每天最多被偷 5%**，不随多天未登录叠加/翻倍 |
| `kGuardGrowthStealMaxTargets` | 全部存活株 | 顺手贼「全园」才有「稀有」的分量 |

**「命中范围」为什么这么定**（不是拍脑袋）：
- 若啃叶虫也全株命中，常见 × 全园 = 每天都掉 2%/株 → 30 天成株变 37.5 天（+25%），这已经不是「小扰动」而是「第二个成长系统」。
- 若顺手贼只命中 1 株，「每株每天封顶 5%」这条硬约束**永远不会被触发**（1 株最多 5%，封顶形同虚设）。只有全株命中，封顶才是活的护栏。
- 期望值核算见 §5.4：啃叶虫 1 株 + 顺手贼全株 ⇒ 平均 **−0.525pp/株/天** ⇒ 30 天 → **31.0 天（+3.4%）**，与天气惩罚（0.30pp/天，+2%）同一量级。

### 3.5 两条 🔴 硬约束（写成验收口径，不是「原则上」）

**约束 A：每株每天最多被偷 5%，且不因多天未登录叠加。**

```
acceptance:
  for any plant p, for any day d:
    totalGrowthStolen(p, d) <= kGuardGrowthStealPerPlantDailyCap  // 0.05
  离线 7 天回来 → 只结算「最近 1 天」，不是 7 天
```

**约束 B：成长进度绝不回退到上一个阶段。**

```
acceptance:
  newStage(p) == oldStage(p)               // 阶段枚举不变
  newProgress(p) = max(0.0, oldProgress - stolen)
  🔴 开花株（bloomed）免疫成长扣减 —— 只可能被偷阳光
```

> **为什么必须写「开花株免疫」**：开花株的 `progress == 1.0`。扣 5% 会把它打到 0.95 → 触发「花期结束 / 退回成株」的判定边界 → **这就是「阶段回退」本身**。P0 一律按「开花株不吃成长扣减」实现（`kBloomWiltProgressFloor=0.5` 的回落逻辑绝不能被守卫二次触发）。
> 同时：**不碰** `bloomedAt` / `bloomCount` / `wiltedAt` / 晨露待收 / 花期计时 / 碎片 / 种子券 / 阳光余额（除了小偷明确要偷的阳光）。

### 3.6 不处理 → 0 点结算

| 项 | 规则 |
|---|---|
| 结算时机 | 任一次「今日页 `_reload`」发现 `storedDayKey < today` → 先结算旧的一天，再生成新小偷。**不新增定时器**。 |
| 结算内容 | 按 §3.4 扣阳光（账本 1 行 `type=plant, refType='guard_stolen', net=-n`）和/或扣 `plant.progress`（走 `PlantRepository.savePlant`） |
| 窗口封顶 | **只结算最近 1 天**（`kGuardSettleMaxDays = 1`）。离线一周回来 = 罚 1 天，不是 7 天 |
| 首次安装 | 无存档 → **不生成历史、不结算损失**（否则新用户一进来就被罚） |
| 时钟回拨 | `today <= storedDayKey` → 不改状态、不产事件 |
| 幂等 | 唯一真源 = `dayKey`。重复调用时 `storedDayKey == today` → 空操作 |
| 免罚 | 无能量 **且** 余额 < 5 → **当天不结算损失**（`kGuardFreeRideBalance=5`），胶囊显示「阿葵自己顶班，今天不用管」 |
| 已点过胶囊但没点「收下」 | 视为**当天已处理，不结算损失**；并**自动补发必得阳光**（券作废，因为已过期）。理由：孩子的动作已完成，账不能因 UI 中断倒退 |

### 3.7 掉落：两步，必掉阳光 + 一次道具掷骰

**第一步（必得，100%）**：阳光 **3~5**（均值 4；B5b 玄参拍板由 1~3 上调 —— 被偷仍 1~3 封顶 3 ⇒ 净额 ∈ [0, +4]），账本 1 行 `type=earn, refType='guard_win'`。

**第二步（一次掷骰）**：

| # | 掉落 | 概率 | 面值(☀) | 生效口径（🔴 全部当天有效、当天过期） |
|---|---|---|---|---|
| 1 | **浇水券** | **35%** | 5~6 | 今日**每次浇水每盆** −1 ☀（与称号减免**相加**）。**当日累计节省封顶 6 ☀** |
| 2 | **劳动券** | **20%** | 2~3 | 今日除草/除虫**每次各 +1 ☀**（加在称号加成**之后**）。**当日累计追加封顶 4 ☀** |
| 3 | **施肥券** | **15%** | 2 | 今日**每次**施肥 −2 ☀：10 → 8（与称号减免相加：9−2=7）。**当日最多 12 次（最大盆位数）、净省最多 24 ☀**；每盆每天限施 1 次，是折扣不是发钱 |
| 4 | **免费浇水券** | **8%** | 5 | **任选一盆、仅一次**浇水免费 |
| 5 | **免费施肥券** | **4%** | 10 | **任选一盆、仅一次**施肥免费（最稀有） |
| 6 | **无道具** | **18%** | 0 | 只拿保底阳光（此时保底阳光**固定取上限 3 ☀**，见 §5.3） |

**合计 100%。期望面值 = 0.35×5.5 + 0.20×2.5 + 0.15×2 + 0.08×5 + 0.04×10 + 0 = 3.525 ☀**

#### 🔴 三条落地硬约束

**A. 「免费」类必须限定单株（本 PRD 最重要的实现陷阱）**

```
本项目有「一键浇水 / 一键施肥」：5 盆一键 = 25 ☀。
若「免费浇水券」按整批生效 → 省 25 ☀ → 直接打穿浇水经济（= 5 天浇水预算）。
acceptance:
  一键浇水 5 盆 + 免费浇水券(指定 1 盆) ⇒ 扣 4×5 = 20 ☀，不是 0 ☀
  一键施肥 5 盆 + 免费施肥券(指定 1 盆) ⇒ 扣 4×10 = 40 ☀，不是 0 ☀
```

**B. 不许有「什么都没有」的档**

18% 无道具档**必须仍有保底阳光**，且**取区间上限（现为 5 ☀）**。理由：家长付费档/无能量档花 5 ☀ 却空手而归，对 6~12 岁是强烈负体验，且会让「下次还敢点吗」变成否定。取上限在玄参拍板的区间内，不越界。（B5b：区间 1~3 → 3~5 后保底同步 3 → 5，语义「同源区间上限」不变。）

**C. 浇水券必须封顶，否则一键批量会放大**

```
4 盆 × 3 次浇水 = 12 次 × 1 ☀ = 省 12
12 盆 × 3 次 = 36 次 × 1 ☀ = 省 36  ← 面值 5~6 的 6 倍，通胀失控
⇒ kGuardWaterVoucherMaxSaves = 6（当日累计，超出不再减免）
```

### 3.8 全道具 × 称号 buff × 一键批量的放大上限（收口表）

| 道具 | 生效方式 | 与称号叠加 | 🔴 硬上限 | 最坏放大值 |
|---|---|---|---|---|
| 浇水券 | 每盆每次浇水 −1 | **相加**：5 − 1(称号Lv.5) − 1(券) = 3，`clamp ≥ 0` | 当日累计 ≤ **6 ☀** | 6（不是 36） |
| 免费浇水券 | **单盆、单次**免费 | 与称号无关（直接归零） | 1 盆 × 1 次 | 5（不是 25） |
| 施肥券 | 今日**每次**施肥 −2 ☀ | **相加**：10 − 1(称号Lv.10) − 2 = 7 | 当日最多 12 次（= 最大盆位数，每盆每天限施 1 次） | 24（12 盆 × 2） |
| 免费施肥券 | **单盆、单次**免费 | 同上（归零） | 1 盆 × 1 次 | 10 |
| 劳动券 | 每次除草/除虫 +1 | **加在称号之后**：草 1+1(称号)+1(券)=3；虫 2+1+1=4 | 当日累计 ≤ **4 ☀** | 4（不是 8.4） |

## 5. 经济测算（算式全部写出，不许拍脑袋）

### 5.1 符号与基线

| 符号 | 定义 | 值 |
|---|---|---|
| `W` | 必得阳光 | 3~5，**E = 4.00 ☀**（B5b 玄参拍板，原 1~3 / E=2.00） |
| `D` | 道具面值 | **E = 3.525 ☀**（§3.7 表） |
| `η` | 道具**实际使用率**（用掉的券价值 / 发出去的券面值） | 未知，**需埋点实测** |
| `L` | 不处理的期望损失 | **E = 1.10 ☀ + 0.525pp/株** |
| `I` | 低龄真实日收入 | **88 ☀**（月 **2640**） |
| `P` | 无能量时的支付 | **5 ☀** |

`L` 的算式：
```
E[偷阳光] = P(馋光鼠)×2 + P(顺手贼)×2 = 0.45×2 + 0.10×2 = 0.90 + 0.20 = 1.10 ☀
E[偷成长/株] = 0.45 × 2% × (1/4) + 0.10 × 3% × 1 = 0.225% + 0.30% = 0.525 pp/株/天
   （啃叶虫随机 1 株 ÷ 4 盆；顺手贼全 4 株各 3% 均值）
```

### 5.2 两条路径的收益

| 路径 | 现金（余额口径） | 面值（含券） | 对比「不处理」 |
|---|---|---|---|
| **有能量（免费）** | `+2.00 ☀` | `+2.00 + 3.525η` | **赚 3.10 ☀ + 保住 0.525pp** ✅ |
| **无能量（付费 5☀）** | `−5 + 2.00 = −3.00 ☀` | `−3.00 + 3.525η` | η=1 时赚 0.53；η=0 时**亏 1.90** ⚠️ |
| **不处理** | `−1.10 ☀` | `−1.10` | 基准 |

### 5.3 🔴 异议 1：付费路径的性价比**完全押在券用不用得掉**

**这是本 PRD 唯一的经济脆弱点，必须写清。**

```
付费路径净收益 = −3.00 + 3.525 × η
盈亏平衡点：η* = 3.00 / 3.525 = 0.851
```

- `η = 1.00` → +0.53 ☀（玄参算的 +0.5，成立）
- `η = 0.85` → **≈ 0**（临界）
- `η = 0.50` → **−1.24 ☀**（孩子花了 5 阳光，只省到 1.8，净亏）

而「不处理」只亏 1.10 ☀。**所以在 η < 0.85 时，「花 5☀ 主动处理」比「什么都不做」更亏** —— 这正是 v1 被否掉的同类硬伤（主动处理比被动挨打还亏）。

**三条缓解（全部零结构变更，建议 P0 全上）**：

| # | 措施 | 成本 | 效果 |
|---|---|---|---|
| R1 | **无道具档（18%）保底阳光固定取区间上限（现为 5）**（不是 3~5 随机） | 0（在玄参区间内） | 最坏情形恒为 `−5+3=−2`（B5b 区间下限抬高到 3 后自然成立）；`E[W]` 4.00 → 4.18 |
| R2 | 结算卡**把券的价值显式写出来**：「花 5☀ · 拿回 2☀ · 一张浇水券（省 5☀）」 | 文案 | 直接把 η 拉高（孩子看得懂「我是赚的」才会去用券） |
| R3 | 付费前给**「今天不赶了」**选项，并明示会损失什么（`−1~3☀ / −1~3% 成长`） | 1 个按钮 | 儿童产品伦理底线：不强迫消费；也顺手消掉「主动处理更亏」的观感 —— 孩子有知情权就不算被坑 |

> R1 后重算：`E[W] = 0.82×2 + 0.18×3 = 1.64 + 0.54 = 2.18 ☀`
> 付费路径 = `−5 + 2.18 + 3.525η = −2.82 + 3.525η`，平衡点 `η* = 0.800`（比 0.851 好 5 个点）。仍未根治，但最坏损失从 −4 收到 −2。

### 5.4 不处理的疼度：够不够「有感」？

| 口径 | 值 | 换算成成株时长（算式：300pp ÷（日成长 − 损失）） |
|---|---|---|
| 平均（零养护） | −0.525 pp/株/天 | `300 ÷ (10 − 0.525) = 31.7 天` → **+5.5%**（30 → 31.7） |
| 平均（满养护） | −0.525 pp/株/天 | `300 ÷ (16 − 0.525) = 19.4 天` → +3.4%（18.75 → 19.4） |
| 单日最坏（顺手贼全园满值） | 每株 −5pp → 4 盆 −20pp | 全园一次性少 **2 天**进度（20pp ÷ 10pp/天） |
| 对照组：极端天气惩罚 | 0.30 pp/天 | `300 ÷ (10 − 0.30) = 30.9 天` → +3.1% |

**结论**：比天气惩罚重约 **1.8 倍**（+5.5% vs +3.1%），但仍在**同一量级**（都是「多等几天」而不是「翻倍」），**不构成「第二个成长系统」**。且「每株 5%/天」的封顶在任何路径下都不会让成株时长翻倍 —— 需要连续 30 天都掷到顺手贼满值（概率 ≈ 1e-30）。若上线后觉得太疼，第一个动作是把 `kGuardSlyGrowthStealMaxPct` 从 0.05 调到 0.03（**一个常量**，顺手贼退化为「重一点的啃叶虫」）。

### 5.5 月度通胀评估（玄参点名要算的）

| 口径 | 日 | 月（30 天） | 占低龄月收入 2640 | 判定（5% 红线） |
|---|---|---|---|---|
| **有能量 · 余额口径**（只算真金白银） | +2.00 ☀ | **+60.0 ☀** | **2.27%** | ✅ 安全 |
| **有能量 · 面值口径**（含券） | +5.525 ☀ | **+165.75 ☀** | **6.28%** | ❌ **超线 1.28pt** |
| 无能量 · 余额口径 | −3.00 ☀ | −90.0 ☀ | −3.41%（负向） | ✅ 不构成通胀 |
| 无能量 · 面值口径 | +0.525 ☀ | +15.75 ☀ | 0.60% | ✅ 安全 |
| 完全不处理 | −1.10 ☀ | −33.0 ☀ | −1.25% | ✅ |

#### 超线了，阀门给三个（按干预成本排序）

| 阀门 | 改什么 | 重算面值/天 | 月 | 占比 | 结构变更 |
|---|---|---|---|---|---|
| **V1** | 浇水券 35% → **25%**，无道具 18% → **28%** | 4.975 | 149.3 | 5.65% | 无（2 个常量） |
| **V2** | `kGuardWaterVoucherMaxSaves` 6 → **3**（浇水券只省 3 而非 5~6） | 4.650 | 139.5 | 5.28% | 无（1 个常量） |
| **V3** | **V1 + V2** | 4.350 | 130.5 | **4.94% ✅** | 无（3 个常量） |

#### 我的建议（不迎合）

**先按原表上线，用「余额口径 2.27%」判 5% 红线，同时接受面值口径 6.28%**，理由三条：

1. **5% 红线原本是拿来防「余额膨胀」的**，而券是**折扣**不是收入 —— 它只在孩子「本来就要浇水/施肥」时才兑现，而「本来就要浇」这件事已被 `4 盆 2水1肥 = 78☀ = 88.6% 的收入` 死锁，不存在「为了用券而多花钱」的路径（浇水次数有硬上限 3/天/盆）。
2. **券没有复利路径**：每天只有 1 只贼 → 1 张券 → 当天过期。没有「攒券」「叠券」「换购」的入口，就没有通胀的放大器。
3. **V3 达标要砍掉 21% 的券包**，代价是「打小偷的爽感」直接缩水（浇水券从「省 5 个」变「省 3 个」，孩子是数得出来的）。**为了 1.3 个百分点的纸面数字牺牲日常爽感，不划算。**

**但必须留两个硬闸 + 一条埋点**：
- `kGuardWaterVoucherMaxSaves = 6`（防一键批量放大，**不可删**）
- `kGuardLaborVoucherCap = 4`（防满园放大，**不可删**）
- 埋点 `guard_voucher_used`（券核销时上报面值与实际节省）→ **上线 2 周看 η**：
  - `η ≥ 0.85` → 保持原表，不动；
  - `η < 0.85` → **先上 R1/R2/R3**（§5.3），再看 η；
  - `η < 0.60` → 付费路径确实在伤人，此时才动 V3（或把 `kGuardPayCost` 5→3，一个常量）。

## 7. 技术口径（能量派生 / 存储 / 幂等）

### 7.1 能量能不能从现有专注记录直接派生？——**能，零新表**

**结论：能。不需要任何新表、不需要给 `FocusRepository` 加任何方法。**

```
今日有效专注次数 = sessionsOfDay(dayKey).where((s) =>
      s.actualFocusMin >= kValidFocusMinutes(15) &&
      s.actualFocusMin / s.plannedMin >= kCompletionRateThreshold(0.90)
    ).length
可用能量 = clamp(今日有效专注次数, 0, kGuardEnergyDailyMax) - 今日已消耗点数
```

依据：
1. `FocusRepository.sessionsOfDay(dayKey)` **已存在**，返回的 `FocusSession` 带 `plannedMin` / `actualFocusMin` 全字段 → 判定所需数据全在（`focus_repository.dart:7`、`focus_session.dart`）。
2. 判定式**已在三处独立实现且口径一致**（`focus_local_repository._isValidSession`、`focus_report_service`、`plant_growth_service`），遵守「单点真源」应抽一个共享纯函数 `isValidFocusSession(FocusSession)`，**不要写第四份拷贝**。
3. 今日页 `_reload` 已经在调 `sessionsOfDay(today)` → **零新增 IO**，把 `sessions` 复用一次即可。

🔴 **不能用 `sessions.length`**：今日页「今日专注 N 次」用的是 `sessions.length`（含 `shortAborted`，即 3 分钟就放弃的会话）。拿它发能量 = 「点开专注 3 秒退出」就能刷能量。

**不能派生的是什么（= 必须存）**：
| 数据 | 为什么不能派生 | 落点 |
|---|---|---|
| **今日已消耗能量点数** | 消耗是「动作」，账本里没有记录（免费路径不写账本） | prefs（1 个 int） |
| **当日小偷 / 落骰结果 / 领取状态 / 当前 buff** | 完全新的状态 | prefs（1 个 JSON） |

### 7.2 存储方案（零 schema 迁移）

| 数据 | 落点 | 键 / 结构 | 丢失后果 |
|---|---|---|---|
| 当日状态 | `SharedPreferences`（String，JSON） | `guard_day_state_v2_<childId>` | 只丢「当天的 1 张券 + 1 次阳光」→ 可接受 |
| 阳光收入 / 付费 / 被偷 | `SunlightRepository.append` | `guard_win` / `guard_pay` / `guard_stolen` | 账本 append-only，永不丢 |
| buff 是否已用 | 同上 JSON 内（`usedCount` / `remainingSaves`） | — | 同上 |

**JSON 结构（建议，架构师可调）**：
```json
{
  "dayKey": "2026-11-08",
  "status": "none|pending|fighting|claimed|short",
  "thiefKind": "sunMouse|leafBug|slyThief|null",
  "energyUsed": 0,
  "paidSun": 0,
  "sunStolen": 0,
  "growthStolen": {"<plantId>": 0.03},
  "winSun": 2,
  "dropKind": "waterVoucher|...|none",
  "buff": {"kind":"waterVoucher","savedSoFar":0,"usedCount":0}
}
```

🔴 **必须带 childId 后缀**。`SharedPreferences` 是**设备级**（现有键如 `kPrefAppUsageDate` 都不带 childId），而专注数据是 **childId 级**（`FocusLocalRepository._childId`）。若不带后缀：家里两个档案时，**A 的小偷会出现在 B 的今日页，A 的浇水券会被 B 用掉**。这是本 PRD 唯一必须加的一条存储纪律。

### 7.3 三步幂等（杀进程 / 跳过 / 重进都必须一致）

```
① resolve()   ：幂等。掷骰（确定性哈希）→ 写 outcome 到 JSON（status=fighting）
                  🔴 只落盘，不写账本、不发 buff
② claim()     ：幂等。status==claimed ⇒ no-op
                  写账本 1 行 earn(guard_win) + 写 buff + status=claimed
③ expire()    ：幂等。dayKey 变化时调用（§3.6）
                  按 status 分支：pending → 结算损失；fighting → 自动 claim 阳光（券作废）；
                                 claimed → 无事；short → 无事
```

**为什么 reward 要在 `resolve` 就定死**：孩子点「跳过」时必须拿到和看完 10 秒一模一样的奖励。若在动画结束时才掷骰，跳过就变成了「另一条路径」，直接违反「奖励与观看时长零相关」的硬约束。

## 11. 验收口径（可执行，逐条能写测试）

| # | 断言 | 做法 |
|---|---|---|
| A1 | **跳过 = 看完** | 同一 `dayKey` + `childId`：跳过路径 vs 看完路径 → 账本行数、金额、buff 种类**逐位相同** |
| A2 | **奖励与观看时长零相关** | 同上，且 `guard_battle_skip` 不影响任何数值 |
| A3 | **先能量、后阳光** | 能量 = 1 → 点击后 `guard_pay` 账本行数 = 0 |
| A4 | **有能量绝不花阳光** | 同上，且余额不变 |
| A5 | **能量来自有效专注** | 3 分钟 `shortAborted` 会话 × 5 → 能量 = 0；15 分钟 / 完成率 95% 的会话 × 1 → 能量 = 1 |
| A6 | **每株每天 ≤ 5%** | 强制 4 盆各扣 10% → 实际扣 5%；连续 7 天不处理 → 每天**各**结算 1 次（单日仍 ≤5%），但**离线 7 天只结算 1 天**（A8） |
| A7 | **阶段不回退** | 种子期 progress=0.02 扣 5% → progress = 0.0，stage 仍为 seed；bloomed 株 progress 恒 1.0 |
| A8 | **离线封顶 1 天** | 模拟离线 7 天 → 只产生 1 天的损失（`kGuardSettleMaxDays`） |
| A9 | **幂等** | 同一 `now` 连调 `resolve` / `claim` / `expire` 各 10 次 → 账本/buff/进度变化 = 1 次的量 |
| A10 | **免费券单株** | 一键浇水 5 盆 + 免费浇水券(1 盆) → 扣 **20 ☀**（不是 0） |
| A11 | **浇水券封顶** | 12 盆 × 3 次浇水 + 浇水券 → 总节省 = **6 ☀**（不是 36） |
| A12 | **劳动券封顶** | 12 盆满园 + 劳动券 → 追加 = **4 ☀**（不是 8.4） |
| A13 | **无道具档仍有阳光** | 强制 `dropKind = none` → 必得 **3 ☀**，结算卡不出现「什么都没拿到」 |
| A14 | **付费路径明示代价** | `pending.paid` 点击 → 必须先出确认卡；取消后余额/状态零变化 |
| A15 | **免罚线** | 余额 4 ☀ + 能量 0 → 胶囊为 `short`，0 点结算 **损失 = 0** |
| A16 | **childId 隔离** | 两个 childId 下同一 `dayKey`：A 的 buff 不出现在 B 的花园，A 的胶囊状态不影响 B |
| A17 | **零新增货币** | 全量搜索：本玩法不写 `premiumFragmentBalance`、不调 `unlockSpecies` |
| A18 | **今日页零回归** | `absent` 时今日页与改动前**逐像素一致**（3 卡 + 钉底按钮 + 场景区位置不变） |
| A19 | **花园页零回归** | 无 buff 时左上角 3 chip 位置逐像素不变；有 buff 时网格可视高度不变 |

### 14.2 存储结论（一句话）

**零 schema 迁移、零新表、零新列**：状态落 `SharedPreferences`（1 个带 childId 后缀的 JSON），金钱落既有阳光账本，进度落既有 `plants` 表。
唯一需要新增的纪律：**prefs 键必须带 childId**（现有 prefs 键都是设备级，而专注/植物数据是 childId 级）。

### 14.3 三条实现红线（写进 code review checklist）

1. **`resolve()` 只落盘、不写账本**；`claim()` 才写账本。否则跳过会变成另一条经济路径。
2. **免费券的接口签名只收 `plantId`**：`freeWater(plantId)`，**不存在** `freeWaterBatch()` —— 用类型系统堵住「整批免费」。
3. **所有券的减免只经 `guard_math.dart` 的纯函数算出**，`garden_page.dart` / `plant_growth_service.dart` 只消费结果，不自行 `-1`。

### 14.4 建议的实现顺序（每步都可独立验收）

```
① guard_math.dart 纯函数 + 单测（A6/A7/A10/A11/A12 全部可在这一步跑绿）
② guard_state_store（prefs）+ childId 隔离单测（A16）
③ guard_service：resolve/claim/expire + 幂等单测（A9/A8）
④ 胶囊 5 态 + 今日页接线（A18 零回归）
⑤ 战斗 overlay + 跳过（A1/A2）
⑥ 结算卡 + 收下（A13）
⑦ 5 种券在花园生效（A10/A11/A12 端到端）
⑧ buff chip（A19）
⑨ 损失结算 + 免罚线（A15/A6/A7）
⑩ 调试面板 + 埋点
```
