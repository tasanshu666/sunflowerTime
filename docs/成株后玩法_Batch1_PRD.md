## 1. 背景与目标

### 1.1 背景
当前（M3 收口、宪法 C12 生效后）植物养成已实现「首次长成 → 盛开 3 天 → 花谢回落 0.5 → 自动/养护回填再盛开」的循环。但该循环**复用首长成的成长速率**，导致：
- 普通植物复开花约 **养护 3 天 / 不养护 5 天**；
- 精品植物复开花约 **养护 6 天 / 不养护 10 天**（精品每阶段 480h，自动回填 5%/天）。

节奏过快、且普通/精品缺乏清晰的档位区分，缺乏「成株后长期养护」的沉淀感与休整期。本次 Batch 1 在既有循环上补齐三件事：**独立的复开花节奏（普通/精品分档）**、**花期双阶段随机事件奖励**、**植物碎片货币**。（后续 2026-09-27 又并入物种表改版与奖励物图标化，见 §8。）

### 1.2 目标（Product Goals，正交）
1. **G1 分档的长期复开花节奏**：复开花统一为「养护约 7 天 / 不养护约 14 天」，**精品在此基础上 ×1.5（养护 ≈10.5 天 / 不养护 ≈21 天）**。
2. **G2 花期情绪与回访钩子**：用「开花瞬间高情绪奖励」＋「**48h 后二次回访奖励**」提升回访与正反馈，奖励全随机、可校验，并**以图标直观呈现「到底奖励了什么」**（C16）。
3. **G3 稀缺的碎片货币**：碎片仅由开花掉落（瞬间 ＋ 48h 后），用于在花园页**按物种兑换**精英物种（2026-09-27 改版后；原「满 8 片解锁」已废止，见 §8.5）。

### 1.3 User Stories
- 作为**孩子**，我希望花朵凋谢后隔一段时间才再次盛开（普通约 1–2 周、精英更久），让花园有「等待与养护」的节奏感。
- 作为**孩子**，我希望一开花就看到**头顶冒出明确的奖励图标**（阳光 / 植物碎片 / 种子），点一下就收下，而不是「一个图标 + 看不懂的文案」。
- 作为**孩子**，我希望**两天后（48h）回来看花时，头顶有可点击的奖励图标**，点一下就能领到二次奖励（即使昨天没开 App 也不会漏）。
- 作为**孩子**，我希望攒够碎片后，能在花园页**选择**兑换哪株植物（并看到它是普通 6 片还是精英 10 片），有收集与决策的乐趣。
- 作为**家长**，我希望碎片来源严格可控（仅开花掉落），避免通胀，保持精英物种稀缺。

## 3. 数值表

> **档位定义**：**精品档 = `rare` + `legendary`（除 `common` 外）**；下文「普通」= `common`，「精品」= 精品档。（2026-09-27 产品负责人裁定）

### 3.1 复开花节奏（**普通 7/14；精品 ×1.5 ≈10.5/21**）

| 项 | 普通 | 精品（×1.5） | 说明 / 收口 |
|---|---|---|---|
| 花谢回落下限 | **0.5** | **0.5** | 复用 `kBloomWiltProgressFloor`，**不变** |
| 花期时长（盛开保持） | **3 天** | **4.5 天** | `kBloomDurationDays = 3`；精品 = 3 × 1.5 |
| **复开花自动回填率** | **≈3.6%/天** | **≈2.4%/天** | `kRebloomAutoProgressPerDay = 0.036`；精品 = 0.036 ÷ 1.5 |
| **复开花养护增量（封顶）** | **≈3.6%/天** | **≈2.4%/天** | 浇水 `kRebloomWaterProgressGain = 0.008`（3 次/天）+ 施肥 `kRebloomFertilizeProgressGain = 0.012`（1 次/天）= 3.6%/天；精品同步 ÷1.5 |
| 不养护再开花 | **≈14 天** | **≈21 天** | 0.5 ÷ 回填率 |
| 养护再开花 | **≈7 天** | **≈10.5 天** | 0.5 ÷ (回填率 + 养护增量) |

> 计算口径：`(1.0 − 0.5) ÷ 速率`。普通：不养护 0.5/0.036≈13.9≈**14**；养护 0.5/0.072≈6.94≈**7**。精品 = ×1.5：≈20.8≈**21** / ≈10.4≈**10.5**。
> **首花（种子→成株）节奏不变**：不养护 30 天 / 精品 60 天 / 满养护约 19 天。

## 4. 数据模型变更 / 技术方案影响

> **schemaVersion 序列**：Batch 1 本体 **v9→v10**（`Plants.bloom_count` ＋ 3 表：`PremiumFragments` / `PendingBloomRewards` / `UnlockedSpecies`）；**v10→v11**（物种表改版，旧植株删除，§8.9）；**v11→v12**（奖励三列，C16，§4.2）。**当前代码 `schemaVersion = 12`。**

### 4.1 碎片与解锁（3 张新表）
- **`PremiumFragments`**：记录碎片持有余额（**对外叫「植物碎片」**；当前用于按物种兑换的余额校验，见 §8.5）。
- **`UnlockedSpecies`**：记录已解锁 / 拥有的物种（**语义已随 §8.5 改变**）。
- ~~**`unlockPremiumSpecies(id)`** / `kPremiumFragmentUnlockThreshold = 8`~~ **【2026-09-27 已废止，见 §8.5】**。

### 4.2 pending 奖励存储（48h 头顶图标；C16 掉落即定奖）

- 开花瞬间写入一条 **pending 记录** 到 **`PendingBloomRewards`**，`due_at = bloomed_at + 48h`，`claimed = false`。
- **掉落即定奖（C16）**：奖励在**登记掉落时**就 roll 定奖并存库 → 新增 **3 列**：

| 列 | 类型 | 默认 | 语义 |
|---|---|---|---|
| `reward_sunlight` | INTEGER | 0 | 预先定好的阳光数 |
| `reward_fragments` | INTEGER | 0 | 预先定好的碎片数 |
| `reward_species_id` | TEXT | NULL | 预先定好的种子物种 id |

- **schemaVersion 11 → 12**。
- **历史行哨兵（关键）**：历史行三列必为 `0 / 0 / null` → 视为「**未预先定奖**」，结算时**退回旧的现场 roll 路径**并把结果回写（保底基础阳光恒 ≥1，哨兵不与真实奖励冲突）；UI 显示**通用礼包图标**。
- 到期后**不自动发放**：奖励以**头顶图标**呈现（植物 / 花盆上方）；小朋友**点击即收下该条全部奖励**（按条收集）→ 发放 → `claimed = true`。
- **自动兜底**：若**花谢前**未点击，则**自动到账**（置 `claimed`）并**提示**「花朵凋谢，奖励已自动收下：+N ☀ 阳光」。
- 状态守卫 ＋ 事务保证**每株只发一次**（不重复、不漏发）。
- **领域结果可回传**：新增 `BloomRewardOutcome{sunlight, fragments, seedSpeciesId, isInstantPhase, autoSettled}`；`collectBloomReward(rewardId, now)` 由 `Future<void>` 改为**返回它**；`tickAll(now, {List<BloomRewardOutcome>? autoSettled})` 增设**可选出参**（默认 null，回传「花谢自动到账」明细，**向后兼容、不改返回类型**）。
- 迁移测试：v9→v10（3 表 + `bloom_count`）、v10→v11（旧植株清理）、**v11→v12（补 3 列，幂等 + 老 pending 行不丢）**。

### 4.3 复开花节奏（技术方案影响）
- **独立常量**：`kRebloomAutoProgressPerDay = 0.036`、`kRebloomWaterProgressGain = 0.008`、`kRebloomFertilizeProgressGain = 0.012`、`kRebloomPremiumCycleMultiplier = 1.5`。
- 复开花回填**不再**使用 `kPlantGrowthHoursPerStageDefault(240)/Premium(480)` 推导的 10%/5%/天。
- **复开花识别**：`Plants.bloom_count`（INT）列。

### 4.4 复用的既有常量（**不变**）
- `kBloomDurationDays = 3`（普通花期；精品 ×1.5 = 4.5）
- `kBloomWiltProgressFloor = 0.5`（花谢回落下限）
- `kPlantWaterProgressGain = 0.01` / `kPlantFertilizeProgressGain = 0.03` / `kPlantWaterMaxPerDay = 3` / `kPlantFertilizeMaxPerDay = 1`（首长成养护；复开花期间由 `kRebloom*` 收口）

> 注：`reward_template.dart`（§4.8 定价表）**不用于**本批开花奖励 —— 本批奖励是系统自动发放的阳光/碎片/物种种子，并非商店兑换。

## 6. 技术风险

- **T1 复开花速率切换点**：未可靠区分「复开花」与「首成长」会出现老 bug；须用 `bloom_count` ＋ 迁移/快进用例锁死。

- **T3 重复发放 / 漏发**：`PendingBloomRewards` 的 `claimed` 守卫 ＋ 事务保证「关 App 跨 48h 多次开关」不重复、不漏发；「花谢前未点自动到账」与「手动点击」两条路径互斥且幂等。（**注**：气泡点击曾因 DAO 裸 `insert` 与 Fake upsert 语义不一致而崩溃，已改 `insertOnConflictUpdate`，见 `bug记录表.md` B-NEW-1）
- **T4 schemaVersion**：v9→v10→v11→v12，均须迁移测试。
- **T5 宪法一致性**：C12「花谢回落 0.5、体型保持成株、养满自动再盛开」全部维持；C12 第 3 条「死亡返还 30%」已被 C15 推翻（死亡全损，§8.6）；C16 只改呈现与 roll 时机，**不动概率数值**。
- **T6 哨兵语义**：历史 pending 行 `0/0/null` 与「真实奖励恰为 0/0/null」的区分依赖「保底基础阳光恒 ≥1」不变量；实现须保证该不变量（否则老行会被误判）。

### 8.3 计价模型（支付方式，2026-09-28 重构，宪法 C17）

- **向日葵（新手免费起始植物）** → **免费**（0）。

### 8.4 限种与再种
- **每物种同时仅存活一株**；**每兑换一次 = 一株**；**种植本身不额外扣阳光**；植株死亡 / 移除后再种需重新交费。

### 8.5 碎片与兑换（**废止「满 8 解锁」**）
