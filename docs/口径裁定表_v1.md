## C3「有效专注」同名不同义

**分歧**：G1 判据＝横屏放置 ≥5min；WFD 口径＝≥15min 且完成率 ≥90%。

## C5 免确认月上限 vs 可调月池

**分歧**：月池可调 100–1200；免确认月累计上限写死 100/40；池调低后 25% 是否重算未定。


## C10 定价取消分龄系数 K（2026-09-21）

**分歧**：原设计消耗侧价格 = `baseCost × 分龄系数 K`（低 1.0 / 中 1.2 / 高 1.5），孩子端显示价与扣费价被 K 放大（家长设 20、高年级孩子看到/扣 30）。真机反馈数值对不上。

**裁定**：**定价不再叠加分龄系数 K**。家长设定价 = 孩子显示价 = 实际扣费价，三者统一为 `baseCost`。

**代码纪律**：
- `RedemptionOrchestrationService._priceFor(RewardTemplate, AgeTier)` 直接 `return t.baseCost`；`store_page` 兑换价直接取 `tpl.baseCost`。
- 删除 `core/utils/math_ext.dart` 的 `applyAgeTierK`（已无调用点）。
- `age_tier_params.dart` 的 `k` 常量与 `ageTierK()` **保留**为档位参数单点，但**生产定价链路不得再调用**（仅供未来分档展示复用）。`reward_template.dart` / `reward_seed.dart` / `age_tier_params.dart` 文件头已注明此决策。
- 巡检：全仓不得出现 `applyAgeTierK(` 调用；定价路径只应出现 `baseCost`。

## C11 每日额度：取消分段软顶，改「两条独立额度线」（2026-09-23）

**分歧**：PRD §4.5 公式①、开发计划 v1.0 T10、验证计划 §4.3 都写「软顶三段：0–60 全额 / 60–90 计 50% / 90–110 计 20% / 硬顶 79」，而 M4 已上线的「每日专注上限」是年段三档 60 / 90 / 120。两套数作用在同一份产出上，互相矛盾：
- 高年段孩子专注满 120 分钟只拿得到 **79** 阳光 —— 「120」是摸不到的天花板；
- 该 79 实际是**按会话**各自过软顶（`settle()` 里套的是本次会话自己的原始产出），一天多场专注可远超 79。

**裁定（玄参，2026-09-23）**：

1. **取消分段打薄**。专注产出恒为 **1 分钟 = 1 阳光**，不再有任何折损率。
2. **每日专注上限跟随年段**：低 **60** / 中 **90** / 高 **120**（对应 1–2 / 3–4 / 5–6 年级）。因 1:1，该上限同时是「当日专注分钟上限」与「当日专注阳光上限」。
3. **成长奖励另有独立日上限** `kTaskCheckinDailyCap = 79`。两条额度线**各读各的账目类型**（专注 `focus_session`、成长 `task_checkin`），**互不挤占**。
4. **「其他年级无限制」不落地**：`AgeTier` 只有低 / 中 / 高三档，App 无第 4 档入口；产品只服务 1–6 年级，现状即满足。
5. **额度必须三道拦**：选时长页灰掉超额度档位 → 开始前按剩余额度截断 → **结算时再硬截断一次**（唯一可靠兜底，防计时器因「离席恢复」多算）。

**数学原因（为什么不能两者兼得）**：分段的第一段本身即「60 分钟以内全额」，因此「封顶值跟随年段」与「分段打薄」不能共存 —— 一旦封顶降到年段值，超出年段的部分必然零收益，打薄没有中间地带。

**废止清单（代码中不得再出现）**：

| 废止对象 | 原位置 |
|---|---|
| `kSoftCapDailyMax` / `kSoftCapSeg1` / `kSoftCapSeg2` / `kSoftCapSeg3` / `kSoftCapSeg2Rate` / `kSoftCapSeg3Rate` | `prd_params.dart` |
| `computeSoftCap(...)` | `math_ext.dart` |
| `TaskCheckInOutcome.cappedBySoftCap` | 改名 `cappedByDailyCap` |
| `_softCapGrant` | 改名 `_dailyRewardGrant` |

**代码纪律**：
- 专注侧额度单点收口在 `math_ext.dart` 的 `effectiveFocusSunlight({focusSunlight, remainingAllowance})`。额度消耗的**唯一真源**是账本 `refType='focus_session'` 的当日净额（`SunlightService.focusEarnedToday` / `focusRemainingToday`）；页面与服务**不得各自求和** `actualFocusMin`。
- 成长侧单点收口在 `task_checkin_service.dart` 的 `_dailyRewardGrant`，**只读 `checkInRefType` 自身账目**。不得再读当日全部 `earn` —— 那会让专注 / 家长赠予一拿满就挤掉成长奖励（「孩子打卡却不发阳光」），这是本次一并修掉的旧 bug。
- `SunlightService.settle` 必须收 `required int dailyFocusCap`（由调用方从 `AppSettings.dailyFocusCap` 传入，服务不另存一份）。专注与任务奖励**分两条账目**写：任务奖励若并进专注那条，其 `net` 会被计入「已用专注额度」，让下一场专注少拿阳光。
- **巡检（只针对代码）**：`lib/` 与 `test/` 内**不得出现** `computeSoftCap` / `kSoftCap` / `cappedBySoftCap` / `softCap` / `cappedBySoftCap`。文档侧允许在**废止清单与历史 bug 台账**中保留旧名（用于追溯），但**描述现行规则**时一律用「额度」口径，不得再写旧公式。

**效力**：本条优先于 PRD §4.5「软顶三段 + 硬顶 79」、开发计划 v1.0 T10「阳光记账与软顶」、验证计划 §4.3「软顶三段写死」三处旧表述。PRD 正文的软顶公式**保留为历史版本**（PRD 由玄参自行维护，不在本次回写范围内）。

## C12 植物枯萎 / 恢复 / 花谢循环（2026-09-23）

**分歧**：PRD §4.6 与 M3 架构/设计文档写「枯萎 = 7 天未浇水 → 花 **20 / 8** 阳光救回（`revive`）→ 再 7 天死亡」，与现行实现对不上（枯萎阈值已改、付费救回已整段删除）。

**裁定（玄参，2026-09-23）**：

1. **枯萎触发**：未浇水天数 **7 → 3 天**（`kPlantWiltDays = 3`）。浇水与施肥**都会刷新**枯萎计时（两者都写 `lastWaterAt`）。
2. **取消付费救回**：`PlantGrowthService.revive()` 与 `kPlantReviveCostLow/High` **整段删除**。枯萎**只能靠养护恢复**：
   - 枯萎未满 **3** 天（`kPlantWiltRecoverHardDays`）：**浇水 1 次**即恢复；
   - 枯萎已满 3 天：需**浇水 3 次 + 施肥 1 次**（`kPlantWiltRecoverHardWater = 3` / `kPlantWiltRecoverHardFertilize = 1`）。
   - 枯萎期间**仍可浇水/施肥**（`careQuota` 放开 `wilting`，actionable = `growing || wilting`）。
3. **死亡**：枯萎后再 **7 天**（`kPlantDeathDays = 7`）仍未恢复 → `dead`，返还 **30%** 种植成本（`kPlantDeathRefundRate = 0.30`，死亡时即返还）。`dead` 只剩「铲除回收」入口。（⚠️ **2026-09-27 更新：本句「返还 30%」已被 C15 推翻 —— 改为死亡全损、不退还任何资源**）
4. **花谢循环**：成株盛开保持 `kBloomDurationDays = 3` 天 → **花谢**（`status → growing`、进度回落至 `kBloomWiltProgressFloor = 0.5`），**体型保持成株不缩回幼苗**；由时间/养护重新养满后**自动再盛开**。老库升级来的已开花植物（`bloomedAt = null`）首次 tick 自动补计时起点，不立即花谢。
5. **恢复次数以账本为唯一事实源**：用 `SunlightRepository.countByRefTypeAndRefIdSince`（按 `refType` + `refId` + 起算时刻计数）派生，**不得给 `Plants` 表加计数列**（免一次 schema 迁移，且天然可对账）。

**代码纪律**：

- `lib/` 与 `test/` 内**不得出现** `revive(` 调用、`kPlantReviveCost`、`onRevive`。账本 `refType = 'plant_revive'` 仅作**历史数据**保留可读（`child_sunlight_history_page.dart` 的展示映射保留，旧账本仍能显示）。
- 枯萎恢复需**清空 `wiltedAt`**，而 `Plant.copyWith` 的 `?? this.x` 模式**清不掉可空字段** → 必须用 `Plant(...)` 构造器显式重建，不得依赖 `copyWith(wiltedAt: null)`。
- 恢复判定顺序：`water` / `fertilize` 写账本后调 `_maybeRecover`；**不得**在服务外用 UI 状态拼装恢复条件。

**效力**：本条优先于 PRD §4.6「7 天枯萎 / 20·8 阳光救回」、`docs/M3_架构设计_家长端补齐与植物养成.md`（revive 设计）、`docs/M3_class-diagram.mermaid` 与 `docs/M3_sequence-diagram.mermaid`（revive 调用链）、`docs/验证计划_SunFocus_G0G2.md:308` 四处旧表述。上述历史设计文档**保留原样**（历史快照），以本条为准。

## C13 花园表现层与美术规格（2026-09-23）

**分歧**：花园原实现为「卡片列表 + 自绘陶盆 `_PotPainter` + 自绘草地渐变 `_GrassArea`」，美术清单 v1 要求的图片规格是「512×512、正方形、主体限制在**居中内切圆**（圆形裁切）」；玄参交付的美术图实际为 **2048×2048 画布（内容仅占 35%×30%）、且植物图自带陶盆**，两套假设互不兼容。

**裁定（玄参，2026-09-23）**：

**① 美术统一画布规格（唯一）**

| 项 | 值 |
|---|---|
| 画布 | **1200 × 2000**（宽 : 高 = 3 : 5），PNG 全透明底 |
| 花盆宽度 | **800 px**（占画布宽 66.75%） |
| 花盆底部 | **贴合画布底边**（`y = 2000`） |
| 盆心水平位置 | **`x = 600`**（画布水平正中） |

- 新图入库前**必须先归一化**：`tools/normalize_plant_art.py`（幂等，glob 扫描 `assets/plants/*.png` 与 `assets/pots/*.png`，新增图自动纳入）；原图备份至 `assets/_originals/`（**不在** `pubspec.yaml` 的 assets 声明内，**不进包**）。
- **废止** v1 清单的「512×512 / 圆形裁切 / 内切圆 86% 安全区」规格：圆形底色与圆形裁切**已从代码中移除**。

**② 花盆归属：植物图自带，代码不叠**

- 每个阶段的植物图**已自带陶盆** → `GardenPot` **只渲染一张植物图**，**不得再叠加** `pot.png`（否则一格画两个盆、边缘错位）。
- 花盆与背景**已从 `CustomPaint` 自绘改为 PNG 美术资源**：`assets/pots/pot.png`（空花盆格用）、`assets/garden/background.png`（页面背景）。自绘实现（`_PotPainter` / 渐变）**仅作资源缺失时的兜底**，不得作为主链路。
- 全部盆**必须等大**：`growthScale = 0`（草地里植物**不再随进度缩放**），进度反馈一律交给**盆下细进度条**。

**③ 网格布局口径**

| 项 | 值 | 常量/出处 |

## C14 App 总使用时长防沉迷（2026-09-23）

**背景**：`anti_addiction_service.dart` 的 `appUsageMinutes` 参数**从未被任何调用方传值**，`AppSettings.dailyAppCapMinutes`（默认 30）是**死设置** → 孩子在 App 里闲逛（花园/商店/我的）**完全不受限**，与「儿童专注 App」定位冲突。

**裁定（玄参，2026-09-23）**：

1. **计时口径**：只统计 **花园 / 商店 / 我的** 三个 tab 的**前台停留秒数**（常量 `kAppUsageCountingTabs = {2,3,4}`）；**今日(0)、成长(1) 不计**；专注链路（`/entry`、`/focus`、`/rest`）**不计**；App 切后台**暂停**；**跨天归零**（`dayKey` 变化即重置）。
2. **到点处置**：当天累计 ≥ `dailyAppCapMinutes`（默认 **30**，家长可调档位 **20 / 30 / 45**）后，**娱乐页（花园 / 商店 / 我的）不可进入** —— 弹**温和提示**（分因文案）并引导去「今日」开始专注；**今日 / 成长 / 专注链路永远可用** —— **绝不因总时长挡住专注**（**硬口径**，已被 QA 变异测试锁住）。
3. **判定单点**：`AntiAddictionService.isAppCapReached`（口径真源）与 `AppUsageService.isCapReached` **只有一处**实现 `seconds >= cap*60`，任何地方**不得再写第二份比较**（防「判定孪生」）。
4. **持久化**：**SharedPreferences**（当日日期 key + 累计秒数），**不升 `schemaVersion`**。理由：`settings` 表若加列会被 `saveSettings` 整行覆盖清空（隐蔽雷）；且 `DataManagementService.clearAll()` 已清全部 prefs，删除权闭环。
5. **异常防御分级**：时钟回拨（`now < baseAt`，环境输入）→ 增量 0 且**仍推进基准、不抛异常**；仅真正的不变量破坏（`storedSeconds < 0`）抛 `StateError`。`capMinutes <= 0` 暂无守卫（受档位约束，P2 遗留）。

**实现落点**：判定在 `ChildShellPage.onDestinationSelected` 拦截；计时由 `AppUsageController` + `AppUsageService.advance()` 纯函数（幂等、**无条件推进基准**）驱动。

## C18 成长 / 养护序列帧动效与花园背景音（2026-09-29）

**背景**：玄参交付 7 张开花静态图 + 向日葵 3 段成长帧 + 浇水/施肥效果帧 + 6 个 mp3（含 `background.mp3`）。工程接入过程中出现若干口径分歧与真机症状（画面闪烁、效果落在盆底、背景音不响），需钉死唯一真源。

**裁定（玄参，2026-09-29，来源=本会话玄参拍板 / 模拟器实测反馈）**：

## C24 专注入口时长档位三排 + 自由专注（2026-09-30）

**背景**：C23 落地后玄参反馈入口页两点——预设时长胶囊「点击时来回变动」手感不稳；底部「把手机横过来…」引导贴士多余。同时提出希望增加「自由」档。

**裁定（玄参，2026-09-30）**：

1. **档位固定三排等宽**：第一排 15-20-25 / 第二排 30-45-60 / 第三排 自由-自定义。**禁用 `Wrap` 等流式排布**——选中态会插入打勾图标 → 胶囊变宽 → 触发重排，表现为「点一下就跳位」。胶囊宽度由 `Expanded` 等分锁定，排数、列数固定。
2. **档位常量**：`kFocusDurationOptions = [15, 20, 25, 30, 45, 60]`（补 60 档）；「自定义」上限仍为 `kFocusDurationMaxMinutes = 180`，并继续受今日剩余额度收口（三处收口口径不变）。
3. **删除横屏引导贴士**：入口页不再出现任何「把手机横过来…」文案，直接点「开始专注」即可。
4. **「自由」档口径**：不预设时长、**不自动到时结算**，孩子自己决定何时结束；计时照走、产光、`lvl2` 报信（引擎 `planned` 改用 `kFocusDurationDefaultMinutes`(20) **仅用于推导 1/3 节奏**）、离席打断与每日额度 / 防沉迷约束**全部照旧**。路由 `/focus?minutes=0&dnd=..&free=1`，落库 `plannedMin=0`（`plannedMin==0` 在结算 / 成长项 / 完美日各处既有守卫天然兼容）。专注页表现为标签「自由专注」且**隐藏「/ 计划时长」**，不给倒计时压力。
5. **自由模式 ≠ 无约束**：`FocusEngine(freeMode: true)` 仅关闭「推进到 planned 自动结算」；`_checkWake` 的离席超时打断、结算侧额度硬截断均不受影响。默认 `freeMode = false`，定时专注行为完全不变。

## C26 花园干扰物「杂草 / 害虫」（2026-10-03）

**背景**：玄参提出花园玩法缺「日常麻烦」——已种植的花盆里随机长杂草 / 虫，孩子点掉即得阳光。核心诉求是「每天发生一次、点一下就清掉、有正反馈」，但**必须**同时确认三件事，否则会做出一个既没惩罚、又能无限刷阳光的假玩法：害处（是不是真玩法）、判定粒度（互斥 / 独立）、以及**会不会永久卡住成长**。

**裁定（玄参，2026-10-03 逐项拍板）**：

1. **有惩罚，且是「当天成长暂停」**（玄参选「有惩罚：存在期间当天成长暂停」）：杂草 / 害虫存在期间该株**当天不涨进度**，点掉图标即恢复。取「暂停」而非「减半」——孩子一眼看懂「不除草就长不大」，且惩罚当天即可消除，不制造长期挫败。
2. **每株每天独立 roll，杂草 / 虫可同时出现**：`kGardenWeedRate = 0.40` / `kGardenPestRate = 0.25` 各自独立判定、互不排斥（同一天同一盆可以既有草又有虫）。每盆差异大，花园更热闹。
3. **只在其出现的当天有效，次日重新 roll（玄参选「当天有效，次日 roll 自动消失」）**：这是「**不会永久卡住成长**」的唯一保证——最坏损失 = 1 天成长 + 1 阳光，死锁不可能出现。
4. **点图标即清除，不再弹确认卡**（玄参选「直接点图标即清除」）：🌿 / 🦗 浮标浮在盆区上、单独可点，点了立刻清除 + 在该花盆**正上方浮 1.2s 的提示**（「🌿 除草 +1 ☀」/「🦗 除虫 +2 ☀」）；点盆的其它区域仍弹养护卡。除草是**正反馈**，加确认卡只会让「点一下就没了」变成「点一下、再点一下」。
5. **奖励**：拔草 `kGardenWeedReward = +1` 阳光、除虫 `kGardenPestReward = +2` 阳光，走账本 `refType = 'plant_weed'` / `'plant_pest'` 入账（新增 refType 必须同步 `child_sunlight_history_page` 的 `_refLabels`，否则孩子端阳光来源一律显示「其他」）。
6. **落库 + 每株每天每种最多清 1 次**：`plants` 加 `weed_at` / `pest_at` / `weed_pest_roll_day` 三列（`schemaVersion` 13 → **14**，迁移补列 + 迁移测试）。清掉后**保留当日 roll 基准**，故同日再 tick 不会又长出来；次日零点 ≠ 昨日零点 → 自动重新 roll。
7. **emoji 占位**：`🌿` 杂草 + `🦗` 害虫（🦗 为标准「跳虫」类 emoji，最接近蝗虫；无专属 emoji）。正式美术图落地时只替换 `kGardenWeedEmoji` / `kGardenPestEmoji` 两个常量，UI 与回调签名不动。

**实现落点（真源）**：`prd_params.dart`（概率 / 奖励 / refType / emoji / 图标尺寸，单点收敛）、`plant.dart`（`weedAt` / `pestAt` / `weedPestRollDay` + `hasWeed` / `hasPest` / `hasPestOrWeed` + **哨兵三态 `copyWith`**）、`tables.dart`（`Plants` 三列）、`app_database.dart`（`schemaVersion 14` + `_ensureColumn` 幂等补列）、`plant_local_repository.dart`（`_toPlant` / `_toCompanion` 映射）、`plant_growth_service.dart`（`_rollWeedPest` 每日幂等 roll、`_advanceGrowth` 成长暂停且**照常推进幂等基准**、`clearWeed` / `clearPest` 入账）、`garden_pot.dart`（`_PestChip` 浮标）、`garden_page.dart`（`_clearPest` 处理器 + 花盆上方浮提示）、`child_sunlight_history_page.dart`（`_refLabels` 补两个 refType）。

## C30 开花奖励改「每日 8 点晨露」（2026-10-07，玄参拍板）

**背景**：玄参真机反馈「开花只奖两次，7 天培养花费远超奖励不合理」——旧口径 = 开花 instant 一条 + 48h 后第二段一条（C16/Batch1），满勤养护 19–30 天投入 475–750☀ vs 一次花期旧口径产出期望 ≈16.5☀（回报率 3.5%）。经济失衡，玄参拍板**改为「开花后每天早上 8 点产生一轮直至花谢」**。

**裁定**：
1. **登记口径**：开花时 `_enqueueBloomRewards` 登记 **instant 一条**（due = `bloomedAt`，即点花即领）+ **花期内每天 08:00 一条「晨露」**。首轮 = 开花**当天** 8 点（若开花时刻早于当天 8:00）否则**次日** 8 点；循环条件 `while (day.isBefore(bloomEnd))`（花期末尾之后到的 8 点**不登记**）。
2. **条数**：普通花期 3 天 → **2~3 条**晨露；精品（rare）花期 4.5 天 → **4~5 条**。加上 instant 共 3~6 条/次花期。
3. **金额与掉落**：**沿用原第二段档**（`_rollSecondPhaseReward` 单点复用）：普通 3–6☀ / 精英 6–10☀ + 原有小概率碎片/种子；**掉落即定奖（C16/v12）不变**——每条 pending 登记时即 roll 定死金额。
4. **花谢兜底照旧**：未领取的 pending 在花谢后由既有自动结算链路兜底到账。
5. **连带 bug 修复 F78**：旧豁免条件只看「此刻 status==bloomed」→ 旧轮未领 pending 在植物**重新开花**后被豁免自动结算、**永久滞留累积**（真机一次蹦出一排奖励图标）。修法 = 判定单点 `_isRewardCollectible(p, r)`：**盛开 且 `!r.dueAt.isBefore(p.bloomedAt!)`（同轮花期）**，两个条件缺一不可；`tickAll` 结算顺序（先推进后自动结算）不变。
6. `kBloomRewardDelayHours`（48h）**废弃**：代码无调用点，常量保留加废弃标注（下版可删）。
7. 经济校验：新口径一次花期总产出 ≈**30☀**（普通档期望），加上养护奖励（C26 除草除虫 +1/+2），投入回报回到可玩区间。
