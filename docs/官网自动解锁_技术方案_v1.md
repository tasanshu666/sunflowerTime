## 1. 工作来源

### 1.1 现状

Android 版买断制走「官网直供单包 + 激活码」，已完成并验证：

- 激活码 = `version(1B) + serial(4B 大端) + Ed25519 签名(64B)` = 69 字节 → Base64URL 92 字符；
- App 内置**公钥**，离线验签，**不联网、不问服务器**；
- 用户流程：官网付款 → 收到码（邮件/网页）→ 打开 App 付费页 → 粘贴 → 解锁。

### 1.2 现状的痛点

| 痛点 | 说明 |
|---|---|
| 码要人工搬运 | 92 字符，虽然在同手机上可复制粘贴，但跨设备（电脑付款、手机激活）就要手抄 |
| 码是可见凭据 | 用户能截图、能转发，**离线验签天生挡不住分享** |
| 转化有摩擦 | 付款与解锁之间存在一次「切 App + 粘贴」的中断 |

### 1.3 本方案要解决什么

让**付款与解锁之间零人工介入**：用户在 App 内点「解锁」→ 支付宝付款 → 自动回到 App → 已解锁。
激活码仍然存在（它是解锁凭据的技术载体），但**不经过用户的手，不出现在任何屏幕上**。

## 2. 目标与非目标

### 2.1 目标

1. App 内发起支付宝付款，付款成功后**自动解锁**，无需输入任何码。
2. 用户**看不到激活码**，因而不具备「截图转发」这个动作路径。
3. 断网、App 被杀、用户中途离开等异常场景下，**付款用户最终一定能拿到码**（补单闭环）。
4. 同一笔订单**重复领取返回同一枚码**（幂等）。
5. 服务端**不持有发码私钥**（见 §8.1），被攻破不导致无限伪造。
6. iOS 链路**零影响**（iOS 仍走 StoreKit，不引入任何网络请求）。

### 2.2 非目标（明确不做，避免范围蔓延）

- ❌ **不做用户账号体系**。无注册、无登录、无密码找回。
- ❌ **不做设备绑定**。换手机不锁死（家长换机频繁，绑定设备会炸口碑）。
- ❌ **不做多设备同时在线校验**。买断制不做并发限制。
- ❌ **不做订阅 / 自动续费**。本产品是永久买断。
- ❌ **不做撤销已解锁权益**。退款后 App 内权益保留（见 §9.3，这是离线方案的固有缺陷，靠购买页文案声明）。
- ❌ **不在网站上承载交易**。网站只展示价格与下载，付款必须发生在 App 内（见 §3.3）。
- ❌ **不做海外支付**。海外只走 App Store（$3.99）。

## 3. 硬约束（违反即方案作废）

### 3.1 合规：网站不得承载交易

备案时网站服务内容勾的是「企业门户 / 信息展示」，**没有也不可以勾「网络购物 / 在线交易」**
（后者触发 ICP 经营许可证，个体工商户办不到）。

因此：

- 🔴 **网站上不得出现购物车、下单按钮、网页收款码、支付宝网页支付**；
- 网站只允许：「产品介绍 + 价格展示 + APK 下载 + 隐私政策」；
- **所有付款必须发生在 App 内**（App 内调起支付宝 SDK 属于 App 支付，不属于网站经营）。

> 这条同时满足支付宝的审核要求（支付宝 APP 支付材料要求「网站有明确的经营内容和价格信息」）
> 与备案要求（网站不承载交易）。**两者靠「展示与交易分离」同时成立**。

### 3.2 安全：App 无法离线确认「付款成功」

用户从支付宝跳回 App 时携带的参数（`result`、`memo`、自定义 scheme 参数）**一律不可信** ——
Android 上任何应用都能构造一个 intent 声称「我付了 1 分钱」。

唯一可信的付款证明是：**支付宝服务端异步通知（`notify_url`）经 RSA2 验签后的结果**。

🔴 推论：**App 必须通过自己的服务端确认付款状态，不能直连支付宝**。
（直连查询需要把商户私钥塞进 APK，反编译即可提取 ⇒ 等于把收款权限公开。此路绝对禁止。）

### 3.3 前置条件（外部依赖，缺一不可）

| 前置 | 状态（2026-11-25） | 阻塞什么 |
|---|---|---|
| APP 备案通过 | 🟡 进行中 | 支付宝签约要求「网站已 ICP 备案」 |
| sunfocused.top 网站备案（个体户主体） | 🟡 进行中 | 同上；且**备案主体须与支付宝主体一致** |
| 云服务器（包年包月，剩余 ≥3 个月） | ✅ 已有 | 按量付费服务器不能用于备案 |
| 支付宝商户号 + APP 支付签约 | ⬜ 未申请 | 需备案下来后才能提交 |
| 支付宝开放平台应用（APPID） | ⬜ 未创建 | 签约后创建应用、配密钥、加「APP支付」功能 |

**当前阻塞点在备案**。备案通过前，本文档仅作设计存档，不可开工实现。

## 4. 系统总览

四个角色：

```
┌──────────────┐   ① 下单     ┌────────────────────┐
│              │ ───────────▶ │                    │
│   App        │              │  自建服务端        │
│  (Android)   │ ◀─────────── │  (1C1G 足够)       │
│              │   orderString│                    │
└──────┬───────┘              └─────┬──────┬───────┘
       │ ② 调起支付宝 SDK            │ ③ 异步 │ ④ 取码
       ▼                             │ 通知    ▼
┌──────────────┐                     │  ┌──────────────┐
│  支付宝 App   │ ────────────────────┘  │  码池文件     │
└──────────────┘    notify_url           │ (离线预签)    │
                                          └──────────────┘
       │ ⑤ 回跳（参数不可信，仅作"该去查了"的信号）
       └────────▶ App 调 ④ 领取
```

**核心思想**：服务端只做三件事 ——「签发订单号」「验支付宝回调」「从码池取一枚码」。
**它不做任何密码学运算**（私钥不在这里）。

## 5. 完整时序

### 5.1 正常路径（付款成功）

```
用户        App                 服务端                支付宝
 │           │                    │                     │
 │ 点「解锁」 │                    │                     │
 │──────────▶│ ① POST /order/create                     │
 │           │───────────────────▶│                     │
 │           │                    │ 生成 out_trade_no    │
 │           │                    │ 生成 claim_token     │
 │           │◀───────────────────│ 落库(status=pending) │
 │           │  {out_trade_no,    │                     │
 │           │   claim_token,     │                     │
 │           │   order_string}    │                     │
 │           │                    │                     │
 │           │ ② 安全区存 pending{out_trade_no,claim_token}
 │           │ ③ PayTask.pay(order_string)              │
 │           │──────────────────────────────────────────▶│
 │ 付款      │                    │                     │
 │───────────┼────────────────────┼────────────────────▶│
 │           │                    │ ④ POST /alipay/notify│
 │           │                    │◀────────────────────│
 │           │                    │ 验签 + 校验金额      │
 │           │                    │ 标 status=paid       │
 │           │                    │ 回 "success"         │
 │           │◀── 支付宝回跳 ──────┼─────────────────────│
 │           │ (参数不可信)        │                     │
 │           │ ⑤ GET /order/redeem?out_trade_no&claim_token
 │           │───────────────────▶│                     │
 │           │                    │ 校验 claim_token     │
 │           │                    │ 从码池取一枚         │
 │           │◀───────────────────│ 绑定 out_trade_no    │
 │           │  {redeem_code, serial}                   │
 │           │                    │                     │
 │           │ ⑥ RedeemCodeVerifier.verify(码) ← 现有代码零改动
 │           │ ⑦ 清 pending，界面解锁                    │
 │ 已解锁 ✅  │                    │                     │
```

### 5.2 异常路径（必须实现，缺一即差评）

| 场景 | 处理 |
|---|---|
| 用户付款后直接杀掉 App | 下次启动读安全区 `pending` → 自动调 ⑤ 领取 |
| 回跳时无网络 | ⑤ 失败 → 保留 `pending`，界面提示「已付款？点这里重新领取」 |
| 支付宝回调晚于 App 领取（时序竞态） | ⑤ 返回 `202 pending` → App 每 2s 重试最多 15 次（30s），仍失败则转人工 |
| 服务端崩了几天 | 用户手里的 `pending` 一直在，恢复后自动补 |
| 用户换了手机 / 重装 App | 安全区数据丢失 → `claim_token` 丢失 → **必须有人工兜底**（见 §9.4） |
| 码池耗尽 | 下单前先查池，空则**拒绝下单**并提示联系客服（绝不收款后无码可发） |

## 6. 接口契约

### 6.0 通则

- 协议：**HTTPS 强制**，HTTP 一律 301 或直接拒绝。
- 域名：`api.sunfocused.top`（与主站分离，便于单独限流与监控）。
- 编码：UTF-8；请求/响应体均为 `application/json`（支付宝回调除外，见 §6.3）。
- 版本：路径前缀 `/v1`。破坏性变更升 `/v2`，旧版至少保留 12 个月。
- 响应统一外层：

```json
{ "ok": true,  "data": { ... } }
{ "ok": false, "error": "ORDER_NOT_FOUND", "message": "订单不存在" }
```

- 🔴 `message` **只用于日志与排障，App 不解析**。App 一律按 `error` 分支处理。
- 每个响应带 `X-Request-Id`（UUID），App 出错时可展示给用户报给客服。

### 6.1 `POST /v1/order/create` —— 创建订单

App → 服务端。**无登录态**，靠限流防滥用（§8.3）。

**请求**

```json
{
  "platform": "android",
  "app_version": "1.1.0+2107",
  "device_hash": "sha256(androidId + 固定盐)[0:32]"
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `platform` | string | ✅ | 固定 `"android"`。服务端遇到非 android 直接拒绝（iOS 不走此链路） |
| `app_version` | string | ✅ | 形如 `1.1.0+2107`，用于灰度与排障 |
| `device_hash` | string | ✅ | 设备指纹哈希。**仅用于限流与风控，不用于绑定权益** |

> `device_hash` 刻意不存原始 androidId —— 拿不到原始值就无法跨库关联用户，
> 符合隐私政策里「不收集设备唯一标识」的表述。

**响应 200**

```json
{
  "ok": true,
  "data": {
    "out_trade_no": "SF2611257K3M9QXA",
    "claim_token": "9f2c8e14d7b64a0f8c3e5d21a6b9f472",
    "order_string": "app_id=2021...&biz_content=...&sign=...",
    "amount": "49.90",
    "expires_in": 900
  }
}
```

| 字段 | 说明 |
|---|---|
| `out_trade_no` | 商户订单号。格式见 §6.1.1。≤ 64 字符（支付宝硬限制） |
| `claim_token` | **领取凭据**，32 位小写 hex（16 字节随机）。App 必须存安全区 |
| `order_string` | 服务端用**支付宝应用私钥** RSA2 签名后的下单串，App 直接喂给支付宝 SDK |
| `amount` | 金额（元，两位小数字符串），**服务端定死 49.90**，不接受客户端传值 |
| `expires_in` | 订单有效期（秒）。超时未付则作废，用户需重新下单 |

**错误**

| error | HTTP | 场景 | App 应做什么 |
|---|---|---|---|
| `POOL_EXHAUSTED` | 503 | 码池见底 | 提示「暂时无法购买，请联系客服」，**不调起支付宝** |
| `RATE_LIMITED` | 429 | 触发限流 | 提示稍后再试 |
| `SERVER_ERROR` | 500 | 内部错误 | 提示稍后再试 |

#### 6.1.1 `out_trade_no` 格式（固定，不可改）

```
SF + yyMMdd + 8 位大写 base32 随机
例：SF2611257K3M9QXA
```

- 总长 16 字符，远小于 64 上限；
- **不含任何用户信息**（无手机号、无设备号、无 serial），避免泄露；
- 前缀 `SF` 便于在支付宝商户后台筛出本产品的订单。

### 6.2 `GET /v1/order/redeem` —— 领取激活码

App → 服务端。**这是全链路最关键的一个接口**，幂等性必须严格保证。

**请求（query）**

```
GET /v1/order/redeem?out_trade_no=SF2611257K3M9QXA&claim_token=9f2c8e14...
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `out_trade_no` | ✅ | 下单时拿到的订单号 |
| `claim_token` | ✅ | 下单时拿到的领取凭据。**这是唯一身份凭据** |

**响应 200（已发码）**

```json
{
  "ok": true,
  "data": {
    "status": "issued",
    "redeem_code": "AQAA...（92 字符，Base64URL，无空格）",
    "serial": 1024
  }
}
```

**响应 202（已付款，回调未到 / 未发码）**

```json
{ "ok": true, "data": { "status": "pending" } }
```

> 🔴 **202 与 200 的区分是硬要求**。App 见到 `pending` 必须**重试**而不是报错 ——
> 支付宝回调通常 1–3 秒到达，但极端情况下可能滞后几十秒。

**响应 200（未付款但订单存在）**

```json
{ "ok": true, "data": { "status": "unpaid" } }
```

**错误**

| error | HTTP | 场景 | App 应做什么 |
|---|---|---|---|
| `ORDER_NOT_FOUND` | 404 | 订单号不存在 / 已过期清理 | 提示联系客服 |
| `CLAIM_TOKEN_MISMATCH` | 403 | 凭据不匹配（伪造或串号） | 提示联系客服，**不重试** |
| `POOL_EXHAUSTED` | 503 | 已付款但码池空（极少见，因下单前已查） | 转人工，**记录 order id 到日志** |
| `RATE_LIMITED` | 429 | 重试过密 | 指数退避 |

**幂等规则（不可协商）**

1. 同一 `out_trade_no` 的 `redeem` 请求，**无论调用多少次，永远返回同一枚码、同一 serial**；
2. 发码动作必须在**数据库事务**内完成：`UPDATE orders SET redeem_code=?, serial=? WHERE out_trade_no=? AND redeem_code IS NULL`，受影响行数为 0 时回头重读已发的码返回；
3. 🔴 **禁止「先查后写」两步**——两个并发请求会各发一枚码，用户白得一单。

### 6.3 `POST /v1/alipay/notify` —— 支付宝异步通知

支付宝 → 服务端。`application/x-www-form-urlencoded`。

**这是唯一可信的付款证明来源。** 服务端必须完成以下五步，缺一不可：

1. **验签**：用**支付宝公钥**（不是应用公钥）对通知参数做 RSA2 验签；
2. **校验 `app_id`**：必须等于自己的 APPID（防止别人的支付宝通知打进来）；
3. **校验 `total_amount`**：必须精确等于 `49.90`（字符串比较，不要转 float）；
4. **校验 `trade_status`**：仅 `TRADE_SUCCESS` 与 `TRADE_FINISHED` 视为付款成功；
5. **校验 `seller_id`**：必须等于自己的 PID（防串商户）。

**关键字段**

| 字段 | 用途 |
|---|---|
| `out_trade_no` | 定位自己的订单 |
| `trade_no` | 支付宝交易号，**必须存**（退款与人工对账都靠它） |
| `trade_status` | 见上 |
| `total_amount` | 金额校验 |
| `gmt_payment` | 实际付款时间 |
| `sign` / `sign_type` | 验签（`RSA2`） |

**响应**：**纯文本 `success`**（不带引号、不带 JSON、不带 BOM）。
返回其他任何内容，支付宝都会认为处理失败并重试。

> 支付宝在 **25 小时内最多重试 8 次**，间隔递增。因此 notify 处理逻辑**必须幂等**：
> 同一 `out_trade_no` 重复通知只能标记一次已付款，不可重复发码（发码本身在 redeem 里，
> 但标记动作也要幂等，否则会覆盖已绑定的码）。

### 6.4 `GET /v1/pool/status` —— 码池余量（内部用）

```json
{ "ok": true, "data": { "available": 812, "issued": 188, "total": 1000 } }
```

- 不需要鉴权，但**不返回任何码内容**；
- 供监控程序每 6 小时拉一次，`available < 10%` 时发邮件告警。

### 6.5 错误码总表

| error | HTTP | 含义 | App 行为 |
|---|---|---|---|
| `POOL_EXHAUSTED` | 503 | 码池耗尽 | 转人工，不重试 |
| `ORDER_NOT_FOUND` | 404 | 订单不存在 | 转人工 |
| `CLAIM_TOKEN_MISMATCH` | 403 | 凭据错误 | 转人工，不重试 |
| `BAD_REQUEST` | 400 | 参数缺失/格式错 | 记录日志，不重试 |
| `RATE_LIMITED` | 429 | 限流 | 指数退避 |
| `SERVER_ERROR` | 500 | 服务端异常 | 指数退避 |

## 7. 数据模型（服务端）

```sql
-- 订单表
CREATE TABLE orders (
  out_trade_no   TEXT PRIMARY KEY,          -- SF2611257K3M9QXA
  claim_token    TEXT NOT NULL,             -- 32 位 hex
  device_hash    TEXT,                      -- 仅风控用
  app_version    TEXT,
  amount         TEXT NOT NULL,             -- '49.90'（字符串，不做浮点运算）
  status         TEXT NOT NULL,             -- pending | paid | issued | void
  alipay_trade_no TEXT,                     -- 支付宝交易号，paid 后写入
  gmt_payment    TEXT,                      -- 支付宝付款时间
  redeem_code    TEXT,                      -- 发出的激活码（issued 后写入）
  serial         INTEGER,                   -- 与 redeem_code 一一对应
  created_at     TEXT NOT NULL,
  paid_at        TEXT,
  issued_at      TEXT
);
CREATE INDEX idx_orders_status ON orders(status);
CREATE INDEX idx_orders_trade  ON orders(alipay_trade_no);

-- 码池表（由离线文件导入，一次性）
CREATE TABLE code_pool (
  serial       INTEGER PRIMARY KEY,
  code         TEXT NOT NULL UNIQUE,
  status       TEXT NOT NULL,               -- available | issued | void
  out_trade_no TEXT,                        -- issued 时写入
  issued_at    TEXT
);
CREATE INDEX idx_pool_status ON code_pool(status);
```

**为什么 `amount` 用字符串**：`49.90` 用 float 会变成 `49.899999...`，与支付宝回传的
`"49.90"` 比较必然不等 ⇒ 全量订单被判定「金额不符」而拒绝。**必须字符串精确比较**。

## 8. 安全设计

### 8.1 🔴 私钥不上服务器（本方案最重要的安全决策）

| 做法 | 服务器被攻破的后果 |
|---|---|
| ❌ 服务器持发码私钥 | 攻击者可**无限伪造**激活码，且您无法吊销（离线验签没有吊销机制） |
| ✅ 服务器只持**离线预签好的码池** | 攻击者最坏拿走池里**未发出的存货**（如剩 800 枚），损失有上限，且**无法继续伪造** |

**因此：发码私钥永远只在您的本机**，服务器上只有已经签好名的码。

码补货流程（纯手工，建议每月一次或 `available < 20%` 时）：

```bash
# 在本机执行：--out 直接写机器可读 JSON，stdout 只留一行摘要（码不进终端日志）
dart tool/issue_redeem_code.dart --serial 1001 --count 1000 \
  --private-key "<私钥种子>" --out build/codes_1001.json
```

🔴 **用 `dart tool/...` 直调，不要用 `dart run tool/...`**。两者生成的 JSON 完全一致，
但 `dart run` 会由 Dart SDK 额外往 stdout 打一句 `Running build hooks...`，破坏
「终端只有一行摘要」的干净输出。

✅ **已补齐（2026-11-26）**：`tool/issue_redeem_code.dart` 已支持 `--out <path>`，
输出 UTF-8 JSON 数组（`indent: 2`，父目录自动创建，`code` 为**不含分组空格的 92 字符
Base64URL 原码**，`-` 原样保留）。完整格式与用法见 `tool/issue_redeem_code.dart`
顶部的 `/// ## 用法` 注释；不带 `--out` 时仍逐字节保持旧的 stdout 分组文本输出。

```json
[
  { "serial": 1001, "code": "AQAA...(92字符)" }
]
```

> 不带 `--out` 的旧用法保留给人工抄写/测试码；**补货一律走 `--out`**，
> 避免从终端输出里抠 1000 行字符串。

补货落地步骤：

1. 本机生成 JSON → `scp` 到服务器（`/tmp`，权限 600）；
2. 导入 `code_pool` 表（`INSERT OR IGNORE`，重复导入不会重复消耗）；
3. **立即删除**本机与服务器上的临时文件；
4. 记账：本轮发放的 serial 区间写入台账（建议新建 `docs/激活码发放台账.md`，防区间重叠）。

> 🔴 补货用的 `serial` 区间必须与已发出区间**连续且不重叠**。当前建议：
> **对外正式发码从 1001 起**（serial 1/2/3 是历史测试码，已公开，保留自用）。
> 启用本方案 B 之后，手动码渠道仍保留，两渠道共用同一个 serial 空间，**务必记账**。

### 8.2 支付宝密钥的两套，不要混

| 密钥 | 在哪 | 用途 |
|---|---|---|
| **应用私钥**（RSA2，2048） | 服务端 | 给下单串签名、调退款/查询接口 |
| **应用公钥** | 传到支付宝开放平台 | 让支付宝验证您的请求 |
| **支付宝公钥** | 服务端 | 验证支付宝的回调与响应 |

🔴 **应用私钥 ≠ 发码私钥**。两者毫无关系：前者是支付宝体系的密钥（泄露可伪造下单、可调退款），
后者是我们的 Ed25519 发码密钥（泄露可伪造激活码）。**绝不能把发码私钥放到服务器上**。

> 注意：应用私钥放在服务器上是**不可避免**的（下单必须它签名）。它的风险边界是
> 「可伪造下单+可调退款」，但不影响激活码的不可伪造性。这是两个独立的风险域。

### 8.3 防刷与限流

| 接口 | 限制 |
|---|---|
| `/order/create` | 单 IP 每 10 分钟 ≤ 5 次；全局每分钟 ≤ 60 次 |
| `/order/redeem` | 单 `claim_token` 每分钟 ≤ 10 次；单 IP 每分钟 ≤ 30 次 |
| `/alipay/notify` | 不限制（支付宝来源），但验签失败即丢并记录 |

`/order/create` 被刷的后果：订单表膨胀 + 码池未被消耗（不会提前发码），
所以**危害有限**，不必过度设计。真正要防的是 `/order/redeem` 被暴力猜 `claim_token`
—— 16 字节随机空间（2^128），暴力不可能成功，限流只是防拖库式探测。

### 8.4 其他

- 服务端**不记录**用户 IP 到业务表（仅在 Nginx access log，保留 7 天）；
- 日志中 `claim_token` 与 `redeem_code` **打码**（只留前 4 后 4），防日志泄露；
- 数据库每日备份到本地磁盘 + 异地一份，保留 30 天；
- 服务器仅开放 80/443，SSH 改端口 + 禁用密码登录（只允许密钥）。

## 9. 三条硬要求（真实支付的血泪，不可省）

### 9.1 幂等

见 §6.2。核心：**发码必须在单条 SQL 的原子更新里完成**，不能「先 SELECT 再 INSERT」。

### 9.2 补单

**定义**：用户付了钱但没拿到码，系统必须能自动或半自动补上。

三条补单通道，按优先级：

1. **App 自动补**：`pending` 存在安全区，App 每次启动/回前台/网络恢复时自动调 `redeem`；
2. **用户手动触发**：付费页常驻一行「已付款但未解锁？点此重新领取」；
3. **人工兜底**：用户重装 App / 换机导致 `claim_token` 丢失，只能走客服。客服凭
   **支付宝账单里的商户订单号**（用户在支付宝「账单详情」能看到 `out_trade_no`）
   在后台手动发码。

> 🔴 第 3 条要求服务端必须有一个**内部后台页面**（哪怕是最简陋的 HTML 表单）：
> 输入 `out_trade_no` → 显示订单状态 → 一键发码。**没有这个页面，客服就是废的。**

### 9.3 退款

- 退款走支付宝 `alipay.trade.refund`（需应用私钥，服务端持有）；
- 退款成功后：订单 `status = 'void'`，对应 `code_pool.serial` 标记 `void`；
- 🔴 **已激活的用户，App 内权益无法撤销**（离线验签方案天生没有吊销通道）。
  这一点必须在**购买页文案**里写明：「数字商品一经激活不支持退款」。
- 支付宝侧：退款**不退服务费**（0.6% 那部分白付）。

### 9.4 换机与重装（当前方案的真实缺口）

**问题**：票据存在 `FlutterSecureStorage`（Android 上是 EncryptedSharedPreferences），
**不参与云备份**。用户换手机或卸载重装 ⇒ 票据与 `pending` 一起消失。

**缓解方案（必须实现其一）**：

- ✅ **推荐**：付费页提供「恢复购买」入口，用户输入**当初那枚激活码**重新激活。
  前提是官网售出时把码**同时发到邮箱**（用户有据可查）。
- ⬜ 备选：让用户在 App 内看到自己的 `serial`（已实现，付费页显示「激活码 #1024」），
  配合客服按 serial 查 `code_pool` 反查出码。
  ⚠️ 但该显示只对**已解锁**用户可见，重装后是免费态 ⇒ 看不到 ⇒ 此路实际走不通。

🔴 **结论：官网发货必须带邮件**，邮件里要有码。这是换机场景的唯一救命稻草。

### 10.3 🔴 iOS 隔离（最容易翻车的地方）

项目当前**没有一个原生支付 SDK 依赖**，iOS 包干净是上架审核的既得优势。引入支付宝 SDK 必须做到：

1. **Android-only 依赖**：Gradle 里 `implementation` 而非 Flutter plugin 全局引入；
   若用 Flutter 插件，必须在 `pubspec.yaml` 里确认它不会把 iOS 二进制链进 `Runner.app`；
2. **iOS 侧代码不引用**：`alipay_bridge.dart` 用 `Platform.isAndroid` 硬门控，且 iOS 分支不 import 任何支付宝符号；
3. **上架前实测**：`flutter build ipa` 后，用 `otool -L Runner.app/Runner` 确认**没有** AlipaySDK 动态库；
   `grep -r "alipay" ios/` 必须零命中（对齐本项目既有做法）；
4. **隐私政策同步更新**：若 SDK 采集设备信息，需在隐私政策第三方清单中列明。

> 风险等级：**高**。若做不到上述隔离，宁可放弃 B 方案 —— 为了 Android 的转化率
> 而污染 iOS 上架，是净亏。

支付宝 SDK 约 **+5~8 MB**（当前 arm64 包 285 MB，影响约 2%）。可接受。

## 12. 验收标准

实现完成后必须逐条实测：

| # | 场景 | 期望 |
|---|---|---|
| 1 | 正常付款 | 付款成功 → 3 秒内自动解锁，用户未接触任何码 |
| 2 | 同一订单连点 10 次「领取」 | 返回同一枚码，`code_pool` 只消耗 1 枚 |
| 3 | 未付款就调 `redeem` | 返回 `unpaid`，App 不解锁 |
| 4 | 伪造 `claim_token` | 返回 403，不解锁 |
| 5 | 付款后立刻杀 App，重开 | 自动补单成功解锁 |
| 6 | 付款后断网，恢复网络 | 自动补单成功解锁 |
| 7 | 支付宝回调延迟 30 秒（人为拖慢） | App 轮询期间显示「正在确认付款」，最终解锁 |
| 8 | 码池置空后下单 | 返回 503，**不调起支付宝**，用户不会被扣款 |
| 9 | 重放攻击（重发一份旧 notify） | 幂等，不重复标记、不重复发码 |
| 10 | 金额篡改（notify 里 total_amount=0.01） | 拒绝处理，记录告警 |
| 11 | iOS 包体检查 | `otool -L` 无 AlipaySDK，`grep -r alipay ios/` 零命中 |
| 12 | 服务器拿不到发码私钥 | `grep -r "BEGIN PRIVATE" /srv` 零命中（人为确认） |

## 13. 风险与决策记录

| # | 风险 | 等级 | 处置 |
|---|---|---|---|
| R1 | 支付宝 SDK 污染 iOS 包体 | 🔴 高 | §10.3 四条隔离措施；做不到则放弃 B |
| R2 | 备案/签约延期，链路无法联调 | 🟡 中 | 本方案可先写服务端骨架 + 沙箱（支付宝有沙箱环境） |

| R4 | 换机/重装丢权益 | 🟡 中 | §9.4：邮件发码 + 恢复购买入口 |
| R5 | 单人维护成本（服务器要长期活着） | 🟡 中 | 1C1G + SQLite，运维量 ≈ 每月 1 小时；但**服务器挂了就卖不了**，需接受 |
| R6 | 支付宝审核不通过（材料/网站内容） | 🟡 中 | 网站只展示不交易（§3.1），材料一次交齐 |
| R7 | 用户付款后客服响应不及时 | 🟡 中 | §9.2 内部后台必须做，否则补单全靠人肉 |

### 已定决策（2026-11-26，玄参拍板）

| 事项 | 决策 | 理由 |
|---|---|---|
| A 方案（deep link 一键填码） | **不做** | App 已有剪贴板读取，只省一次点击；且 B 上线后 A 完全冗余（B 是根本没有码）。若 B 因 iOS 关卡夭折再补，一天可做完 |
| 手动输码入口 | **保留**，B 上线后降为次要入口 | 客服补发 / 换机恢复（邮件里的码）/ 服务端故障兜底，三个场景都要它 |
| 服务器技术栈 | **Python 3 + FastAPI + SQLite** | 支付宝官方服务端 SDK 支持 Python（签名验签不用自己写，这是支付代码最易错的部分）；FastAPI 自带 `/docs` 交互文档，玄参不懂服务器也能点着测；代码可读性好；SQLite 单文件备份。🔴 不用 Dart：官方无 Dart SDK，自己实现 RSA2 风险过高；不用 Go：同样无官方 SDK |
| 沙箱 | **先行**，不等备案 / 商户号 | 官方原文：沙箱「无需具备所需的商业资质，无需绑定和开通产品」。现在即可联调 |
| 推进顺序 | 服务端沙箱跑通 → 备案下来 → 商户号签约 → **最后**才动 App | 服务端阶段完全不碰 App 代码，因此没有 iOS 包污染风险；即使最后 iOS 那关过不去，服务端与客服后台仍可配合手动发码继续使用 |
