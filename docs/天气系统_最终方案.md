## 1. 一页结论

### 1.1 一句话

花园每天（本地自然日）从 **9 种**天气里落一种：**80% 温和 + 20% 极端**。温和只改三个乘数（`g` 自然生长 / `w` 浇水 / `f` 施肥）且**净中性**；极端（干旱 / 大风 / 极寒 / 暴雨）要孩子**花 10☀ 买一件道具 + 做一个动作**才不受罚，不做的代价是 −1% 进度/动作/天，且**只罚已经过完的日子**。

### 1.2 六个必须记住的数

| 数 | 值 | 含义 |
|---|---|---|
| 极端总概率 | **20.00%** | 4 种摊：**7 / 5 / 5 / 3**（干旱 / 大风 / 极寒 / 暴雨） |
| 温和总概率 | **80.00%** | 5 种摊：20/14/18/14/14，加权 `g` **精确 = 1.0000** |
| `E[g]` | **0.9280** | 天气对自然生长的净效应 = **−7.2%**（极端的代价锁在这里） |
| `E[w]` / `E[f]` | **1.0700 / 0.9514** | 温和的雨天/旱天把两个通道拉回来，孩子端感知不到 |
| 判定基准成本 | **19.50☀/盆/天**（2 水 1 肥 + 道具分摊） | 4 盆 = **78.0☀** = 低龄最紧档 88☀ 的 **88.6%** ✅ |

## 2. 玄参 3 项裁定的落点

### 2.1 裁定 1：温和清单加「小雨」

**玄参原话**：「微风、阳光明媚，阴天、多云**等等你自己定义就好**」。

**v6 的判断是错的，本版删除**。v6 §3 里写了「玄参给的温和清单是 4 种，加小雨属于扩大授权范围，不采纳」——这是把开放列举当成了封闭清单。正确读法：「等等」= 温和池的内容归我定义，只受两条软约束（`g` ∈ ×0.93~×1.06、加权 ≈ 1.00）和一条硬约束（合计 80.00%）管。

**落点**：温和 5 种 = 阳光明媚 20 / 微风 14 / 多云 18 / 阴天 14 / **小雨 14**，合计 80.00%。小雨的定位是**温和偏正面**（`g` ×1.03），它同时是**唯一一个会压低浇水额度的温和日**（额度 3 → 1），这是它存在的经济意义：给「雨水代劳」一个 14% 的日常出口，而不是只在 3% 的暴雨里出现。

### 2.2 裁定 2：极端 20% 摊到极端池，温和 80% 摊到 5 种

**落点**：见 §3 全表。极端池经**裁定 5** 收敛为 **4 种 = 7 / 5 / 5 / 3**（干旱 / 大风 / 极寒 / 暴雨），温和 5 种 = 20 / 14 / 18 / 14 / 14。两边的权重**直接就是有效概率**。

⚠️ **注意本版做了一处简化**：v6 为了让干旱名义 5.15% 落到有效 5.00%，造了一套软约束搬迁机关。加小雨之后，温和加权 `g` 只要权重选对就**精确 = 1.0000**（20×1.05 + 14×1.02 + 18×0.96 + 14×0.93 + 14×1.03 = 80.00），**机关全部拆掉**。测试断言直接写权重本身，不再有「名义值 / 有效值」两套数。

### 2.3 裁定 3：4 盆缺口改口径

**玄参原话**：「养不过来不需要提示，还有其他机制」。

**落点**：
- 经济判定基准从「3 水 1 肥（25☀）」改成 **「2 水 1 肥」（19.50☀/盆/天，4 盆 = 78.0☀ = 88.6%）**。
- 「4 盆满养护 94.6☀」**保留在表里，如实标注超出 6.6☀/天**，不再包装成「刚好打平」。
- 补一条出路：**Lv.5 浇水折扣（5→4☀）后 4 盆满养护 = 84.1☀ = 95.5%**，Lv.5 + Lv.10 = 80.1☀ = 91.0%。所以「4 盆 + 满养护」不是做不起，是**要等级**。

### 2.4 裁定 4：反馈只给 ✅ + 👍，不给阳光

**落点**：见 §9.5 / §9.6。全文删除「给阳光 / 给碎片 / 给进度」的所有表述。「连续照顾天数」写进 §9.10「后续可加」，**不进本版 i18n、不进工程量**。

### 2.5 裁定 5：删「高温」极端日型

**玄参裁定**：删除「高温」极端天气，**只保留干旱**；极端总概率 20% 不变。

**落点**：
- 高温整行删除（`g×1.15`、浇水额度 4、`weather.heat` 全部下线）。
- 腾出的 4.00% **只补给干旱（5→7）、大风（4→5）、极寒（4→5）**，合计仍是 `7+5+5+3 = 20.00%`。
- 🔴 **暴雨 3% 与小雨 14% 一个不动**：这两个是成本表里**唯二有额度截断**的日型（暴雨额度 0、小雨额度 1），一动它们，两张成本表就得全面重算。按上面的分法分完，**两张成本表一行都不用改**（浇水次数期望仍是 2.630 / 1.800 / 0.970）。
- **干旱 `g = ×0.20` 不动**：它是难度旋钮，动要玄参点头。权重从 5% 涨到 7% 只是更常出现，单价不变。

## 3. 新日型总表（**9 种**，权重即有效概率）

### 3.1 生成方式（确定性纯函数）

```
dayKey = "yyyy-MM-dd"（孩子设备本地自然日）
seed   = FNV-1a 32bit(dayKey + "|weather|v1")     // 固定 salt，跨版本不得改动
u      = seed / 2^32                               // [0,1)
按累计权重落桶
软约束（纯函数，不改 u 的确定性）：
  ① 同一日型不连续出现 3 天 → 命中则顺延到下一桶（回绕）
  ② 同一种极端不连续出现 2 天 → 命中则顺延到下一桶（回绕）
```

**禁止 `Random`**。玄参要的「无规律」由哈希扩散提供，同一台设备同一天永远同一种天气（可重放、可断言）。

> 🔴 **约束 ② 的原始表述已作废（2026-11-02 实测翻案）**：原文写的是「**任何**两种极端不得连续」，但它在数学上与「极端占 20%」**互斥** —— 稳态解 `e = p / (1 + p) = 0.20 / 1.20 = **16.67%**`，被挡下的极端永远补不回来，实测只有 16.45%。玄参当日的裁定是「**极端天气的 20% 概率保持不变**」，因此让步的是约束而不是概率：**收窄为「同一种极端不得连续两天」**（干旱 → 干旱 要改；干旱 → 暴雨 允许）。
>
> 实测（2000-01-01 ~ 2099-12-31，36525 天）：**极端合计 20.31%**，9 种日型最大偏差 **0.71pp**；「同型极端相邻」**0 次**、「不同极端相邻」**1701 对**。放宽前还带一个畸形：被挡下的极端全部回绕到第 0 桶 ⇒ **晴天实测 23.03%**（比设计多 3 个点，孩子会觉得「怎么老是晴天」）；收窄后晴天回到 **19.29%（−0.71pp）**。
>
> 为什么不采用「挡下后顺延到明天还债」：那会造出「极端、温和、极端、温和」的规律交替，与玄参要的「无规律」正相反。

### 3.4 三个派生量

```
极端加权 g = (7×0.20 + 5×0.95 + 5×0.85 + 3×0.80) / 20 = 12.80 / 20 = 0.6400
E[g] = 0.80 × 1.0000 + 0.20 × 0.6400 = 0.9280     ← 天气净拖慢自然生长 7.2%
E[w] = (20×1.10 + 14×1.00 + 18×0.95 + 14×0.90 + 14×0.65 + 7×3.00 + 5×0.90 + 5×1.10 + 3×0.40) / 100
     = (74.80 + 32.20) / 100 = 1.0700
E[f] = (20×1.05 + 14×1.00 + 18×0.98 + 14×0.95 + 14×0.90 + 7×0.60 + 5×0.80 + 5×1.50 + 3×0.30) / 100
     = (78.54 + 16.60) / 100 = 0.9514
```

**为什么不让 `E[g] = 1.0000`**：极端必须真的慢一点，否则「20% 极端」只是装饰。−7.2% 摊到 30 天首花周期上是 +2.3 天，孩子感知不到，但足以让「不看天气」有真实代价。

**⚠️ 删高温的连带效应（必须知道）**：高温（`g×1.15`）是**唯一一个加快生长的极端**，删掉它之后 `E[g]` 从 0.9520 掉到 0.9280，**天气整体变慢 2.4 个百分点**。这不是算错，是裁定的必然结果；周期基准因此按 `0.9520 / 0.9280 = 1.0259` 等比拉长约 2.6%。

### 3.5 温和「有正有负、算一个随机因子」怎么落地

- 五种温和里 **2 正 3 负**（×1.05 / ×1.03 对 ×0.96 / ×0.93 / 小雨的 `w`×0.65 是**好事**）。
- 但**加权后净中性**（1.0000），所以「天气是随机因子」而不是「天气是税」。
- **温和只改乘数、不改额度**；额度只由极端（+ 小雨）改写 —— 这条保证「温和日孩子永远能做满 3 水 1 肥」的肌肉记忆不被打破。

### 3.6 为什么买遮阳棚了还是长得慢

`g` 是当日的**基础成长乘数**，买道具**只免掉「道具类惩罚 −1%」，不恢复 `g` 拖累**。这是有意的：天气的体感要「看得见」，如果 10☀ 一买就回到晴天速度，天气就退化成了一个每日 10☀ 的过路费。孩子的正确直觉是「干旱天本来就长得慢，我浇了水、搭了棚，至少不会倒退」。

## 4. 道具系统（4 件，10☀/天/园）

### 4.1 四件道具

| 道具 | refType | 价格 | 覆盖天气 | 作用 |
|---|---|---|---|---|
| 遮阳棚 | `shelter_shade` | 10☀ | **干旱**（高温已删，此棚现只服务 1 种天气，但仍必须保留） | 免掉该日的道具类惩罚 |
| 遮雨棚 | `shelter_rain` | 10☀ | 暴雨 | 同上 |
| 挡风板 | `shelter_wind` | 10☀ | 大风 | 同上 |
| 保温棚 | `shelter_warm` | 10☀ | 极寒 | 同上 |

**refType 一分为四（终裁）**：一个 `refType='shelter'` + `refId` 区分，会让「同一园同一天买两种棚」在账本里无法区分；四个 refType 则天然一行一物，且 `countByRefTypeAndRefIdOnDay` 直接可用。

### 4.2 统一规则

1. **按园买，不按盆买**：`refId = 'garden'`。一棚护全园，这是 10☀ 定价能成立的前提。
2. **当天买当天有效**：账本按自然日切分，次日自动失效，不需要退货流程。
3. **买棚 = 覆盖该日的道具类惩罚**，不覆盖动作类惩罚（干旱的「浇水 ≥ 1」、暴雨的「施肥 ≥ 1」仍要做）。
4. **不买也能过**：不买 = 该日吃 −1% 进度。**不阻断任何操作**，孩子不会被卡死。
5. **额度用尽仍可买**：棚不占浇水/施肥额度。

### 4.3 零迁移

- 只在既有阳光账本写一行 `refType='shelter_<kind>'`、`refId='garden'`、`amount=-10`。
- **零 `schemaVersion` 变更，零新增字段**。
- 🔴 **禁止给 `SunlightRepository` 增加任何接口方法**：全仓约 45 处测试假实现，加方法 = 45 个文件编译红。道具判定一律用既有 `countByRefTypeAndRefIdOnDay(refType, refId, day)`。

### 4.4 九条边界

> 🔴 **A2 期提示（2026-11-03）**：本节第 **8** 条与第 **9** 条**已作废**，A2 起不再实现 —— 理由与落点见文末 **《附录 A · A2 期裁定登记》**。第 1~7 条继续有效（第 8、9 条已作废）。

1. 一天最多买 4 件（4 种各 1 次），重复买直接拒（当日已有该 refType 记录）。
2. 买错棚（如干旱日买遮雨棚）→ 允许，但不减免任何惩罚；UI 只在该日型高亮推荐的那一件。
3. 阳光不足 → 按钮禁用 + `garden.shelter.insufficient`，不弹窗。
4. 极端日型切换（跨零点）时棚自动失效，不提示。
5. 棚不进「还要 N 天」计算（不改变 `g`）。
6. 棚不影响晨露。
7. 棚不影响枯萎/死亡计时。
8. 棚在花盆卡与养护卡**两处都可买**，同一天第二处显示「今日已购」。
9. 棚的购买记录**不进天气条幅的完成态判定**（完成态只看动作，见 §9.5）。

## 5. 强制养护与惩罚（判定基准 = 2 水 1 肥）

### 5.1 规则表

| 天气 | 强制动作 | 完成判定 | 未完成 |
|---|---|---|---|
| 干旱 | 浇水 ≥ 1 次 **且** 当日买遮阳棚 | 两者都满足 | 每缺一项 −1%（B 口径） |
| 暴雨 | 施肥 ≥ 1 次 **且** 当日买遮雨棚 | 两者都满足 | 每缺一项 −1% |
| 大风 | 当日买挡风板 | 满足 | −1% |
| 极寒 | 当日买保温棚 | 满足 | −1% |
| 温和 5 种 | 无 | — | 0 |

**「浇水 ≥ 1 次」的判据**：当天该盆的浇水记录 ≥ 1 条即算完成。干旱日若需浇 2 次以上，**做 1 次就算完成强制**（剩余次数是收益，不是义务）。

### 5.2 两种惩罚口径

| 口径 | 定义 | 日均惩罚 |
|---|---|---|
| **A（宽松）** | 每个极端日**最多**罚 1%（不论几个动作没做） | **0.2000 %/天**（删高温后不变） |
| **B（严格，建议默认）** | 每个未做动作**各**罚 1% | **0.3000 %/天**（删高温前是 0.3200） |

`A = 1% × (7+5+5+3)% = 0.2000`；`B = 1% × (7×2 + 5×1 + 5×1 + 3×2)% = 1% × 30% = 0.3000`。
**B 为什么降了 0.02**：高温带了 2 个强制动作（浇水 + 遮阳棚），删掉它之后「动作总额度」从 32% 掉到 30%。
**建议取 B**：A 会让「两个动作只做一个」与「一个都不做」等价，孩子学不到「棚和浇水是两件事」。

### 5.3 惩罚结算位置（三条原则，全部免费满足）

- **P1**：结算后 `progress.clamp(0.0, 1.0)` —— 不为负，零字段。
- **P2**：**今天永远不进惩罚循环**，只罚已经过完（已关门）的日子 ⇒ 当天补救永远来得及，**不需要退款机制**。
- **P3**：游标是既有的 `stageStartedAt`，**本仓没有 `lastTickAt`**，不发明新字段；重复 tick 只累加新增量。

>
> **候选成因（按可能性排序，查的时候别从「时序系统性错位」开始）**：
> 1. **个别起点丢一次动作**（最可能）：`kPlantWaterIntervalMinutes = 30` 的冷却判定、或某次动作的 `ts` 跨零点被记到次日 ⇒ 那天少 1 次水（**≈0.7pp ≈ 0.1 天**）。单看很小，但**只有那些「最后一天正好差 0.1 天」的起点才会被顶过整整一天**，与「730 个起点里只有 1 个变 10」完全自洽。
> 2. **`stageStartedAt` 游标离开零点**（即上面机制 3 的真实放大）：非零点 tick 会让某段是半天段，**只拿半个 auto 增量却吃整天惩罚**。本节机制 3 早就写了这条，但当时估的是「真实使用 0.05~0.2 天/株」；在 7~9 天这种短周期上，半天的 auto 缺口就是 **3.4pp ≈ 0.5 天**，加上整天惩罚可到 **0.5~0.8 天**，足以把 9 顶成 10。
> 3. **`tickAll` 与浇水的先后**（下调）：若这是**系统性**错位，会把约 15%（≈110 个）起点集体顶掉一天，**不可能只动 1 个** —— 所以它只能以「个别起点」形式出现，不能当第一嫌疑。
>
> **已排除**：买棚（无棚才是最慢边界，买棚只会更快，方向相反）；量纲整体右移（整档 +1 会把众数从 8 变 9，但 QA 与本节的众数都是 **8**）。
>
> **定案方式**：QA 给出「跑出 10 的那个起点日期 + 天数定义（花谢日 vs 花期起算、`N` vs 下标 `i`）+ 每次 `tickAll` 的 `now` 是否在零点 + 3 次浇水的 `now` 怎么构造」；工程师用真代码**单跑该起点**，逐日打点（日型 / `g` / 当日增量 / 惩罚项 / **当日账本里该盆的浇水条数与施肥条数**）。判据很硬：**某天浇水 < 3 或施肥 < 1 ⇒ 坐实丢动作**；**每天都真是 3+1 ⇒ 那就是天数起算点晚了一天**。
>
> 🔴 **在定案前本节一律写「口径无关」的表述（实测最高 10）**，不许把它写成「A4 才会到 10」或「A1 就能到 10」。

### 5.6 Q2：复开花阶段惩罚是否减半

**定论：不减半。**

1. 惩罚是**绝对量**（−1% 进度/动作），不是按比例缩放。复开花 3 水 1 肥日进度 **6.86pp**、首花 15.13pp ⇒ 同样的 −1% 对复开花的相对权重是 **2.2 倍**；对零养护复开花（3.34pp）更是 **4.5 倍** —— 这是**设计上正确的**：复开花更依赖每日照料，不照料本就该更慢。
2. 绝对代价很小：B 口径下复开花 3 水 1 肥 **7.29 → 7.62 天，+0.33 天**（零养护 14.97 → 16.44，+1.47 天）；首花 +0.40 天。换算成「孩子多等几天」，都在可接受范围。（2026-11-02 校准：v6.1 这里写的「14.81 → 16.25，+1.44 天」是跟着 §5.4 的错值走的，已作废。）
3. 减半要多一个常量 + 一个 `bloomCount >= 1` 分支，收益只是把 **+4.6% 压到 +2.2%**，**性价比不成立**。
4. **留后门（写进代码注释，不实现）**：将来若玄参觉得复开花被罚太狠，在 `penaltyOf()` 里乘 `bloomCount >= 1 ? 0.5 : 1.0` 即可，一行开关。

### 5.7 Q3：32.33 天算不算虫草暂停 —— 必须计入，但不能进基准分母

**先把代码事实钉死**（`lib/domain/services/plant_growth_service.dart`）：

- `:861` `if (p.hasPestOrWeed) { return p.copyWith(stageStartedAt: now.isAfter(p.stageStartedAt) ? now : p.stageStartedAt); }`
  ⇒ 命中当天**不累加进度**，但**照常把基准推到 now** ⇒ 这段时长**永久损失**。
- `:836` 每日**独立** roll：`kGardenWeedRate = 0.40`、`kGardenPestRate = 0.30`（`prd_params.dart:928 / :931`），可同时出现 ⇒ 单日「至少一个」的概率 = `1 − 0.6 × 0.7 = **58%**`。
- 🔴 **本仓不存在 `kWeedPauseHours` / `kPestPauseHours` 两个常量**（此前文档引用过，是错的）。机制不是「暂停 N 小时」，是「整天不推进 + 基准前移」。

**关键性质**：损失量 = **上一次结算点到本次 tick 的整段时长**，所以它取决于 **tick 密度**，不是常数。清理虫草**救不回**这段（因为损失发生在 roll 之前的时段）。

| tick 密度 | 每日实际损失 | 零养护真实周期 |
|---|---|---|
| 每小时（`ChildTabAutoRefresh` 60s 轮询） | 58% × 1h/24h ≈ **2.4%** | **33.1 天** |
| 每 4 小时 | ≈ **9.7%** | **35.8 天** |
| 每天只开一次（08:00） | **58%** | **77.0 天** |

**定论**：
1. **基准分母不摊虫草**，因为它是「按次损失」不可写成常数；
2. 但**必须把上表附在测试用例旁边**，作为 G1a 的**上界说明**：G1a 的 32.33 天只对「App 高频使用」的孩子成立；
3. 🔴 **P1 风险上报**：现有代码的「暂停吃掉前一段时长」意味着**每天只开一次 App 的孩子会永久损失 58% 的生长时间**（77 天 vs 32.3 天）。这是**天气系统之外**的既有机制，本版不动代码，但需要单独立项请玄参裁定（建议改成「暂停期间只跳过受影响的时段，不清零前一段」）。

### 8.6 G5：单位 ☀ 换到的进度（相对无天气基线）

**算式（本版写死，便于复算）**：
`指标 = (天气版日进度 ÷ 天气版日成本) ÷ (无天气版日进度 ÷ 无天气版日成本) − 1`
无天气基线：3水1肥 = 15.00pp / 25.00☀；1水1肥 = 14.00pp / 15.00☀；1水0肥 = 11.00pp / 5.00☀。

| 画像 | 天气版 pp/☀ | 无天气 pp/☀ | 指标 | 判定 |
|---|---|---|---|---|
| 3 水 1 肥 | 15.1262 ÷ 23.65 = 0.6396 | 15.00 ÷ 25.00 = 0.6000 | **+6.60%** | ✅ 效率反而更高（`w`×1.07 把浇水拉值了） |
| 1 水 1 肥 | 13.1922 ÷ 15.35 = 0.8594 | 14.00 ÷ 15.00 = 0.9333 | **−7.92%** | ⚠️ 见下 |
| 1 水 0 肥 | 10.3380 ÷ 5.35 = 1.9323 | 11.00 ÷ 5.00 = 2.2000 | **−12.17%** | ⚠️ 最差，但未破 −15% 护栏 |

**为什么低养护档更亏**：道具是**按园买、固定 0.50☀/盆/天**（4 盆），它占 3 水 1 肥 23.65☀ 的 2.1%，却占 1 水 0 肥 5.35☀ 的 **9.3%**。所以**越是低养护，道具的相对负担越重** —— 这是「固定成本 × 小分母」的必然，不是 bug。护栏定在 **≥ −15%**，最差 −12.17% 留 2.8pp 余量，**本版不修**。

> 注：本版把 G5 的算式显式写出来了。v6.1 那三个数（+2.69 / −1.83 / +10.84）用的是「增量」口径、与本表标题不符，已作废；`E[g]` 从 0.9520 降到 0.9280 也让单位效率整体再降约 2.6%。

## 10. 感知链路：「还要 N 天」

> 🔴 **A5 修正（2026-11-04）**：「已浇水次数」口径**已作废**，改为「**当日额度满载**」，并补入 A4 的额度截断 / 雨水代劳、以及复开花独立速率线。原文保留在下方「原文口径」块内以便追溯，**冲突处以「现行口径」为准**。设计、算式与验收见 `docs/天气系统_A5_增量设计.md` §4。

**原文口径（v6.2 · 已作废，仅留档）**

```
剩余进度 pp = 300 − 当前累计进度（pp）
N = ceil(剩余 pp ÷ 当前日进度估计)
当前日进度估计 = 10 × g(今天) + 已浇水次数 × 1.0 × w(今天) + 已施肥 × 3.0 × f(今天)
```

**现行口径（A5 · 2026-11-04 起）**

```
# 剩余量按「本阶段」而非全生命周期 300pp（跨阶段后 stageStartedAt 被重置，全生命周期口径拿不到分段数据）
remaining = 1 − growthProgress                      # 0..1，1pp = 0.01

# 自然项：首花 24h/T×g；复开花走独立速率线（精品再 ÷1.5）
natural = bloomCount == 0
            ? 24 / growthHoursPerStage × g(今天) × kPlantAutoGrowthScale
            : kRebloomAutoProgressPerDay × g(今天) ÷ (isPremium ? 1.5 : 1.0)

# 养护项：次数取**当日额度**（不是「已做次数」）
care = min(3, waterQuota) × 浇水增益 × w(今天)
     + min(1, fertilizeQuota) × 施肥增益 × f(今天)

# 雨水代劳（A4 已进日结）
rain = rainWaterBonusPp                             # 暴雨 1pp / 其余 0

N = ceil(remaining ÷ (natural + care + rain)).clamp(1, 999)
```

> 🔴 **「已做次数」为什么必须作废（算式留档，别删）**：早晨尚未浇水时 `已浇水次数 = 0`，干旱日只剩自然项 `10 × 0.20 = 2.0 pp/天`，`remaining 50pp ⇒ N = 25 天`；同一时刻按当日额度满载则是 `2.0 + 3×1.0×3.00 + 1×3.0×0.60 = 12.8 pp/天 ⇒ N = 4 天`。**同一株花、同一时刻，两种口径差 6.4 倍（25 天 vs 4 天）**，且卡片文案「每天按时养护，还需约 {days} 天长成」本身就以「会做满」为前提 ⇒ 只能取满载。附带好处：满载口径下「浇水 ⇒ 进度↑ ⇒ N 不增」，一天内单调不增，不会出现「浇完水反而更久」的错觉。
> 🔴 **复开花必须走独立速率线**：复开花（花谢后 `status=growing`、进度回落 0.5）若沿用首花的 `24/T`（普通 10pp/天），「还要 N 天」会显示 **4 天**，而真值 `3.6pp/天` + 养护 ⇒ **7~12 天**（差 2.8 倍）。鉴别器是 `bloomCount`，不是 `status`。
> 🔴 **只用今天的天气**：不做未来逐日外推 —— `g` 变小使 N 变大是设计要的（见下条），逐日外推会把这个信息抹平。

- 只在**花园页**与**花盆卡详情**显示，不进首页。
- 天气变了（跨零点）→ `ChildTabAutoRefresh` 60s 纯函数比对自动刷新，不主动弹提示。
- 极端日 `g` 变小 → N 会变大，**这是设计要的**「今天没照顾好，花长得慢」，但文案不得写「因为你没照顾」（零指责原则）。

## 11. 技术前提与三处伪代码改法

### 11.1 R1 ~ R12（对齐架构师 6 条代码事实）

### 11.2 改法 1：`w` / `f` 从日结搬到即时侧

**位置**：`plant_growth_service.dart:1174`（浇水）与 `:1219`（施肥）。

```dart
// ── waterPlant() 内，替换原 :1174-1175 ──────────────────────────────
final String dayKey = _dayKey(now);
final WeatherDay wd = _weatherByDay[dayKey] ?? WeatherDay.neutral;   // tickAll 预取，见改法 3
final double progress = p.growthProgress +
    _careProgressGain(p, kPlantWaterProgressGain, kRebloomWaterProgressGain, sp)
        * wd.waterFactor;                 // ← w 乘在这里，不进日结
final Plant after = p.copyWith(
  growthProgress: progress > 1.0 ? 1.0 : progress,   // 上限不变
  waterUsed: true,
  lastWaterAt: now,
);

// ── fertilizePlant() 内，替换原 :1219-1221 ──────────────────────────
final double progress = p.growthProgress +
    _careProgressGain(p, kPlantFertilizeProgressGain, kRebloomFertilizeProgressGain, sp)
        * wd.fertilizeFactor;             // ← f 乘在这里
```

**注意**：`_weatherByDay` 必须在 `tickAll` 里预取并缓存到字段（或经构造参数传入），**不能在 `waterPlant` 里现查账本**——那会把一次点击变成一次 IO，且违反 R7 的同一模式。

### 11.3 改法 2：日结循环边界 + 惩罚只结算「已关门」的日子

**位置**：`plant_growth_service.dart:846-` `_advanceGrowth` 内，`while` 循环体。

```dart
// 循环外：先算今天关没关门（唯一判据，照 :881 的写法）
final DateTime today    = DateTime(now.year, now.month, now.day);
final DateTime todayEnd = today.add(const Duration(days: 1));
final bool dayClosed    = !now.isBefore(todayEnd);   // 过了本地零点才算关门

DateTime cursor = p.stageStartedAt;
while (cursor.isBefore(now)) {
  final DateTime dayEnd = DateTime(cursor.year, cursor.month, cursor.day)
      .add(const Duration(days: 1));
  final DateTime segEnd = dayEnd.isAfter(now) ? now : dayEnd;      // 完全沿用 :881
  final double segHours = segEnd.difference(cursor).inMicroseconds / 3600000000.0;
  final String dk = _dayKey(cursor);

  final double g = _weatherByDay[dk]?.growthFactor ?? 1.0;         // g 进日结，OK
  progress += segHours * g / sp.growthHoursPerStage * kPlantAutoGrowthScale;

  // ① 只有「这一段走完了整天」才允许落惩罚 ⇒ 今天永远不罚（P2）
  if (!dayEnd.isAfter(now)) {                                      // dayEnd <= now ⇒ 已关门
    progress -= _penaltyByDay[dk] ?? 0.0;
  }
  progress = progress.clamp(0.0, 1.0);                             // P1
  cursor = segEnd;
  // ...
}
// 循环结束后若 dayClosed 仍为 false（今天还没走完），今天只吃了 g、没吃惩罚 —— 符合 P2
```

**为什么不是 `while (cursor.isBefore(today))`**：现有循环还必须服务「今天这几个小时也要按今天的 `g` 计进度」的需求；把今天整体排除会让今天的进度延到明天才结算，`「还要 N 天」`会跳变。**正确做法是「循环照旧，惩罚加关门判据」**，语义等价于 `dayClosed`，但零回归风险。

### 11.4 改法 3：`tickAll` 里预取天气表与惩罚账本（唯一 `await` 点）

```dart
// ── tickAll() 开头，先例同 _validFocusDayKeys ──────────────────────
final Set<String> days = _daysCoveredBy(plants, now);   // 近 90 天自然日 key 集合
_weatherByDay = <String, WeatherDay>{
  for (final String d in days) d: WeatherSystem.ofDay(d),   // 纯函数，零 IO
};

// 唯一 await：把「每天该罚多少」一次性算好（每盆每天一个 double）
_penaltyByDay = <String, double>{};
for (final String d in days) {
  final bool shade = (await _sunlight.countByRefTypeAndRefIdOnDay(
        refType: 'shelter_shade', refId: 'garden', day: d)) > 0;   // R8/R9：只用既有方法
  _penaltyByDay[d] = _weatherByDay[d]!.penaltyFor(
    hasShade: shade, /* 动作侧由 plant 自身字段判定 */);
}

// 然后同步调用，循环内零 await
for (final Plant p in plants) {
  final Plant np = _advanceGrowth(p, sp, now, wfdDays);   // 同步，读上面两张表
  ...
}
```

**四条硬约束**：
1. `_advanceGrowth` 内**不得出现 `await`**（R6）。
2. `_penaltyByDay` / `_weatherByDay` 是**批内缓存**，每次 `tickAll` 重建，不落库、不跨 tick 复用。
3. 窗口 `_daysCoveredBy` 必须覆盖最长可能跨度 → 取 **90 天**。最长跨度是**精品首花·零养护·B 口径**（设计 69.12 天，单起点整数天最差 **77 天**，§5.4.1），**不是**精品复开花（那只有 22.45~25.94 天）。90 天对 77 天留约 17% 余量。
   ⚠️ 实现上该值是「**下限保证**」而非「上限截断」：窗口起点取 `min(各盆 stageStartedAt 最早日, now − 90 天)`，即覆盖优先。改成 `max` 会让超窗日子查不到账本事实 ⇒ 老盆远古极端日被**静默**罚满 2pp（不抛异常、不打日志），属最难查的一类 bug（见 `plant_growth_service.dart` 的 `_weatherWindowDays` 注释）。
4. 惩罚判定的**动作部分**（浇水次数 / 施肥次数）本来就落在 `Plant` 上（`waterUsed` / `fertilizerUsed` / 当日账本 `plant_water`），不需要额外查询。
