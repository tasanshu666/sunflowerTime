## 1. 空间布局（带坐标）

### 1.1 现状基线（A2 封版，逐位锁定）

| 件 | 坐标 | 依据 |
|---|---|---|
| 薄行 `Positioned` | `top = (embedded ? 12 : 60) − 6` ⇒ **6 / 54** | `garden_page.dart:2785` |
| 薄行命中容器 | 高 **44** | `:2775-2778` |
| 薄行视觉带 | `y = 12..44`（chips 28 @ 12..40、胶囊槽 32 @ 12..44、按钮 32 @ 12..44） | `:2780`、测试 `weather_a2_test.dart:1298-1322` |
| 花盆网格顶 | `y = 12`（`_buildGardenBody` 的 `EdgeInsets.fromLTRB(12, 12, 12, 0)`） | `garden_page.dart:2607` |
| 第一排格高 | 390 宽：`gridInnerWidth 366 → cellW (366−12)/3 = 118 → cellH = 118/0.55 ≈ 214.5` | `garden_pot.dart:177` `cellAspectRatio = 0.55` |
| 花盆图形顶 | ≈ `y 38`（格顶 12 + 阴影带 12% ≈ 26） | `gardenShadowHeightFactor = 0.12` |

⇒ 现状薄行只压到花盆图形的 `38..44`（6pt），**几乎不遮**。

### 1.2 🔴 冲突的量化

§9.9 要求条幅 `top: 0`、**全宽**、高 **56**：

- 覆盖区间 `y = 0..56`，而薄行视觉带是 `12..44` ⇒ **完全重叠**；
- 薄行右端的**道具按钮是买棚唯一入口**（`garden_page.dart:2841` `_shelterBoughtToday` → `GardenWeatherRow.showShelterButton`）⇒ 被盖 = 买不了棚 = **条幅的 todo 态自锁**（永远做不完）；
- 薄行左端的 chips（碎片 + 两种子）同样被盖 ⇒ 20% 天数丢资源入口。

**这不是"排布不好看"，是功能自锁 + 入口丢失。**

### 1.3 为什么"改宽度/改横向"不可行（一条硬论证）

A2 的宽度预算是**把 366pt 用满**的：chips `179` + 天气区 `187`（测试夹具 `weather_a2_test.dart:1301` `chipsWidth: 179`）。条幅若与 chips 并排，剩余宽度 = `366 − 179 − 24(图标) − 90(按钮) ≈ 73pt` ⇒ 英文 todo 文案 60 字符需 **6 行**（`60 × 6.2 ÷ 73`）⇒ 完全不可用。

⇒ **条幅要全宽，就只能把 chips 与胶囊**纵向**让开。** 横向塞不下，这是算术结论，不是偏好。

### 1.4 选定布局

```
极端日（4 种）                       温和日（5 种）—— 逐位照旧
──────────────  Positioned(top:6/54, left:12, right:12) ──────────────
┌──────────────────────────────────┐  ┌─────────────────────────────┐
│ WeatherBanner  56 × 全宽          │  │ [chips]        [天气胶囊]   │ 44
│  位图图标 24 │ 文案 2 行 │ 按钮 32 │  └─────────────────────────────┘
└──────────────────────────────────┘  视觉顶 y=12（不变）
  SizedBox(6)
┌──────────────────────────────────┐
│ [chips]                          │ 28
└──────────────────────────────────┘
```

| 坐标 | 温和日（现状） | 极端日（A3） |
|---|---|---|
| 浮层 `Positioned.top` | 6（embedded）/ 54（standalone） | **同值，不改** |
| 条幅 | — | `y = 6..62`（embedded）/ `54..110`（standalone），高 **56**、全宽 |
| 条幅→chips 间距 | — | **6** |
| chips 行 | `y = 12..40` | `y = 68..96`（embedded）/ `116..144`（standalone），高 28 |
| 天气胶囊 | `y = 12..44` | **不渲染**（由条幅承接） |
| 顶部带总高 | 38（6..44） | **90**（6..96）/ 138（54..144） |
| 第一排花盆被压 | `38..44` = **6pt** | `38..96` = **58pt**（占花盆图形 188pt 的 **31%**） |

**实现形态（一处改动点）**：把 `garden_page.dart:2782-2849` 那个 `Positioned` 的**唯一子项**从 `Row(spaceBetween)` 换成

```dart
Column(
  mainAxisSize: MainAxisSize.min,
  crossAxisAlignment: CrossAxisAlignment.stretch,
  children: <Widget>[
    if (banner.mood != WeatherBannerMood.none) ...<Widget>[
      WeatherBanner(state: banner, onTap: _showGardenHelp, onShelterTap: _onShelterTap, …),
      const SizedBox(height: 6),

```

- **温和日**：`Column` 只有 `Row` 一个子项 ⇒ 高度 = 44、位置 = 6/54、`crossAxisAlignment.start`、chips 的 `Padding(top: 6)` 全部照旧 ⇒ **A2 几何逐位不变，零回归**。
- **极端日**：`Padding(top: 6)` 必须**去掉**（否则 chips 视觉顶变成 74，与条幅间距变 12）。⇒ 用 `if (isExtreme) Row(...) else Padding(top: 6, child: Row(...))`，或把 `top` 参数化（两者等价，工程师选后者更少分支）。

## 2. 三态判定（纯函数、零 IO、可测）

新增 `lib/domain/services/weather_banner_logic.dart`：

```dart
/// 条幅三态（§9.2）。
enum WeatherBannerMood { none, todo, done }

/// 一次判定的完整结果（不可变；UI 只读它，不再自行推导）。
class WeatherBannerState {
  final WeatherBannerMood mood;
  final WeatherKind kind;
  /// 该日型对应道具 refType；温和日为 null。
  final String? shelterRefType;
  const WeatherBannerState(this.mood, this.kind, this.shelterRefType);
}

/// 园级判定：园内**任意一盆**动作做齐 + 道具已买 ⇒ done（§9.3）。
/// 🔴 纯函数：全部入参都是**已算好的事实**，函数内零 IO、零时钟、零 context。
WeatherBannerState resolveWeatherBanner({
  required WeatherDay day,
  required bool anyWateredToday,       // 任一盆 waterUsedToday ≥ 1
  required bool anyFertilizedToday,    // 任一盆 fertilizeUsedToday ≥ 1
  required bool shelterBoughtToday,    // countByRefTypeAndRefIdOnDay(refType,'garden',dayKey) > 0
  required bool sessionDone,           // 本会话 Set<String> 命中（§3）
});
```

**判定顺序（穷举，无 default 分支）**

```
① kind.isMild                 ⇒ none                （5 种温和日，不问任何入参）
② sessionDone                 ⇒ done                （本会话已置上，§3）
③ 动作齐 && shelterBoughtToday ⇒ done
④ 其余                        ⇒ todo
```

**「动作齐」按日型（逐条对齐 §5.1 规则表 `:224-230`）**

| 日型 | 动作判据 | 道具 |
|---|---|---|
| 干旱 `drought` | `anyWateredToday`（**浇 1 次即算**，§9.3 `:639`） | `shelter_shade` |
| 暴雨 `rainstorm` | `anyFertilizedToday`（浇水额度为 0，**不判浇水**） | `shelter_rain` |
| 大风 `wind` | 无动作 | `shelter_wind` |
| 极寒 `cold` | 无动作 | `shelter_warm` |

> 🔴 大风/极寒**不判动作**：`anyWateredToday` 等入参对它们**不参与判定**（不是"传 false"，是根本不读）。这条写成变异点 M-A3-4：若写成"所有日型都要求动作齐"，大风/极寒将永远 todo。

**数据来源（全部既有接口，零新方法、零 schema）**

| 入参 | 来源 | 依据 |
|---|---|---|
| `day` | `WeatherSystem.ofDay(DateTime.now())` | `garden_page.dart:2739`（已在算，页面唯一入口） |

## 3. 完成态的生命周期（Q2 的正面回答）

### 3.1 结论

**`done` 的事实源是账本，不是内存 Set。** 内存 Set 只是"本会话已确认"的加速/防闪，删掉它功能仍正确（只会多一次重算）。

### 3.2 为什么重算是幂等的

| 完成条件 | 落地事实 | 生命周期 |
|---|---|---|
| 干旱「浇水 ≥1」 | 阳光账本 `refType='plant_water'`、`refId=<植物id>`、当日行 | **append-only，永不删** ⇒ 当日永远可重查出 |
| 暴雨「施肥 ≥1」 | `plant_fertilize` 同日行 | 同上 |
| 道具 | `refType='shelter_shade'…`、`refId='garden'`、当日行 | 同上（`countByRefTypeAndRefIdOnDay` `:202`） |

⇒ 切 tab、退出花园、进程被杀后重进，**重算得同一结果** ⇒ §9.3「当天不回退」**成立**，而且是靠账本而不是靠内存。

### 3.3 内存 Set 的作用（不是为了"不回退"）

```dart
final Set<String> _doneWeatherKeys = <String>{};   // 元素 = dayKey('yyyy-MM-dd')
```

只解决两件事：① **完成瞬间立刻切态**（不等下一次 `_reload` 的异步账本查询，满足 §9.8「立即」）；② 避免 `careQuotas` 查询期间出现 `done → todo → done` 的闪跳。

**失效条件**：`dailyResetKey != 当前 dayKey` 时 `clear()`（跨零点）。跨零点后账本重算自然返回 todo ⇒ 与清除等价，两条路径互为兜底。

### 3.4 🔴 必须落纸的口径降级（一条真实例外）

§9.3 原文「完成态一旦置上，**哪怕后续额度用尽、盆被铲除也不回退**」。

- **额度用尽** ⇒ 账本行还在 ⇒ 重算仍 done ✅ 成立。
- **盆被铲除** ⇒ 那盆从 `_plants` 消失，`careQuotas` 查不到它的 `waterUsedToday` ⇒ 若园里**只有那一盆**做过动作，重算会退回 todo ❌ **不成立**。

**处置（选其一，本设计选 A）**

| 方案 | 做法 | 代价 |
|---|---|---|
| **A（选）** | 承认边角：**「不回退」= 同一页面会话内不回退；重建后以账本重算为准**，唯一例外是"做齐后把那一盆也铲了" | 零代码成本；边角概率极低（当天、园里仅 1 盆、做齐后立刻铲） |
| B | 写一条 0 元账本行 `weather_banner_done` | 违反 §9.7"不给奖励"的纯粹性（虽 0 元）、孩子端阳光账单要多一条过滤、`refLabelOf` 必须同步否则显示"其他"（`prd_params.dart:1155-1160` 已有该警告）⇒ **不建议** |

⇒ **§9.3 的那句要改成**：`完成态在**同一页面会话内**不回退；页面重建后按当日账本重算（动作与道具都是 append-only 事实），**唯一例外**是"完成之后把做动作的那一盆铲除且园内无其他盆完成"，此时会退回 todo —— 已评估、接受、不修。

| ② | 页面内**直读挂钟** | `garden_page.dart:2739` `final WeatherDay todayWeather = WeatherSystem.ofDay(DateTime.now());` |
| ③ | `WeatherSystem` **无日型注入接缝**，全仓无 `package:clock`（`grep -n clock pubspec.yaml` 为空） | 只暴露纯静态 `ofDay` / `dayKey` / `weightOf` |

⇒ 3 个调用点、**7 次执行**（`:1806`×2、`:2120`×2、`:2177`×3）在**极端日全红**（约 20% 的日历天），温和日全绿。这是典型的"今天绿、明天红"。**必须在 A3 之前解决，不能带着上线。**

### 13.2 方案：`TodayWeather` 值对象 + 一个 provider

新增 `lib/core/di/today_weather.dart`（**唯一读挂钟的地方**）：

```dart
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:sunflower_time/domain/services/weather_system.dart';

/// 今日天气的**同源快照**：`day` / `dayKey` / `observedAt` 全部由**同一个 `now`** 派生。
///
/// 🔴 为什么是一个值对象而不是三个 provider：拆开后每多一个 provider 就多一次
///    `DateTime.now()`，跨零点时 `day` 与 `dayKey` 可能分属两天 —— 那正是 A3 要修的
///    那个 bug 的同一形状（§13.4）。
class TodayWeather {
  final WeatherDay day;
  final String dayKey;       // 'yyyy-MM-dd'，与 day 同一瞬间
  final DateTime observedAt; // 同一瞬间；写账本 / 传 service 都用它
  const TodayWeather({required this.day, required this.dayKey, required this.observedAt});
}

/// 今日天气 provider（页面唯一入口；测试用 `overrideWithValue` 钉日型）。
final todayWeatherProvider = Provider<TodayWeather>((ref) {
  final DateTime now = DateTime.now();
  return TodayWeather(
    day: WeatherSystem.ofDay(now),
    dayKey: WeatherSystem.dayKey(now),
    observedAt: now,
  );
});
```

**import 关系**：`today_weather.dart` → `flutter_riverpod` + `domain/services/weather_system.dart`；`garden_page.dart` → `core/di/today_weather.dart`。**无环**（`weather_system` 不反向依赖 `core/di`）。`providers.dart` **不动**（`TodayWeather` 是值对象不是 DI 装配，混进 providers.dart 会让那个文件再涨一截）。

### 13.3 五个调用的同源化（**少改一处就分裂**）

| 行 | 现在 | 改成 |
|---|---|---|
| `:568` `_reload` 内 | `WeatherSystem.ofDay(now).kind.shelterRefType` + `WeatherSystem.dayKey(now)` | `final TodayWeather w = ref.read(todayWeatherProvider);` 然后用 `w.day.kind.shelterRefType` + `w.dayKey` |
| `:1693` `_shelterRefTypeToday` getter | 独立 `DateTime.now()` | **该 getter 已删除**（T00 实施时）：唯一调用点 `_onShelterTap` 改为在开头锁一次 `TodayWeather w`，getter 留着只会让后来人再读一次钟 ⇒ 此处的读钟数 **1 → 0**，比「改成 provider 读」更彻底 |
| `:1759` `buyShelter(DateTime.now())` | **第三次**独立读钟 | `buyShelter(w.observedAt)`，`w` 由 `_onShelterTap` 开头锁一次并透传（§13.5） |
| `:1872` `batchNoneWaterMessage(day: …)` | `WeatherSystem.ofDay(now)` | `ref.read(todayWeatherProvider).day` |
| `:2739` 首帧天气 | `WeatherSystem.ofDay(DateTime.now())` | `final TodayWeather today = ref.watch(todayWeatherProvider);` |

### 13.4 🔴 对主理人第 2 条坐标的更正（bug 是真的，坐标要换）

主理人说「`:1693` 与 `:568` 是两次独立 `ofDay(DateTime.now())`，跨零点购买会出现按今天的 ref 判断、按明天的 key 记账」。

- **`:568` 本身自洽**：`WeatherSystem.ofDay(now)`（`:568`）与 `WeatherSystem.dayKey(now)`（`:576`）用的是**同一个局部 `now`** ⇒ 不会错位。
- **真实错位是另一对**：`_onShelterTap` 通过 `_shelterRefTypeToday`（`:1705` → `:1693`）在**点击那一刻 T1** 读钟 —— 用于**确认卡文案与道具名**；而 `_buyShelterNow` 用 `buyShelter(DateTime.now())`（`:1759`）在**确认之后 T2** 再读一次钟 —— 用于**真实记账**。T1/T2 之间隔着一整个弹窗交互（孩子可能看很久）。
  ⇒ 23:59:5x 点开确认卡、23:59:5y 点「搭起来」就会：**卡片写"要搭遮阳棚吗"、账本按次日写成 `shelter_rain`**，同时 `_shelterBoughtToday` 被置 true（`:1765`）⇒ UI 显示"今日已购"，与账本那行对不上。
- 结论：**bug 成立，唯一可复现路径是 `:1693` ↔ `:1759`**（不是 `:1693` ↔ `:568`）。按 `:568` 去改是安全的但修不掉它。

### 13.5 顺带修复 + 跨零点刷新

1. **同源锁时**：`_onShelterTap()` 开头 `final TodayWeather w = ref.read(todayWeatherProvider);`，透传给 `_buyShelterNow(w)` ⇒ 卡片与账本**由构造保证同源**。
   **口径**：按**用户点按钮那一刻**的自然日记账（弹窗开 20 分钟也不改记到哪一天）—— 与方案 §4.2「当天买当天有效」一致。
2. **跨零点刷新**：Riverpod `Provider` 会缓存 ⇒ 在 `onTabRefreshRequested()`（`child_tab_refresh.dart:97`，本页 `:178` 已 mixin）里先 `ref.invalidate(todayWeatherProvider)` 再 `_reload()`。成本：一次 32 位哈希（`WeatherSystem` 自带 `dayKey → WeatherDay` 缓存）。
3. **注释订正**：`garden_page.dart:1869-1870` 现写「本页时间源是 `DateTime.now()`，widget 测试碰不到暴雨日」—— 接缝之后**不成立**，改为「本页天气来自 `todayWeatherProvider`（测试可 override 钉任意日型，含暴雨）」。
