> 用途：把文档之间的分歧钉死成唯一真源，作为 workbuddy 的约束输入

> **优先级**：本表 > 开发计划 v1.0 > 验证计划 G0–G2 > PRD v2.0。冲突处一律以本表为准。

## 总纪律（三条）

1. **唯一真源顺序**：本表 > 开发计划 v1.0 > 验证计划 > PRD v2.0。
2. **参数单点**：所有可调数值集中在 `core/constants/prd_params.dart`，每条注释标 PRD 节号。任何文件出现第二个相同含义的字面量即为缺陷。
3. **口径巡检**：每个里程碑收尾，全仓 grep 关键数字，确认全部来自常量引用。AI 生成速度越快，这一步越不能省。

## C3「有效专注」同名不同义

**分歧**：G1 判据＝横屏放置 ≥5min；WFD 口径＝≥15min 且完成率 ≥90%。

**订正（2026-09-15 巡检）**：5 分钟在 G1 判据与结算门槛里是同一个概念（验证计划 §2.5 明确「对齐 §6.2」），只需一个常量。原裁定把它拆成两个名字，属过度拆分，现合并。

**裁定**：

```dart
// core/constants/prd_params.dart
const int kMinFocusMinutes = 5;                // 单次有效专注门槛：G1 放置判据（验证计划 §2.5）＋结算门槛（PRD §6.2）
const int kValidFocusMinutes = 15;             // WFD：一个有效专注日（验证计划 §3.3）
const double kCompletionRateThreshold = 0.90;  // WFD：完成率门槛
// completion_rate = actual_focus_min / duration_setting
```

两个分钟常量不得互相引用，不得在别处出现字面量 `5` / `15` / `0.9`。**`kPlaceMinMinutes` 不得存在**（已废止，与 `kMinFocusMinutes` 同义）。

## C5 免确认月上限 vs 可调月池

**分歧**：月池可调 100–1200；免确认月累计上限写死 100/40；池调低后 25% 是否重算未定。
**定型（2026-09-22 玄参拍板）**：可调区间收敛为 **50–500**，且 M2 落地为**周度池**（每周一 0 点重置）；免确认上限仍按 `min(天花板, 池 × 25%)` 实时计算。

**裁定**：

```
monthlyAutoApproveCap = min( 固定天花板, 当前月池 × 25% )
固定天花板：高年级 100 / 低年级 40
```

池降到 200 时，上限随之降到 50（高）/ 20（低）。写死的 100/40 是天窗，不是恒定值。

## C9 M1 批次口径裁定（5 项悬空口径闭环）

**背景**：M1 批次二收尾时，`docs/产品开发文档_M1.md` §4 与 `docs/软件设计文档_M1.md` §10 登记 5 项 PRD 与实现不一致的悬空口径，需产品拍板。2026-09-15 经玄参大人逐条裁定，结论如下（均"保持现状"，M1 无需改代码，仅钉死为唯一真源）。

| # | 口径 | 裁定 | 理由 |
|---|---|---|---|
| 1 | 送光基准 | 保持按会话进度送光（离席跨 1/3 边界仍送光） | 光定位为"进度反馈"非"在场奖励"；与倒计时同源自洽；改"仅到场"需可靠在场检测（无触摸信号关、传感器静止停发事件 B31 已证不可靠），M1 性价比低 |
| 2 | 离席冻结倒计时 | 保持不冻结 | 孩子承诺时长即应放满；在场检测不可靠，冻结易被绕过/误判 |
| 3 | 时长档位 | 保持 15/20/25/30/45 | 开发指令以 45 替换 10 档；10 分钟过短不具专注意义 |
| 4 | 无触摸信号 | 保持关闭（留接口） | PRD §4.2 打盹屏不可交互与 §4.3 离席信号冲突；专注本就不该触摸，开启误报离席 |
| 5 | 唤醒补判时刻 | M1 接受恢复瞬间补判；M3 视真机数据再评估前台服务 | OS 挂起 ticker 为技术现实，上前台服务代价大，M1 不值 |

**代码纪律**：以上裁定均"保持现状"，M1 不改代码；若后续 M3 评估上前台服务或开启无触摸信号，须重新走裁定。

## C10 定价取消分龄系数 K（2026-09-21）

**分歧**：原设计消耗侧价格 = `baseCost × 分龄系数 K`（低 1.0 / 中 1.2 / 高 1.5），孩子端显示价与扣费价被 K 放大（家长设 20、高年级孩子看到/扣 30）。真机反馈数值对不上。

**裁定**：**定价不再叠加分龄系数 K**。家长设定价 = 孩子显示价 = 实际扣费价，三者统一为 `baseCost`。

**代码纪律**：
- `RedemptionOrchestrationService._priceFor(RewardTemplate, AgeTier)` 直接 `return t.baseCost`；`store_page` 兑换价直接取 `tpl.baseCost`。
- 删除 `core/utils/math_ext.dart` 的 `applyAgeTierK`（已无调用点）。
- `age_tier_params.dart` 的 `k` 常量与 `ageTierK()` **保留**为档位参数单点，但**生产定价链路不得再调用**（仅供未来分档展示复用）。`reward_template.dart` / `reward_seed.dart` / `age_tier_params.dart` 文件头已注明此决策。
- 巡检：全仓不得出现 `applyAgeTierK(` 调用；定价路径只应出现 `baseCost`。

## C11 每日额度：取消分段软顶，改「两条独立额度线」（2026-09-23）

**分歧**：PRD §4.5 公式①、开发计划 v1.0 T10、验证计划 §4.3 都写「软顶三段：0–60 全额 / 60–90 计 50% / 90–110 计 20% / 硬顶 79」，而 M4 已上线的「每日专注上限」是年段三档 60 / 90 / 120。两套数作用在同一份产出上，互相矛盾：
- 高年段孩子专注满 120 分钟只拿得到 **79** 阳光 —— 「120」是摸不到的天花板；
- 该 79 实际是**按会话**各自过软顶（`settle()` 里套的是本次会话自己的原始产出），一天多场专注可远超 79。

**裁定（玄参，2026-09-23）**：

1. **取消分段打薄**。专注产出恒为 **1 分钟 = 1 阳光**，不再有任何折损率。
2. **每日专注上限跟随年段**：低 **60** / 中 **90** / 高 **120**（对应 1–2 / 3–4 / 5–6 年级）。因 1:1，该上限同时是「当日专注分钟上限」与「当日专注阳光上限」。
3. **成长奖励另有独立日上限** `kTaskCheckinDailyCap = 79`。两条额度线**各读各的账目类型**（专注 `focus_session`、成长 `task_checkin`），**互不挤占**。
4. **「其他年级无限制」不落地**：`AgeTier` 只有低 / 中 / 高三档，App 无第 4 档入口；产品只服务 1–6 年级，现状即满足。
5. **额度必须三道拦**：选时长页灰掉超额度档位 → 开始前按剩余额度截断 → **结算时再硬截断一次**（唯一可靠兜底，防计时器因「离席恢复」多算）。

**数学原因（为什么不能两者兼得）**：分段的第一段本身即「60 分钟以内全额」，因此「封顶值跟随年段」与「分段打薄」不能共存 —— 一旦封顶降到年段值，超出年段的部分必然零收益，打薄没有中间地带。

**废止清单（代码中不得再出现）**：

| 废止对象 | 原位置 |
|---|---|
| `kSoftCapDailyMax` / `kSoftCapSeg1` / `kSoftCapSeg2` / `kSoftCapSeg3` / `kSoftCapSeg2Rate` / `kSoftCapSeg3Rate` | `prd_params.dart` |
| `computeSoftCap(...)` | `math_ext.dart` |
| `TaskCheckInOutcome.cappedBySoftCap` | 改名 `cappedByDailyCap` |
| `_softCapGrant` | 改名 `_dailyRewardGrant` |

**代码纪律**：
- 专注侧额度单点收口在 `math_ext.dart` 的 `effectiveFocusSunlight({focusSunlight, remainingAllowance})`。额度消耗的**唯一真源**是账本 `refType='focus_session'` 的当日净额（`SunlightService.focusEarnedToday` / `focusRemainingToday`）；页面与服务**不得各自求和** `actualFocusMin`。
- 成长侧单点收口在 `task_checkin_service.dart` 的 `_dailyRewardGrant`，**只读 `checkInRefType` 自身账目**。不得再读当日全部 `earn` —— 那会让专注 / 家长赠予一拿满就挤掉成长奖励（「孩子打卡却不发阳光」），这是本次一并修掉的旧 bug。
- `SunlightService.settle` 必须收 `required int dailyFocusCap`（由调用方从 `AppSettings.dailyFocusCap` 传入，服务不另存一份）。专注与任务奖励**分两条账目**写：任务奖励若并进专注那条，其 `net` 会被计入「已用专注额度」，让下一场专注少拿阳光。
- **巡检（只针对代码）**：`lib/` 与 `test/` 内**不得出现** `computeSoftCap` / `kSoftCap` / `cappedBySoftCap` / `softCap` / `cappedBySoftCap`。文档侧允许在**废止清单与历史 bug 台账**中保留旧名（用于追溯），但**描述现行规则**时一律用「额度」口径，不得再写旧公式。

**效力**：本条优先于 PRD §4.5「软顶三段 + 硬顶 79」、开发计划 v1.0 T10「阳光记账与软顶」、验证计划 §4.3「软顶三段写死」三处旧表述。PRD 正文的软顶公式**保留为历史版本**（PRD 由玄参自行维护，不在本次回写范围内）。
